# B1.4 — Event log + checkpoints

**Phase:** 1 · **Track:** B · **Est:** 4d · **Status:** done
**Depends on:** B1.2 · **Blocks:** B1.5, B1.6, G4.1
**Plan refs:** §5.4, §12.7

## Goal
Event-sourced session persistence: the append-only log is the source of truth; checkpoints
are derived snapshots at phase transitions enabling resume, fork, and time-travel.

## Subtasks
- [x] Full `session`, `session_event` (append-only, `UNIQUE(session_id, event_seq)`,
      kinds per §12.7), `message`, `checkpoint` (append-only), migrations replacing T0.8's
      minimal versions; RLS + isolation tests. `session`/`session_event`/`message` were
      already incrementally extended in place by B1.2/B1.3 (not "replaced" — the same
      forward-compatible-subset pattern T0.8's own docstring promised); this task adds the
      new `checkpoint` table plus `session.forked_from_checkpoint_id`.
- [x] Event append API used by interpreter/runtime — monotonic `event_seq` allocation safe
      under the single-writer lock. Already built (B1.2's `_next_event_seq`); unchanged.
- [x] Checkpoint written at **every phase transition** (not every message): `{phase, state,
      actor_cursor, entity_versions, knowledge_version_pins}`. `make_checkpoint_hook`
      plugs into B1.2's `checkpoint_hook` seam for real.
- [x] Resume: load latest checkpoint + replay trailing events → identical in-memory state
      (property test). Scoped to `(phase, state)` — see design notes for why
      `actor_cursor` is deliberately excluded from what "replay" reconstructs.
- [x] Fork: new session rooted at any checkpoint with knowledge version pins copied from it
      (`forked_from_checkpoint_id`); the API exists now, UI later.
- [x] SSE event kinds aligned with `session_event.kind`; `Last-Event-ID` = `event_seq`.
      Already true — T0.8's SSE layer reads `kind`/`payload` generically off the row/pubsub
      message, never hardcoding which kinds exist. Verified, not modified.

## Acceptance criteria
- [x] State reconstructed from checkpoint+tail equals state carried in memory across 100
  randomised turns (property test).
  `test_state_reconstructed_from_checkpoint_and_tail_matches_live_state_across_100_turns`:
  drives the cyclic MVP flow through 100 interpreter steps with randomised turn content
  (seeded for a non-flaky test), then confirms `reconstruct_state` — using *only* the
  latest checkpoint plus the `session_event` tail after it, never the live `session` row —
  reaches the exact same `(phase, state)` the live row actually has. A sanity assertion
  (`state["round"] > 0`) guards against the property vacuously passing because nothing
  happened.
- [x] Fork at turn N: parent continues, child diverges, no shared mutable state (test).
  `test_fork_at_a_checkpoint_diverges_without_touching_the_parent`: forks at the
  first checkpoint (`player_act`, `round=0`), advances the *parent* several more steps and
  confirms the child is untouched, then advances the *child* and confirms the parent is
  equally untouched — proving isolation in both directions, not just one.
- [x] No UPDATE/DELETE grants on `session_event`/`checkpoint` (grant test).
  `session_event`'s grant was already fixed and tested during the Phase-0/1A review
  (`tests/isolation/test_append_only_grants.py`, which is precisely why that test exists);
  `checkpoint` is now registered in the same enforced set. Confirmed live: the suite's own
  `test_no_unexpected_append_only_tables_appeared` guard caught `checkpoint` as
  unregistered *before* this registration, proving the guard actually works, not just that
  the grant happens to be correct.

## Design decisions

- **`reconstruct_state` deliberately does not reconstruct `actor_cursor`.** Only
  `phase_transition` events change `(phase, state)` (message events don't mutate state —
  see `core.process.interpreter`), so those two are fully derivable from checkpoint+tail.
  `actor_cursor`, by contrast, changes on *every* actor turn via B1.3's scheduler, which
  writes it directly to the live `session` row and emits no event recording the delta —
  reconstructing it from the log alone isn't possible with the current event schema. Since
  `actor_cursor` is already continuously, transactionally live-persisted independent of
  checkpoint boundaries (B1.3), this isn't a functional gap for resume (the live row always
  has the current cursor) — it's specifically a boundary on what the checkpoint+replay
  *property test* can prove, documented rather than silently narrowed.
- **The append-only-grants gap-that-was-already-fixed is not a coincidence.** `session_event`
  shipped in T0.8 without its `REVOKE UPDATE, DELETE`, found and fixed during the Phase-0/1A
  review specifically *because* there was no test asserting append-only grants at all. That
  review's fix (`tests/isolation/test_append_only_grants.py`) was explicitly designed with a
  `test_no_unexpected_append_only_tables_appeared` guard so the *next* append-only table
  (this task's `checkpoint`) couldn't repeat the same mistake silently — confirmed live: the
  guard failed with exactly `{'checkpoint'}` the moment the table existed, before this task
  registered it.
- **A second circular-FK-at-CREATE-TABLE-time bug, same shape as A1.1's, this time between
  `session` and `checkpoint`** (a checkpoint FKs to its session; a forked session's origin
  pointer FKs to a checkpoint). Declared with `ForeignKeyConstraint(..., use_alter=True)`
  in `SessionRow.__table_args__`, the identical fix A1.1 used for
  `knowledge_source`/`knowledge_source_version`'s identical shape — found immediately via
  `alembic check`'s "unresolvable cycles" warning, not by a failing test later.
- **`knowledge_version_pins` is real** (A1.8's `resolve_effective_version_id` per
  workspace-attached source, computed fresh at each checkpoint write) **but
  `entity_versions` is always `{}`.** Consistent with B1.3's own finding: there is no
  `entity`/`entity_schema` table anywhere in Phase 1's task list. The column exists so a
  later phase's entity work extends this schema in place rather than adding a new one —
  same pattern as B1.3's entity-field injection seam, one layer up.
- **Fork copies session-row state, not the checkpoint's own identity.** The forked session
  gets a brand-new row (`current_phase`/`state`/`actor_cursor` copied *by value* from the
  checkpoint, `forked_from_checkpoint_id` set for provenance) — never a shared reference to
  the parent's mutable state. This is what the isolation test actually proves: advancing
  either session afterward mutates only that session's own row.
