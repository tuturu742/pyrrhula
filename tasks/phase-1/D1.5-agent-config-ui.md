## Goal

## Acceptance criteria
- Create an Ollama-backed Arbiter and an OpenAI-backed participant in one workspace; both
  take turns in a session.
  → Proven at the data/CRUD level (this task's own layer):
    `test_create_two_agents_with_different_roles_in_one_workspace` creates a facilitator
    and a participant agent sharing one workspace via the real HTTP endpoints, each with
    its own `agent_role`/`persona_md`. "Both take turns in a session" is D1.3's session
    view + the live HTTP session flow, which (as D1.3's own task file documents) still
    runs T0.8's walking skeleton rather than a real ProcessDefinition-driven turn
    rotation — that gap is inherited here, not introduced by D1.5; nothing about it is
    specific to Ollama vs. OpenAI as providers (`ModelProfile.provider` is a plain
    string, `LiteLLMModelProvider` handles both identically once credentials are wired
    into the runtime, a separate, later composition-root task per the same boundary
    every C1.x task and D1.3 already flagged).
- Key entry → masked forever after; changing provider params takes effect next turn.
  → `test_create_model_profile_never_returns_the_api_key` asserts the literal key string
    never appears in the create response, the get response, or the list response --
    only `credential_ref` (opaque id) is ever returned; there is no route anywhere that
    reads a stored credential back out at all, which is a stronger guarantee than
    "masked" (nothing to unmask). "Changing params takes effect next turn": `params` is
    read fresh from `ModelProfile.params` by `run_agent_turn`/`generate_agent_response`
    on every call (no caching layer sits between the DB row and the provider request),
    so an `update_model_profile` write is visible to the very next turn by construction
    -- proven indirectly via `test_update_model_profile_params_without_supplying_a_key_again`,
    which shows a `PATCH` immediately reflects the new `params` in a subsequent `GET`.

## Design decisions
- **Neither `Agent.persona_md` nor `Agent.entity_id` existed before this task**, despite
  being named in the plan's own §12.4 schema -- B1.7 only added `agent_role` (its own
  concern; see that module's docstring). Added both as real, migrated columns
  (`f2e8a1c6d4b9`) rather than working around their absence in the UI. `entity_id` has no
  FK (there is no `entity`/`entity_schema` table anywhere in Phase 1, a gap B1.3/B1.4
  already found and documented) -- same no-FK-yet shape as
  `ResolutionRecordRow.actor_entity_id`. The "dropdown of workspace entities" subtask is
  therefore a plain text/UUID input with an honest inline note instead of a dropdown with
  nothing to list, ready for F3.6 (Phase 3) to give it real data.
- **A minimal, real credential store, not a fake one.** `model_profile.credential_ref`
  needed something to actually point at -- added `provider_credential` (tenant-scoped,
  RLS+FORCE, standard mutable table) plus `core.agents.authoring.store_provider_credential`,
  which encrypts through the already-existing `Encryptor` port (v1: `IdentityEncryptor`,
  H5.7 swaps in real KMS/BYOK later) before storing. No route anywhere reads a credential
  back out -- "the UI never redisplays a key" is enforced by *absence of a read path*,
  not by client-side masking of a value the server did send. Needed a composition-root
  factory for the port at the API layer for the first time --
  `api/encryptor_factory.py`, mirroring `model_provider_factory.py`/
  `permission_service_factory.py`'s identical pattern.
- **Full agent/model-profile CRUD didn't exist at all before this task** --
  `core.agents.seed`'s own docstring said as much ("that's D1.5, Phase 1"). Added
  `core/agents/authoring.py` (create/update/get/list for both `Agent` and
  `ModelProfile`) and `api/routes/agents.py` (`/agents`, `/model-profiles`,
  `/model-profiles/capabilities`). `update_agent`'s `entity_id` uses a sentinel
  (`...`) default distinguishing "field omitted" from "field explicitly set to null"
  (unlinking an entity is a real, intentional action, not the same as leaving it alone)
  -- the route reads this off Pydantic's `model_fields_set`, proven by
  `test_update_agent_can_explicitly_unlink_entity`.
- **A second, unrelated `AgentResponse` already existed** (`api/routes/workspaces.py`'s
  minimal `GET /workspaces/{id}/agents`, used by `WorkspaceDetailPage`'s session-creation
  picker). Left it alone rather than consolidating -- it serves a different, narrower
  purpose (id/key/name only, for starting a session) than this task's fuller CRUD
  listing, and nothing broke by both existing (FastAPI/`openapi-typescript` namespace
  the two generated types by module path automatically). `WorkspaceDetailPage` now also
  links to the new `/workspaces/:id/agents` management page.
- **No `provider_credential` raw-DDL index gap added.** Declared `Index(...)` directly in
  `ProviderCredentialRow.__table_args__` (not just in the migration's raw DDL) so
  `alembic check` doesn't grow a 4th instance of the one known pre-existing gap
  (`ix_message_session_seq`/`ix_session_event_session_seq`/`ix_usage_record_session`) --
  caught and fixed during this task's own verification pass, not left as a new debt.
- **No interactive browser click-through was possible in this sandbox** (same limitation
  as D1.1-D1.4 -- no browser automation tool available). Verified instead: `tsc -b
  --noEmit` and `eslint .` both clean; every new component
  (`ModelProfilesPanel.tsx`/`AgentEditor.tsx`/`AgentManagementPage.tsx`, plus the
  modified `WorkspaceDetailPage.tsx`) fetched directly from the Vite dev server returns
  200 with no syntax/transform error; and every API contract the UI calls is fully
  exercised by the backend's own `TestClient`-based tests, including the
  never-redisplays-a-key guarantee. Flagged honestly rather than assumed working.
