# A1.7 — Reranker

**Phase:** 1 · **Track:** A · **Est:** 3d · **Status:** done
**Depends on:** A1.6 · **Blocks:** C1.2
**Plan refs:** §6.3 steps 4–5, §13.3

## Goal
Class-blind cross-encoder rerank within each class bucket, in-process (no API call).

## Subtasks
- [x] `bge-reranker-v2-m3` loaded in the API/worker process (lazy, singleton); top-32 → 16
      per class.
- [x] **Fuse-before-rerank order** preserved (WRRF first, then rerank — the empirically
      better cascade; do not "optimise" the order).
- [x] **Class-blind by design:** the reranker never sees or conditions on class — class
      policy lives in bucket allocation where it's auditable (D2 rationale).
- [x] Latency budget: ~50–100ms for 32 candidates on CPU; measure and record in the OTel span.
- [x] Config to disable reranking (degraded mode for tiny deployments) — ranking falls back
      to WRRF order.
- [x] Stub-model injection point for fast CI (real model exercised in a nightly job).

## Acceptance criteria
- [x] Rerank changes within-bucket order only; bucket membership and budgets untouched
  (test). `test_reranking_does_not_change_bucket_token_allocation`: runs the same corpus
  with and without a reranker, asserts the per-class token split is identical (computed
  purely from ratios/max_tokens, independent of reranking) and every included chunk's
  class matches what it was seeded with in both runs.
  `test_reranking_changes_within_bucket_order`: two rules chunks tied on dense score (same
  embedding) — only the reranker's text-based scoring can promote the lexically-relevant
  one to rank 1, proving reranking actually does something.
- [x] Runs fully offline (full-local deployment mode). The real adapter
  (`CrossEncoderReranker`) lazy-loads `sentence_transformers.CrossEncoder` only on first
  `.rerank()` call — same lazy-import pattern as A1.3's embedding adapter, so constructing
  it never requires model weights already present, and nothing in this task's own test
  suite needs network access (the stub adapter is used throughout).
- [x] OTel span with candidate count + latency present per call.
  `rerank_bucket` wraps its work in `_tracer.start_as_current_span("rerank.rerank_bucket")`
  and sets `pyrrhula.rerank.candidate_count`/`pyrrhula.rerank.latency_ms` — same
  `core.observability.otel.get_tracer` pattern already used in `core.process.skeleton`.

## Design decisions

- **The class-blind guarantee is structural, not a policy choice that could be
  violated.** `core.ports.reranker.Reranker.rerank(query, candidates)` has no `class_`
  parameter at all — an adapter has nothing to condition on even if it wanted to.
- **Reranking is wired into `assemble.search_and_budget` as `reranker: Reranker |
  None = None`**, inserted between WRRF fusion and bucket fill (extending A1.6's
  orchestration in place, not adding a parallel pipeline). `reranker=None` is the
  degraded-mode fallback: WRRF order stands, *unbounded* by the reranker's top-32-in/
  16-out cap — that cap exists specifically to keep reranking cheap, and doesn't apply
  when there's no reranking to bound.
- **`FusedHit` is reused as the rerank output type** rather than introducing a parallel
  `RerankedHit` — `rerank_bucket` returns the same shape with `.rank`/`.wrrf_score`
  updated to the post-rerank order/score and `"reranked"` appended to
  `.contributing_lists` (so the eventual manifest's `why` column reflects it happened).
  This means `budget.py`'s fill functions need zero changes to consume reranked input —
  they were always agnostic to how a `FusedHit` list got ordered.
- **`api/reranker_factory.py` and `worker/reranker_factory.py`** (composition roots,
  mirroring A1.3's embedding-provider factories) exist even though nothing calls
  `get_reranker()` yet — no route or job wires up `search_and_budget` with reranking
  enabled, since that's C1.2's job. Built now so C1.2 has a ready seam, same as A1.3's
  embedding factory existed before anything but A1.2's chained job used it.
