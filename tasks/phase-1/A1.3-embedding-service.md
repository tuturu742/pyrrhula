# A1.3 — Embedding service

**Phase:** 1 · **Track:** A · **Est:** 3d · **Status:** done
**Depends on:** A1.2 · **Blocks:** A1.4
**Plan refs:** §13.3, §13.9

## Goal
Self-hosted embeddings in the worker (full-local mode is a supported deployment; embedding
through a paid API must never be required).

## Subtasks
- [x] `bge-m3` (1024-dim) loaded in the worker process; batched embedding job consuming the
      ingestion queue; GPU optional, CPU workable.
- [x] Dimension pinned in config **and recorded on every chunk row**; mismatch at query time
      is a hard error, not a silent zero-recall bug.
- [x] API-provider adapter (OpenAI/Voyage) behind the same port for tenants who opt in —
      subject to the D14 egress policy (`purpose='embed'`).
- [x] **Re-embed job written now** (not Phase 4): iterate chunks where
      `embedding_model != current`, re-embed, swap atomically per source version.
- [x] Embedding cache keyed by `content_hash` so version publishes reuse vectors (with A1.2).

## Acceptance criteria
- [x] End-to-end: uploaded md file → searchable vectors, no external API involved. Verified
  through the real containerized worker (not simulated): upload → chained `knowledge_ingest`
  → `embed_chunks` job → `knowledge_chunk.embedding` populated, `vector_dims() == 1024`,
  `embedding_model` recorded — zero external API calls (self-hosted embedding path).
- [x] Re-embed job migrates a seeded corpus to a new model tag and search still works (test
  with a stub model to keep CI fast — see note below on why the stub is 1024-dim here, not
  literally 8). `test_reembed_picks_up_chunks_under_a_different_model_tag` and
  `POST /knowledge/reembed` verified live.
- [x] Egress: `purpose='embed'` blocked to cloud when tenant policy says local-only.
  `test_embed_chunks_respects_tenant_egress_policy_blocking_cloud` seeds a real tenant's
  `settings.egress_policy` and proves the block happens before any network call.

## Design decisions

- **New `EmbeddingProvider` port** (`core/ports/embedding.py`), separate from
  `ModelProvider`: embedding models are a different shape (`list[str] -> list[vector]`,
  no streaming, no tool loop) and a different library stack entirely. `provider_kind()`
  (`core/ports/model_provider.py`) is generalised to also treat a `local/` prefix as
  local (alongside generation's `ollama/`), so both purposes share one egress classifier
  and one `check_egress()` — D14's point (`usage_record`/egress share one `purpose`
  taxonomy) extends naturally to embedding.
- **Three adapters** behind the port: `adapters/embedding/local/` (real —
  `sentence-transformers` + `BAAI/bge-m3`, lazy-imported so constructing/testing the
  adapter never requires the ~2GB of weights already be present), `adapters/embedding/
  stub/` (deterministic hash-based, no model/network — the "stub model to keep CI fast"
  this task's own acceptance criteria call for), `adapters/embedding/cloud/` (LiteLLM,
  OpenAI/Voyage/etc, egress-gated).
- **The "8-dim stub" note re-scoped.** `knowledge_chunk.embedding` is a fixed
  `vector(1024)` column (A1.1) — pgvector's `vector(N)` type is a hard per-row dimension
  constraint, not just documentation, so an 8-dim vector literally cannot be written
  through it. Tests that write through the real table construct
  `StubEmbeddingProvider(dimension=1024)`; the stub adapter's own default (8) is only
  exercised in its isolated unit tests, which never touch that column. (The "8-dim stub
  model" the task file originally described maps to `vector_store_item`, T0.3's
  small placeholder table — not the real production-shaped chunk table this task
  actually writes to.)
- **Chained jobs, not inline embedding.** `worker.ingestion.run_ingestion_job` enqueues
  `"embed_chunks"` (scoped to the source it just processed) after a successful ingest —
  inside the `@idempotent`-wrapped function, so a cache-hit replay never double-enqueues.
  `"reembed_stale"` is a separate, tenant-wide sweep (`knowledge_source_id=None`),
  triggered via `POST /knowledge/reembed` (an operator action, e.g. after changing
  `Settings.embedding_model`), not chained automatically.
- **Content-hash cache covers same-run duplicates, not just prior rows.** Two pending
  chunks that happen to share identical text (duplicate boilerplate, or two entries with
  byte-identical bodies) are grouped by `content_hash` *before* calling the provider, so
  they cost one inference between them, not one each — caught by
  `test_identical_content_hash_reuses_cached_embedding_not_recomputed` initially failing
  (2 embedded instead of 1) until the dedup-by-hash grouping was added; a naive per-row
  "check DB cache, else embed" loop only catches reuse against *already-written* rows,
  missing duplicates within the same batch.
- **`torch` pinned to the CPU-only build.** "GPU optional, CPU workable" (plan §13.9)
  means the default self-host image must not carry ~1.5GB of CUDA/nvidia wheels it
  doesn't need. `pyproject.toml` lists `torch` as a direct dependency (not just pulled in
  transitively by `sentence-transformers`) with `[tool.uv.sources]` routing it to the
  `pytorch-cpu` explicit index, and `[tool.uv] environments` is restricted to Linux (the
  only real deployment target — Docker) so the lock doesn't need a macOS/Windows wheel
  that would defeat the override. GPU users can override at deployment time; that's a
  separate concern from what ships by default.

## Bugs found and fixed along the way
- **`[tool.uv.sources]` silently didn't apply** to `torch` while it was only a
  *transitive* dependency (via `sentence-transformers`) — `uv lock` kept resolving the
  full CUDA wheel from PyPI regardless of the configured override. Fixed by listing
  `torch` as a direct project dependency too, which made uv actually honour the source
  routing. Also needed `[tool.uv] environments = ["sys_platform == 'linux'"]`: a
  cross-platform (mac/Windows/Linux) universal lock was part of why the resolver
  preferred a plain PyPI wheel over the Linux-only CPU index.
- **The dedup-by-hash gap** described above (initially only checked the DB, not
  same-run duplicates) — caught by its own test before this task was considered done,
  not discovered later.
- No new tiktoken/network-at-runtime surprises this time (A1.2 already fixed that class
  of bug for the worker container generally) — but this task's Docker build step doing a
  91s `sentence-transformers`/`torch` install (CPU-only, ~185MB torch download) was worth
  confirming actually completes in a normal build rather than assumed.
