# C1.5 — RuleSystem + validator

**Phase:** 1 · **Track:** C · **Est:** 4d · **Status:** done
**Depends on:** T0.3 · **Blocks:** C1.6, F3.7
**Plan refs:** §9.3

## Goal
The `RuleSystem` object that defines which mechanical expressions are legal and how
modifiers derive from entity state — so the engine, not the model, computes the "+5".

## Subtasks
- [x] `RuleSystem` model (pack content, tenant-scoped storage): `key`, `dice_grammar`,
      `check_types`, `outcome_bands`, `modifier_resolver` (CEL over entity fields),
      `validators` (CEL predicates).
- [x] Expression grammar + parser for dice notation (`1d20+5`, `2d6+STR`, advantage/keep
      syntax minimal for MVP); grammar rules come from the RuleSystem, not hardcoded —
      a coin-flip system must be expressible.
- [x] `modifier_resolver` evaluation: CEL over the actor entity's fields, e.g.
      `(fields.strength - 10) / 2` — returns the authoritative modifier.
- [x] Validation API: `validate(expression, check_type, actor_entity, phase) → ok | typed
      error` (illegal expression / wrong modifier / check not legal in phase).
- [x] Outcome banding: map totals to outcomes (`>= target: success`; PbtA-style bands
      expressible declaratively).
- [x] MVP fixture rule system: a minimal d20-like system (core-neutral naming) used by the
      Phase-1 exit slice; full `dnd5e_srd`/`pbta`/`coin_flip` land with F3.7.

## Acceptance criteria
- `1d20+5` claimed by a model for an entity whose derived modifier is +3 → rejected with a
  structured error naming the correct modifier (the anti-hallucination property, §9.2 step 2).
  → `test_claimed_modifier_mismatching_the_actors_actual_modifier_is_rejected`
- The same validator code path accepts a d20 system and a coin-flip system fixture (no core
  branching on system kind).
  → `test_same_validate_function_handles_d20_and_coin_flip_with_no_branching`
- Grammar fuzz: invalid expressions never crash, always produce typed errors.
  → `test_fuzz_never_raises_anything_but_grammar_error` (hypothesis, arbitrary text input),
    `test_garbage_expression_never_crashes_always_typed_error`

## Design decisions
- **`actor_fields: dict[str, object]` is caller-supplied, not read from a live Entity
  table.** No Entity system exists anywhere in Phase 1 (F3.6 is Phase 3) -- this is the
  same injection-seam pattern C1.2 already established for entity state. `validate()`'s
  anti-hallucination property (comparing a claimed modifier against a *computed* one)
  works identically regardless of where `actor_fields` ultimately comes from; F3.6
  replaces the source, not `validate()`'s shape.
- **Grammar is generic (`NdM[kK][+-]MOD...`), not d20-specific**, so "a coin-flip system
  must be expressible" falls out for free -- a coin flip is just `1d2`. Which
  sides/counts/keep-syntax are actually *legal* is a per-`RuleSystem` `dice_grammar`
  policy checked by `validate()`, not a grammar-level distinction.
- **`rule_system` is a mutable, upserted-by-`(tenant_id, key)` table**, not an immutable
  version history like `process_definition` (B1.1) -- matches `knowledge_source`'s shape
  instead. Nothing in this task's acceptance criteria needs pinned rule-system versions;
  if that need surfaces later (mirroring A1.8), it's additive, not a redesign.
- **Authoring-time CEL validation (`validate_definition`) only checks that
  `modifier_resolver`/`validators` expressions *parse***, not that they evaluate safely --
  unlike B1.1's `compile_check` (which builds a dummy activation from the DSL's own
  *declared* `state:` types), `actor_fields` has no fixed declared schema across rule
  systems (a d20 system and a PbtA system use entirely different field names). A
  documented, real limitation, not a silent gap; the interpreter-style backstop is
  `validate()`'s own `modifier_resolution_failed` error at evaluation time.
- **A symbolic modifier term (`2d6+STR`) has nothing literal to cross-check against** --
  the computed modifier is still returned and still authoritative, it just isn't compared
  against a claim. Only a *literal* numeric term in the expression (`1d20+5`) is
  something the model could have hallucinated, so that's the only case
  `modifier_mismatch` can fire on.
- **Custom `validators` (CEL predicates) run last**, after the modifier-mismatch check --
  an expression with a wrong claimed modifier is rejected on that basis before a rule
  system's own extra predicates ever run, avoiding a confusing "which one is my real
  problem" double-signal.
