# A1.9 — Retrieval cache

**Phase:** 1 · **Track:** A · **Est:** 2d · **Status:** done
**Depends on:** A1.6 · **Blocks:** —
**Plan refs:** §6.3 cost note, §16.1

## Goal
Redis cache over the per-class retrieval cascade — within a scene the same content re-queries
for many turns, so hit rates should be high.

## Subtasks
- [x] Cache key: `(query_hash, scope_set, class, version_set)` — **scope set is part of the
      key**; a cache that ignores scopes is a leak. Version set makes publishes
      self-invalidating.
- [x] Cache the post-WRRF, pre-rerank candidate list per class (reranking is query-specific
      and cheap enough to redo; candidates are the expensive part).
- [x] TTL + explicit invalidation on attachment changes (pin change, enable/disable, scope
      change).
- [x] Hit/miss metrics exported (feeds the Q7 cost telemetry). Scoped to what this codebase
      actually has today — see design notes.

## Acceptance criteria
- [x] Two principals with different scope sets never share a cache entry (test).
  `test_different_scope_sets_never_return_each_others_cached_hits` (unit, `cache.py` only)
  and `test_different_scope_keys_never_share_a_cached_result` (integration, through
  `search_and_budget`: a `gm_only`-scoped caller populates the cache, a `workspace_public`
  -only caller gets a real miss and correctly finds nothing, never the gm-only chunk).
- [x] Publishing a new source version changes the key and misses (no stale reads).
  `test_publishing_a_new_version_changes_the_key_and_misses` (unit) and
  `test_different_version_sets_produce_independent_cache_entries` (integration, through
  `search_and_budget`'s new `version_set` parameter).
- [x] Measured hit rate on a scripted 20-turn scene > 50% (informational baseline).
  Ran a 6-distinct-query, 20-turn scripted scene (a handful of repeated player intents,
  matching how real play loops within a scene) against a live Redis + Postgres: **85% hit
  rate** (17 hits / 3 misses — one miss per distinct query, then cached for every repeat).

## Design decisions

- **What's cached is the fully-fused (dense+sparse+keyed) per-class candidate list, not
  just dense+sparse.** The alternative — caching only dense+sparse and re-fusing fresh
  keyed/activation hits on every call — would keep the keyed contribution always current,
  but WRRF's `fuse()` combines all three lists' raw ranks in one pass; splitting that
  into "cached partial fuse + fresh partial fuse, merged" would need a new partial-fusion
  primitive for a benefit this task doesn't need yet. The trade-off this creates: a cache
  hit can serve a slightly stale activation state (sticky/cooldown windows) for up to the
  cache's TTL (5 minutes). Documented in `assemble.py`'s docstring as a deliberate,
  bounded staleness window, not a hidden gap — activation state is itself usually stable
  turn-to-turn within a scene, which is exactly the assumption the whole cache rests on.
- **`version_set` is a parameter the caller resolves, not something `cache.py` or
  `assemble.py` compute themselves.** Neither module has (or should have) access to
  `workspace_knowledge_attachment` — that's A1.8's `resolve_effective_version_id`, one
  layer up, in whatever composes a `ContextAssembler` call (C1.2, not yet built). Until
  then, `search_and_budget(version_set=...)` defaults to `None` (empty), which is
  correct-but-non-invalidating on publish for any caller that doesn't pass it — flagged,
  not silently assumed solved, same pattern as A1.8's own workspace-granularity scoping
  note.
- **Hit/miss metrics are in-process counters (`RetrievalCache.hits`/`.misses`/
  `.hit_rate`) plus an OTel tracing span attribute per `get()` call
  (`pyrrhula.retrieval_cache.hit`), not an OTel *metrics* pipeline.** No metrics
  exporter exists anywhere in this codebase yet (only tracing spans, e.g. A1.7's
  reranker) — matching that existing pattern rather than inventing a one-off metrics
  pipeline for this task alone. A real Q7 cost-telemetry dashboard would read these
  counters via whatever aggregation layer eventually wraps `ContextAssembler` calls;
  that layer doesn't exist yet either.
- **`invalidate_tenant` is tenant-wide, not scoped to the one changed attachment.**
  Attachment changes that don't publish a new version (enable/disable, `scope_key`
  change, re-pinning to an *already-existing* version) don't change any version id, so
  they can't self-invalidate via the key the way a publish does. A precise
  per-attachment invalidation would need to know which cache entries that specific
  attachment's chunks ever contributed to — not tracked, and not worth tracking for a
  cache whose entries expire in 5 minutes regardless. Over-invalidating (the whole
  tenant) costs some otherwise-still-valid cache entries; under-invalidating is
  leak-adjacent. Chose correctness over precision, consistent with every other
  cache/visibility trade-off in this codebase so far.
