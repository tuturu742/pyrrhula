# A1.10 — Library tenant (D13)

**Phase:** 1 · **Track:** A · **Est:** 2d · **Status:** done
**Depends on:** A1.1, T0.4 · **Blocks:** F3.7 (seed content), Phase 3 provisioning
**Plan refs:** D13, §16.8

## Goal
A well-known, read-only library tenant holding pack seed content (embedded once, not once
per tenant), readable via exactly one named exception in the knowledge RLS policy.

## Subtasks
- [x] Reserved library tenant with a well-known UUID, created by migration; no memberships;
      flagged `is_library` (or equivalent) so it can never be logged into.
- [x] Knowledge-table RLS policies (source/version/entry/chunk) gain **one named disjunct**:
      `tenant_id = current_setting('app.tenant_id')::uuid OR tenant_id = '<library-uuid>'`.
      Read-only: no write policy for foreign tenants under any condition.
- [x] Workspace attachment of a library source works like any attachment (pin, scope,
      priority) — the attachment row lives in the *consuming* tenant. Required zero code
      changes: `attach_source_to_workspace`/`resolve_effective_version_id` (A1.8) already
      read the source through a tenant-scoped session, which the new RLS disjunct now
      lets see a library-owned source — see design notes.
- [x] **Fork-on-edit:** attempting to edit a library source forks it into the acting tenant
      (reuses A1.8 fork); UI affordance comes later, API behavior now.
- [x] Provisioning path: seeding a pack embeds its content into the library tenant once;
      tenant provisioning attaches, never copies.
- [x] **Extend T0.4's matrix** (required, same PR): parameterise {tenant A, tenant B,
      library} and assert B reads library ∧ B cannot read A ∧ nobody writes library.

## Design decisions

- **The RLS change is one `ALTER POLICY` per table widening only `USING`, `WITH CHECK` is
  byte-identical to before.** This is what makes "read-only" true without a second policy:
  Postgres evaluates `WITH CHECK` on the *proposed new row* for every INSERT/UPDATE
  regardless of what `USING` allowed the caller to see, so a foreign tenant's write to a
  library-owned row still fails (`InsufficientPrivilegeError`, confirmed live) even though
  that same tenant's `USING` clause now makes the row visible for read. Two separate
  policies (one broad read-only `SELECT` policy, one narrow read-write policy) would work
  too, but would double the surface a reviewer has to convince themselves is consistent
  for no behavioral gain.
- **`fork_if_library` needed zero changes to A1.8's `fork_source`.** `fork_source` already
  does everything through a tenant-scoped session (`session.get(KnowledgeSource,
  from_source_id)`, entry copies, a `publish_version` whose `parent_version_id` can cross
  source boundaries) — none of that cared whose tenant the origin belonged to, it only
  ever checked "is this row visible to my scoped session," which the new disjunct now
  answers yes for a library source. The *only* new code is `library.py`'s `fork_if_library`
  wrapper: detect "is this a library source," find-or-reuse an existing fork (via A1.8's
  own `parent_version_id` provenance chain — no new column needed), and fall through to
  `fork_source` on a miss.
- **Existing-fork detection walks `parent_version_id` provenance rather than adding a
  `forked_from_source_id` column.** A source has no "I am a fork of X" pointer of its own
  in this schema — only its *versions* do (A1.8), set once at the fork's first publish.
  Querying `knowledge_source_version` for a row owned by the caller's tenant whose
  `parent_version_id` is any version of the library source answers "have I already forked
  this" without a schema change. Real cost: this makes a repeat edit's first call one
  extra query slower than a bespoke pointer would; not worth a column for.
- **A real, non-obvious test interaction found while running the full suite twice: the
  library disjunct means *any* tenant's unfiltered scan of the four covered tables now
  legitimately includes the library's rows, not just its own.** Two pre-existing things
  broke because of this, both fixed in this PR:
  1. `tests/isolation/test_knowledge_filter_omission.py`'s three source/version/entry
     tests asserted strict `{row[0] for row in rows} == {tenant_a}` — provably false now,
     by design, the moment any library content exists in the same database (which my own
     new tests' fixtures immediately do, permanently, since a published version's draft
     row is deliberately never deleted — see `authoring.publish_version`'s docstring).
     Fixed to assert the still-load-bearing half (`tenant_b` never appears) plus `<=
     {tenant_a, LIBRARY_TENANT_ID}` instead of strict equality — this *is* "extend T0.4's
     matrix," just distributed across the existing file rather than only the new one.
  2. `packages/core/knowledge/ingestion/tests/test_pipeline.py`'s shrinking-document test
     read `SELECT id FROM knowledge_entry WHERE version_id IS NULL` with no
     `knowledge_source_id` filter, silently relying on "the only draft row visible in my
     tenant scope" being unique — true before A1.10 by accident (nothing else in that
     tenant's own scope could produce a second draft row), false after, the instant any
     other draft-holding library source exists in the same live database. Fixed by adding
     the `knowledge_source_id` filter it always should have had; this was latent
     fragility A1.10 exposed, not something A1.10 broke.
  Neither fix weakens any isolation guarantee — both make an assumption that was always
  either false-by-luck or genuinely narrower than intended into one that's actually true.
- **Retrieval (`search_dense`/`search_sparse`) still filters by exactly one `tenant_id` —
  an attached library source's chunks do not yet appear in actual retrieval results.**
  This is a deliberate scope boundary, not an oversight: A1.10's own file list is the
  RLS/authoring/fork layer, not retrieval plumbing, and surfacing attached library content
  in `search_and_budget` needs to know *which* tenant_ids are relevant to a given
  workspace (own tenant + whatever library sources are attached) — that's C1.2's
  (`ContextAssembler`) job, the layer that resolves attachments before calling search, not
  something to bolt onto A1.4/A1.6's already-tested single-tenant-id query contract here.
  Flagged so C1.2 doesn't silently inherit a gap it needs to know about.
