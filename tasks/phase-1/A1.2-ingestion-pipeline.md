# A1.2 — Ingestion pipeline

**Phase:** 1 · **Track:** A · **Est:** 6d · **Status:** done
**Depends on:** A1.1 · **Blocks:** A1.3
**Plan refs:** §6.1, §15.4

## Goal
Turn uploaded documents into entries and retrieval-ready chunks, as a worker job.

## Subtasks
- [x] Parsers: Markdown, plain text, PDF (text extraction; scanned PDFs out of scope —
      reject with a clear message).
- [x] Entry splitting: heading-based for md, heuristic for txt/pdf; author can re-split in
      the UI later (D1.1) — keep split points editable data.
- [x] Chunking: semantic-ish splitter targeting ~400 tokens with overlap; chunk ordinal +
      token_count recorded; tokenizer via `ModelProvider.count_tokens` parity rules.
- [x] Job flow: upload → `BlobStore` → ingestion job (parse/split/chunk) → embedding job
      (A1.3) → chunk upsert; job states surfaced via API for UI progress.
- [x] **Content-hash skip:** unchanged entries (same `content_hash`) keep their chunks and
      vectors across re-ingestion/version publish.
- [x] Idempotent jobs (`@idempotent` from T0.7) — re-running an ingestion job is safe.

## Acceptance criteria
- [x] Ingesting the same file twice produces zero new chunks (hash skip proven). Verified
  in `core/knowledge/ingestion/tests/test_pipeline.py` and, separately, end-to-end through
  the real containerized worker: re-uploading an identical file produced
  `{"chunks_created": 0, "chunks_unchanged": 2}`.
- [x] A 200-page PDF ingests without blocking the API process (worker-side, streamed).
  Structural, not simulated: `POST /knowledge/sources/{id}/ingest` only writes a blob and
  enqueues a job (no parsing/chunking in that process at all), verified to complete in
  ~15ms regardless of upload size (`test_upload_enqueues_job_and_worker_processes_it`).
  Parsing/chunking/upserting all happen in the worker process, claimed off the job queue.
- [x] Chunks carry correct denormalised `class`/`scope_key` from their entry (spot-check
  test): `test_chunks_carry_denormalised_class_and_scope_key`.

## Design decisions

- **Ingestion never calls `publish_version`.** It creates/updates *draft* entries only
  (`version_id IS NULL`) and chunks them there. Reasoning: `publish_version` (A1.1) copies
  draft entries into brand-new rows (new `entry_id`) on every publish, even when content is
  unchanged — chunking against that copy would mean every republish looks like a brand-new
  entry to the hash-skip logic (different `entry_id`, same `ordinal` never previously seen),
  producing fresh chunk rows on every publish and making "ingesting the same file twice
  produces zero new chunks" impossible to satisfy. Chunking against the stable draft entry
  (same id across re-ingestion runs, since `upsert_draft_entry` updates in place) is what
  makes the acceptance criterion achievable. Publishing is a still a separate, explicit
  authoring action — how a published version's retrieval resolves to a specific chunk set is
  A1.4/A1.8's problem, not ingestion's.
- **`knowledge_chunk.version_id` is now nullable** (migration `3f7c2b8d5e91`, on top of
  A1.1's `8a1f2c9e4b6d`) for the same reason — chunks attach to draft entries during
  ingestion, which have no version yet.
- **Content-hash skip is chunk-level, not entry-level.** No new `knowledge_entry.content_hash`
  column was needed: re-deriving identical text from unchanged `body_md` naturally
  reproduces the same per-chunk `sha256`, so the upsert against `(entry_id, ordinal)`
  is a no-op by construction, not a special case requiring its own hash column.
- **Chunker**: paragraph-aware packing to ~400 tokens (configurable) with an overlap tail
  carried into the next chunk; a single paragraph that alone exceeds the target falls back
  to word-count slicing (unbounded chunk size would defeat chunking's purpose). Token
  counting is injected (`CountTokens` callable) — `core` never imports the tokenizer
  directly; the worker composition root supplies `LiteLLMModelProvider.count_tokens`.
- **BlobStore/JobQueue composition roots**: `api.blob_store_factory` /
  `api.job_queue_factory` / `worker.blob_store_factory` /
  `worker.model_provider_factory` — one small factory file per port per process,
  mirroring the existing `api.model_provider_factory` pattern (T0.8). Api and worker each
  get their own singleton (two processes in production) rather than sharing module state.
- **`JobQueue` port gained a `get(job_id)` method** (with `Job` gaining `status`/`result`/
  `error` fields) — needed for "job states surfaced via API for UI progress." The `job`
  table has no RLS by design (cross-tenant, `core.ports.job_queue`), so
  `GET /knowledge/jobs/{id}` does its own manual tenant check rather than relying on RLS.

## Bugs found and fixed along the way
- **`packages/worker/main.py` was still T0.3's idle stub** — its own docstring said
  "T0.3 replaces this with JobQueue.poll()," but that never actually landed; the worker
  process did nothing but sleep. This is the first task that needs a real out-of-process
  job to run, so this task implements the real dispatch loop (claim → dispatch by `kind`
  from a handler registry → complete/fail) that finishes what T0.3 promised.
- **tiktoken tries to download its encoding from the internet on first use** —
  `LiteLLMModelProvider.count_tokens`'s fallback (`tiktoken.get_encoding("cl100k_base")`,
  used for any non-OpenAI model) silently requires network access the first time it runs.
  Invisible in every prior task because nothing had exercised that fallback path yet; found
  by running the real containerized worker (no network) end-to-end, where the job failed
  with a DNS resolution error. This would have equally broken T0.8's usage-metering token
  counts for Ollama/echo models in an offline deployment — full-local is a supported
  deployment mode (plan §13.9), not just for the model calls within it. Fixed by
  pre-fetching the encoding at Docker build time (`docker/Dockerfile`, where network access
  is available) into a baked-in `TIKTOKEN_CACHE_DIR`, so the actually-offline runtime
  container never needs to reach the network.
- **BlobStore volume permissions**: a named volume mount lands root-owned on first use
  unless the image's existing directory (copied in as the volume's initial content) already
  has the right ownership. Fixed by pre-creating `/app/data/blobs` before the Dockerfile's
  existing `chown -R pyrrhula:pyrrhula /app` step.
- **Cross-test pollution via the unscoped `job` table**: `test_job_status_endpoint_requires_
  matching_tenant` enqueued a real `"knowledge_ingest"`-kind job it never claimed/completed;
  since `job` has no RLS and this run's test DB persists across test files,
  `claim_one(kinds=["knowledge_ingest"])` in a different test picked up that stale pending
  row (oldest-first) instead of the job the test had actually just created. Fixed by giving
  that test a harmless placeholder kind (`"test_probe"`) instead of colliding with the real
  dispatch kind — it only exercises the tenant-mismatch check, not real ingestion.
