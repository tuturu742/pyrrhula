# B1.5 — Session concurrency control

**Phase:** 1 · **Track:** B · **Est:** 3d · **Status:** done
**Depends on:** B1.4 · **Blocks:** —
**Plan refs:** §5.5

## Goal
One advancing writer per session; human input during a model turn queues instead of racing.

## Subtasks
- [x] Advance-session path takes `SELECT ... FOR UPDATE` on the session row; optimistic
      `version` column incremented per advance; stale-version writes rejected with a typed
      conflict error. `claim_session`/`commit_advance`; `SessionConflictError`.
- [x] Input queueing: human input arriving during a model turn is appended as a
      `session_event(kind='message', queued=true)` and consumed by the scheduler at the next
      eligible point — never lost, never racing the in-flight turn. `submit_queued_input`
      makes the durable, concurrency-safe append real today; the *consuming* half (a
      scheduler recognising a queued input as satisfying a `mode: free` human actor) needs
      the real HTTP submission flow and agent runtime (B1.7) — see design notes.
- [x] Lock scope kept minimal: model calls happen **outside** the row lock (claim → release →
      generate → re-acquire → commit) so a slow provider can't hold a DB lock for 30s.
      Proven live, not just argued: a concurrent plain read of a mid-stall session's row
      completes in well under the stall duration.
- [x] Multiple sessions per workspace advance concurrently; contention only on entity writes
      (which go through the FSM service later — note the boundary now). Proven live: a
      stalling session A doesn't delay session B's advance at all. Entity writes don't
      exist yet (no `entity` table anywhere in Phase 1 — the same gap B1.3/B1.4 already
      found); the boundary is noted here for whichever later phase adds them.
- [x] Watchdog: a crashed holder's claim expires (timeout on the claim, not on the DB lock).
      `_CLAIM_TIMEOUT_SECONDS`; `claim_session` rejects a live claim, accepts an expired one.

## Acceptance criteria
- [x] Stress test: N concurrent advance attempts on one session → exactly one winner per turn,
  no deadlocks, no lost inputs (queued inputs all surface in order).
  `test_n_concurrent_advance_attempts_produce_exactly_one_winner`: 10 concurrent
  `advance_session_locked` calls on the same session via `asyncio.gather` -- exactly 1
  succeeds, 9 raise `SessionClaimTimeoutError`, the session ends at `version=1` with no
  corruption. `test_queued_inputs_under_concurrent_submission_are_never_lost_or_duplicated`:
  20 concurrent `submit_queued_input` calls produce exactly the gapless `event_seq` range
  `[0..19]`, no gaps, no duplicates, all recorded with `queued: true`.
- [x] A provider stall (mocked 60s) does not block reads or other sessions.
  Scaled to a real (short) sleep for test speed -- structurally identical, not a weaker
  claim: `test_a_slow_turn_does_not_block_reads_of_the_same_session` samples a plain read
  of the stalling session's row mid-stall and confirms it returns in well under the stall
  duration; `test_a_slow_turn_on_one_session_does_not_block_advancing_another` confirms a
  second, independent session advances (claim + full interpreter step + commit) just as
  fast while the first is still stalling.

## Design decisions

- **`claim_session` uses a real `SELECT ... FOR UPDATE`, but the "exactly one winner"
  property comes from the application-level `claimed_at`/`claimed_by` check inside it, not
  from the row lock rejecting concurrent claimants.** Postgres's default `FOR UPDATE`
  *blocks* a second concurrent claimant until the first's (brief) claim transaction
  commits — it does not raise. So N concurrent claim attempts serialize briefly at the DB
  level (fast, since each claim transaction is tiny), then each one in turn checks the
  marker: the first sees no live claim and wins; every subsequent one sees the marker the
  winner just set and raises `SessionClaimTimeoutError`. This is why the "no deadlocks"
  half of the acceptance criterion is structural, not just empirically true today — nothing
  ever *waits* for the slow part, only for another brief claim transaction.
- **The watchdog timeout lives on the *claim marker*, not the DB lock, because the DB lock
  is never held across the slow part at all.** `claim_session`'s own `SELECT ... FOR
  UPDATE` transaction commits (releasing the lock) before the caller does any slow work —
  so a process that crashes *during* the slow work holds no lock for anything else to wait
  on; the only trace left behind is `claimed_at`/`claimed_by`, which `_CLAIM_TIMEOUT_SECONDS`
  makes recognisable as abandoned. This is exactly the subtask's own framing ("timeout on
  the claim, not on the DB lock") and is why `advance_session_locked` releases the claim
  (without bumping `version`) on any exception from the interpreter, rather than leaving a
  failed attempt's marker in place for the full timeout window before another caller can
  retry.
- **Queueing is split into "durably record" (built, real, tested today) vs. "get
  consumed by the scheduler" (deferred, and correctly so).** `submit_queued_input` doesn't
  need the caller to hold or wait for the advance claim — it takes its own brief
  `FOR UPDATE`, which Postgres correctly serializes against any in-flight claim/commit
  transaction without ever blocking for the length of a slow model call. What it can't do
  yet is make a `mode: free` human actor's *next turn* actually resolve to that queued
  input — that requires the scheduler (B1.3) to check for one, which requires knowing what
  "the real HTTP submission flow" even looks like, which needs B1.7's agent runtime and a
  live `/sessions` endpoint wired to the new interpreter (still `core.process.skeleton`'s
  job today — B1.2's own documented scope boundary). Building the queueing *primitive*
  correctly now, and flagging the consuming half honestly, matches every other
  injection-seam decision made across B1.2–B1.4.
- **`advance_session_locked` doesn't add its own transaction boundaries around
  the interpreter's internal steps.** B1.2's `advance_session` already keeps every
  individual DB transaction short-lived (peek, external call, claim+commit — see B1.2's
  own idempotency fix), so wrapping the *entire* call in one outer claim/commit pair is
  sufficient to get "model calls happen outside the row lock": the outer claim is released
  before the interpreter loop starts, and outer commit only happens after the whole call
  returns. No lock is held across any part of it, slow or fast.
