# A1.6 — WRRF fusion + bucketed budget ★

**Phase:** 1 · **Track:** A · **Est:** 5d · **Status:** done
**Depends on:** A1.4, A1.5 · **Blocks:** A1.7, A1.9
**Plan refs:** §6.2, §6.3 (D2). **Critical path.**

## Goal
The mechanism that makes rule-vs-lore priority real: per-class token quotas from
`phase.budget.ratio`, weighted reciprocal-rank fusion for ordering. **No score multipliers
anywhere** — priority is budget allocation, never a scalar on similarity scores (D2).

## Subtasks
- [x] Budget split: `phase.budget.{ratio, max_tokens}` → per-class token buckets;
      `workspace_knowledge_attachment.priority_weight` applied as class-weight override.
      (`ratio`/`max_tokens`/`priority_weight` are passed as plain parameters, not read from
      a real `ProcessDefinition`/phase object — B1.1 doesn't exist yet; see design note.)
- [x] WRRF within class: fuse dense/sparse/keyed candidate lists on **ranks**,
      `k=60` (workspace-tunable), list weights `{dense: 1.0, sparse: 0.8, keyed: 1.2}`.
- [x] Bucket fill: `constant` entries first, then fused-ranked entries until the token
      bucket is exhausted; entries never split mid-chunk.
- [x] Spill policy: unfilled budget in one bucket spills to others — `proportional` default,
      `none` option; read from `phase.budget.spill`. (Same caveat: passed as a parameter.)
- [x] Every included chunk carries `(source_id, version, entry_key, chunk_id, class, bucket,
      rank, score, why)` — the manifest's raw material (C1.3) and requirement 6's substrate.
- [x] Property test: changing `ratio` changes bucket composition deterministically; same
      inputs → same output (no hidden randomness).

## Acceptance criteria
- [x] A rules entry and a lore entry never compete for the same slot — cross-class
  displacement is impossible by construction (test).
  `test_rules_and_lore_chunks_never_compete_for_the_same_slot`: gives lore an objectively
  *stronger* per-chunk signal (exact embedding match + exact keyword match) than rules,
  and confirms rules still gets its full 50% budget share regardless — a lore chunk never
  displaces a rules slot, because they were never competing for the same one.
- [x] With ratio `{rules: 0.75, lore: 0.25}` vs `{rules: 0.25, lore: 0.75}` on a fixed
  corpus and query, the included sets differ and the difference is fully explained by
  bucket math (golden test — feeds the Phase-1 exit gate). `test_budget_ratio_change_
  produces_different_included_sets`: 8 equally-matching chunks (4 rules, 4 lore, 10 tokens
  each), 40-token budget — asserts the exact counts (3 rules/1 lore vs. 1 rules/3 lore),
  not just "differ."
- [x] `grep -ri "score *\*" packages/core/knowledge/retrieval/` finds no class weighting
  applied to scores — encoded as an actual automated test
  (`test_no_score_multiplier.py`), not left as a manual review checklist item, matching
  this project's existing pattern (e.g. T0.5's INV-1 import-graph lint) of turning a
  reviewer's checklist item into something that fails CI if violated in the future.

## Design decisions

- **`RetrievalHit` (A1.4) gained `entry_key`/`token_count`.** WRRF and bucket-fill need
  `token_count` to know a hit's budget cost and `entry_key` for the manifest row shape;
  cheaper to select both once in `dense.py`/`sparse.py`'s existing join than to re-fetch
  per hit later. Backward-compatible (additive fields only).
- **Keyword-activated entries (A1.5) are expanded to chunk-level candidates**
  (`core/knowledge/retrieval/keyed.py`) before fusion: activation operates at the *entry*
  granularity, WRRF/the manifest operate at the *chunk* granularity. Each activated
  entry's chunks (ordinal-ordered) inherit a rank derived from the entry's activation
  rank, banded by `1000 * (activation_rank - 1) + ordinal + 1` so multi-chunk entries
  never collide on one rank and entries stay in their relative activation order.
- **`phase.budget.{ratio, max_tokens, spill}` are plain function parameters**, not read
  from a real `ProcessDefinition`/phase object — B1.1 (the DSL that would define them)
  doesn't exist yet, and this task's own dependency line (`A1.4, A1.5` only) deliberately
  doesn't wait for it, same scoping choice as A1.5. `core.knowledge.retrieval.assemble.
  search_and_budget` is the seam a future `ContextAssembler` (C1.2) will call, passing in
  whatever a real phase object resolves to.
- **`search_and_budget` is explicitly *not* the `ContextAssembler`** — it's the retrieval
  + fusion + budget slice only. No `VisibilityResolver` (C1.1, scope_keys is a parameter
  here), no entity-state rendering, no secrets gate, no prompt layout, no
  `ContextManifest` persistence (C1.3). Named to avoid any confusion with the later,
  much bigger C1.2 class.
- **Spill is one redistribution pass, not an iterative fixed point** — documented as a
  deliberate simplification in `fill_all_buckets`'s docstring, not a silent gap.
- **`bucket` and `class_` are the same value** in this design (one bucket per class) —
  kept as separate `BudgetedChunk` fields anyway to match the manifest's named columns
  from the plan exactly (plan §6.3 step 7 lists both).
