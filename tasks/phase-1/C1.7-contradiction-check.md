# C1.7 — Contradiction check (flag-only)

**Phase:** 1 · **Track:** C · **Est:** 2d · **Status:** done
**Depends on:** C1.6 · **Blocks:** —
**Plan refs:** §9.2 step 7, §16.4 (Q4: badge, no auto-regeneration)

## Goal
Best-effort scan of a reply against its turn's resolution records; contradictions get
flagged for a UI badge. **No regeneration** — Q4 is decided. (This does NOT generalise to
the Phase-2 secret leak check, which does regenerate.)

## Subtasks
- [x] Scanner: extract numerals and outcome words from the reply near references to the
      resolution; compare against `total`/`outcome` of the turn's records; conservative —
      prefer false negatives over noisy flags.
- [x] Flag persisted on the message (`moderation_flags.contradiction: [record_ids]`).
- [x] SSE event so the UI can render the correction badge (D1.3 consumes).
- [x] Contradiction-rate metric exported (§16.4: measure from the first session; under ~1%
      the badge is the permanent answer).

## Acceptance criteria
- Seeded fixtures: "you barely fail" against a SUCCESS record → flagged; a faithful
  narration → not flagged; a narration not mentioning the roll → not flagged.
  → `test_barely_fail_against_a_success_record_is_flagged`,
    `test_faithful_narration_is_not_flagged`,
    `test_narration_not_mentioning_the_roll_is_not_flagged`
- No model call, no added turn latency beyond a bounded scan (<10ms typical).
  → structural: `scan_for_contradictions` does zero I/O, zero model calls -- two regex
    scans over the reply text and a linear walk over the turn's (small, typically
    single-digit) record list. Not covered by a timing assertion (flaky in CI by nature);
    the property is guaranteed by what the function doesn't do, not something to measure.

## Design decisions
- **Two independent, narrow signals, each only fires when unambiguous.** Outcome words:
  a reply mentioning both success- and failure-family words (ambiguous prose) gets no
  signal at all, not a guess -- `test_ambiguous_text_mentioning_both_outcomes_is_not_flagged`.
  A stated total: only numbers in roll-referencing patterns ("rolled a 12", "total of 12",
  "12 vs 15") count as a claimed total -- a stray digit elsewhere ("12 gold coins") is
  never mistaken for one (`test_stray_number_unrelated_to_the_roll_is_not_flagged`).
- **Banded outcomes (`"partial_success"` etc, PbtA-style) are never checked by the
  outcome-word heuristic** -- only compared when `record.outcome` is literally
  `"success"`/`"failure"`. This simple word lexicon has no reliable way to represent
  "partial success" narration, and guessing would risk exactly the noisy false positive
  the task explicitly says to avoid (`test_banded_outcome_is_never_flagged_by_the_word_heuristic`).
- **`message.moderation_flags` added by this task's migration** (plan §12.7 already
  reserved the column; nothing had written to it yet). `flag_contradictions()` is a no-op
  on an empty flag list, leaving the column at its default `{}` -- "flagged" means
  exactly "the `contradiction` key is present and non-empty," never "present but empty."
- **SSE wiring reuses the existing, already-generic `api.streaming.pubsub.publish_event`**
  (built for T0.8's walking skeleton, already carries arbitrary `kind`/`payload`) rather
  than a new mechanism -- a caller emits a `"contradiction_flag"` kind event through it.
  Not yet wired into the actual turn-commit flow (`core.agents.runtime`/
  `core.process.skeleton`), the same "not yet integrated into the runtime" gap C1.2-C1.6
  all flagged for their own pieces -- there is still no caller in Phase 1 that both
  generates a reply *and* has resolution records from the same turn to scan against
  (that integration is real, but it's D1.3/the eventual runtime-wiring task's job, not a
  redesign of this module).
- **`contradiction_rate` is a plain aggregate query** over `message.moderation_flags` --
  no new table, mirrors C1.4's `usage_dashboard` shape (a read-only aggregation layer
  over data another module already writes).
