# D1.2 — Process Definition editor (React Flow)

**Phase:** 1 · **Track:** D · **Est:** 10d · **Status:** done
**Depends on:** T0.9, B1.1 · **Blocks:** F3.11 reuses the canvas
**Plan refs:** §5.2, §13.4. The reason the frontend is React (plan D9).

## Goal
Visual authoring of ProcessDefinitions by non-programmers: phases as nodes, transitions as
edges, everything the DSL expresses editable in an inspector.

## Subtasks
- [x] React Flow canvas: phase nodes, transition/gate edges (on_complete, gates with
      `on`/`when`/`else`, await timeout edges rendered distinctly); layout persistence.
- [x] Phase inspector panel: label_key, actors (role, mode, order, max_turns), **visibility
      block** (knowledge classes, scopes, entity fields, secrets mode), **budget** (ratio
      sliders that must sum to 1, max_tokens, spill), flags (`mechanical`,
      `requires_citation`), tools, await config.
- [x] Session-state variable editor (`state:` declarations with types/defaults).
- [x] CEL editing with save-time validation surfaced inline (B1.1 returns field-addressed
      errors — map them onto the canvas/inspector; a phase missing `visibility` renders as
      invalid).
- [x] Version history: definitions are versioned; publishing from the editor creates a new
      version; read-only view of prior versions.
- [x] Template gallery: start from the shipped fixtures (3-phase MVP, Standard Session
      Flow) — **never from an empty canvas** (§16.5 discipline 2).

## Acceptance criteria
- Author the §5.2 Standard Session Flow entirely in the UI; the saved JSON validates and
  runs a session.
  → `ProcessDefinitionListPage`'s template gallery serves `STANDARD_SESSION_FLOW` verbatim
    (new `GET /process-definitions/templates`, backed by B1.1's own fixture, not a
    frontend-duplicated copy); `ProcessEditorPage` loads it as the working draft and
    "Publish new version" calls the same `POST /process-definitions` a hand-authored
    document would. Proven server-side by
    `test_standard_session_flow_template_publishes_unmodified` (fetches the template,
    publishes it unmodified, re-fetches and re-validates the persisted document — 200,
    `{"valid": true, "issues": []}`). That this exact fixture actually *runs* a session
    end to end is already proven by B1.2's own `test_interpreter.py`/`test_awaits.py`
    golden tests — this task doesn't re-prove interpretation, only that what the editor
    hands the author is byte-identical to what those tests already exercise.
- Every B1.1 validation failure fixture surfaces as a visible, located error in the editor.
  → `ProcessEditorPage` debounces the working draft into `POST /process-definitions/validate`
    on every change and stores the field-addressed `issues` array; `ProcessCanvas` maps
    `phases.<key>...` prefixes onto the matching node (red border) and `PhaseInspector`
    maps exact/prefixed paths onto the specific control (`label_key`, each actor, each
    gate, budget.ratio, await.timeout/on_timeout, effects) via a shared `issuesFor()`
    prefix-match helper — the same `field_path` strings `validator.py` emits, unmodified.
- Budget ratios: UI prevents publishing ratios that don't sum to 1.
  → `ProcessEditorPage.budgetRatioIssues()` recomputes every phase's ratio sum client-side
    (same ±0.02 tolerance as `validator.py`'s `_BUDGET_RATIO_TOLERANCE`) and disables the
    "Publish new version" button whenever any phase's budget doesn't sum to ~1 — checked
    before the request is even sent, not just surfaced after a 422. The inspector's
    `BudgetEditor` shows the running sum live next to the ratio sliders.

## Design decisions
- **No update-in-place endpoint exists, by design (B1.1)** — `create_definition` always
  inserts a new, immutable, auto-incremented version row for a given `(workspace_id, key)`.
  The editor's "Publish new version" button is therefore always a `POST`, never a `PUT`;
  there is no separate "save draft" state — the working draft lives only in the editor's
  React state (and the version-history panel's "View / restore" action) until published.
- **Two small, genuinely necessary backend additions** (same bar as D1.1's three):
  - `DefinitionResponse.created_at` — needed to order/display the version-history list;
    the column already existed on `ProcessDefinitionRow`, just wasn't exposed. Covered by
    `test_definition_response_includes_created_at`.
  - `GET /process-definitions/templates` — serves `STANDARD_SESSION_FLOW`/`MINIMAL_MVP_FLOW`
    from B1.1's own `fixtures.py` rather than hand-duplicating that JSON in a `.tsx` file,
    so the gallery can never drift from what B1.2's interpreter tests actually exercise.
    Registered *before* `/{definition_id}` in the router (FastAPI matches path-param
    routes eagerly; a literal segment must come first or "templates" 422s trying to parse
    as a UUID). Covered by `test_templates_endpoint_serves_the_named_fixtures`.
  - No new migration — both additions are read paths over existing columns.
- **The DSL's JSON shape is hand-mirrored in `dsl.ts`, not derived from the generated
  OpenAPI schema.** `DefinitionResponse.definition` is `dict[str, object]` on the wire
  (Pydantic's own JSON-schema generation erases `ProcessDefinitionDSL`'s structure at the
  API boundary, since it's stored/returned as opaque JSONB) — `schema.ts` only ever sees
  `{ [key: string]: unknown }` for it. `dsl.ts` is deliberately documented as a hand-kept
  mirror of `packages/core/process/dsl/schema.py` that must be updated by hand if that
  file changes; the backend's own `/validate` endpoint remains the actual authority on
  "is this a legal document," so a `dsl.ts` drift can produce a document that's rejected
  server-side (loud, visible) but never one that's silently accepted when it shouldn't be.
- **Layout is not part of the authored document.** `schema.py`'s models are all
  `extra="forbid"`, and node position is presentation, not process content — B1.2's
  interpreter has no use for it. Positions are computed client-side (`layout.ts`'s
  `autoLayout`, a BFS-depth-from-`initial_phase` column layout) and persisted separately
  in `localStorage`, keyed by `workspace_id:key` — not round-tripped through the backend
  at all. A definition with no saved layout (a fresh template, or opened on a different
  browser) just re-auto-lays-out; dragging a node persists that phase's position going
  forward.
- **Version history lists client-side-filtered, not via a new endpoint.** Unlike D1.1
  (where "list versions of a source" and "list attachments of a source" were added as
  real endpoints because A1.8/A1.1 never needed either), `list_definitions` already
  returns every version of every key in a workspace — the version-history panel just
  filters that response by `key` and sorts by version descending. The result set here is
  inherently small (one row per publish), so no backend change earns its keep the way
  D1.1's did.
- **"CEL editing" is plain text inputs, not a syntax-highlighted/autocompleting editor.**
  `gate.when` and `effect.to` are rendered as `<input>` (monospace) with no client-side
  CEL parsing — `compile_check` (C1.5/B1.1) is the only real CEL validator in the system,
  and it's already wired in via the debounced `/validate` call, so a second, weaker
  client-side CEL implementation would just be a second source of truth to keep in sync
  for no benefit the acceptance criteria asked for.
- **No interactive browser click-through was possible in this sandbox** (same limitation
  as D1.1 — no browser automation tool available). Verified instead: `tsc -b --noEmit` and
  `eslint .` both clean; every new source file (`dsl.ts`, `layout.ts`, `ProcessCanvas.tsx`,
  `PhaseInspector.tsx`, `StateVarsEditor.tsx`, `VersionHistoryPanel.tsx`,
  `ProcessDefinitionListPage.tsx`, `ProcessEditorPage.tsx`, plus the modified `App.tsx`/
  `AppShell.tsx`) fetched directly from the Vite dev server returns 200 with no
  syntax/transform error, including confirming `@xyflow/react`'s pre-bundled JS and its
  `style.css` both resolve; and the exact API contract the editor calls
  (`/process-definitions/validate`, `/process-definitions` POST/GET,
  `/process-definitions/{id}`, `/process-definitions/templates`) is fully exercised by the
  backend's own `TestClient`-based tests. Flagged honestly rather than assumed working.
