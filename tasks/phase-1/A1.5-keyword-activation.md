# A1.5 — Keyword activation (SillyTavern-style)

**Phase:** 1 · **Track:** A · **Est:** 5d · **Status:** done
**Depends on:** A1.1 · **Blocks:** A1.6
**Plan refs:** §6.4, §3.3

## Goal
The activation semantics borrowed from SillyTavern's World Info — the hard-won,
non-obvious part of the category's best knowledge-injection system.

## Subtasks
- [x] Key matching: `keys[]` / `secondary_keys[]` with AND/OR/NOT `logic`; optional
      `use_regex` (compile-checked at save; catastrophic-backtracking guard via timeout).
- [x] `constant` entries: always active, consume budget first (fill order handled in A1.6).
- [x] **Temporal state:** `sticky: N` (stays active N turns after firing), `cooldown: N`
      (can't refire for N turns), `delay: N` (won't fire before turn N). State is
      per-session, stored in session derived state — never on the entry.
- [x] `trigger_pct` probabilistic activation (seeded from session for replayability);
      `inclusion_group` (only one member activates — highest rank wins).
- [x] Scan window: recent turns text assembled per phase; activation evaluated per class.
      (`activate_entries` takes already-assembled `scan_text` — assembling it *per phase*
      from recent turns is the future assembler's job, C1.2; not something this pure
      function can own without a phase/turn model to read from.)
- [x] Returns activated entries as a ranked list (`keyed` list for WRRF, weight 1.2).

## Acceptance criteria
- [x] Table-driven tests for every field and combination (sticky continuing across turns,
  cooldown blocking refire, delay gating, group exclusivity). 24 tests in
  `packages/core/knowledge/tests/test_activation.py`, pure unit tests (no DB — the
  function this task builds is pure).
- [x] Activation state survives session resume (persisted with session state) — **scoped
  down, see note below.** Verified at the granularity this task actually owns: `new_state`
  is a plain, JSON-shaped dict of `EntryActivationState` that round-trips correctly when
  fed back in as `prior_state` on a later call. The actual DB/session persistence wiring
  depends on B1.4 (event log + checkpoints), which doesn't exist yet — this task's own
  dependency line (`Depends on: A1.1` only) deliberately doesn't wait for it, matching how
  Track A and Track B were originally meant to be built by different engineers in
  parallel. `core.knowledge.activation` owns the activation logic and its state *shape*;
  wiring that state into a real session's persisted, checkpointed storage is B1.4's
  integration job, not re-scoped into this task.
- [x] Replaying a session (INV-10) reproduces identical activation outcomes, including
  `trigger_pct` (seeded) — same scoping: `test_replaying_the_same_turn_sequence_
  reproduces_identical_outcomes` proves a multi-turn sequence of `activate_entries` calls
  (same `rng_seed` throughout) reproduces byte-identical outcomes at every turn. Full
  session-level INV-10 replay (via a `ContextManifest`) is C1.3's job.

## Design decisions

- **Pure function, not a DB-touching module.** `activate_entries` takes already-fetched
  entries (an `ActivatableEntry` Protocol, satisfied structurally by
  `core.knowledge.models.KnowledgeEntry` — tests use a lightweight `FakeEntry` instead of
  real ORM rows), scan text, turn index, prior state, and an rng seed; returns activated
  entries + new state. No `tenant_scope`, no imports of `core.knowledge.repo` or
  `authoring`. The caller (eventually the assembler) fetches entries and persists state.
- **Secondary-key logic condensed to 3 modes**, not SillyTavern's 4
  (`AND_ANY`/`AND_ALL`/`NOT_ANY`/`NOT_ALL`), to fit the `logic` CHECK constraint already
  committed in A1.1's schema (`'AND'|'OR'|'NOT'`): primary `keys[]` always match on OR;
  `logic` governs how `secondary_keys[]` modifies that verdict (`AND` = secondary must
  also match; `OR` = either list alone suffices; `NOT` = secondary match blocks
  activation). Documented in the module docstring as a deliberate, faithful-in-spirit but
  not byte-identical simplification.
- **`inclusion_group` exclusivity uses `insertion_order`** (lowest wins) as the ranking
  signal, since WRRF's real `rank` (A1.6) doesn't exist yet at this stage of the pipeline
  — activation runs before retrieval is fused in.

## Bugs found and fixed along the way
- **The regex catastrophic-backtracking guard didn't guard anything, twice.** First
  attempt: `ThreadPoolExecutor` used as a `with` block — its `__exit__` calls
  `shutdown(wait=True)`, which blocks until the submitted (runaway) task finishes,
  completely defeating the `future.result(timeout=...)` call right above it. Fixed to
  `shutdown(wait=False)` — but the *real* problem surfaced next: CPython's stdlib `re`
  engine never releases the GIL and has no periodic interrupt check during a match, so
  even with `shutdown(wait=False)`, a genuinely catastrophic pattern (`(a+)+$` against 30+
  `a`s) hung the entire test process for 15+ minutes (confirmed by manually killing a
  stuck `pytest` process burning 99% CPU) — no purely Python-level timeout mechanism
  (threads, `concurrent.futures`, `asyncio`) can interrupt it, because the interpreter
  itself is stuck inside a C loop that never yields. Fixed by switching to the
  `regex` package (already an undeclared transitive dependency via `transformers`;
  declared directly now), whose matching loop performs its own internal timeout checks
  and can actually abort a runaway match. This is the standard, correct solution for this
  exact problem — the thread/future approach was never going to work for stdlib `re`.
