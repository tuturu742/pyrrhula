# B1.2 — Process interpreter

**Phase:** 1 · **Track:** B · **Est:** 6d · **Status:** done
**Depends on:** B1.1 · **Blocks:** B1.3, B1.4
**Plan refs:** §5.3 (D1)

## Goal
The interpreter loop that executes ProcessDefinitions: phase state, gate evaluation,
effects, transitions. Replaces T0.8's placeholder engine.

## Subtasks
- [x] Core loop per §5.3: load session (FOR UPDATE — full locking in B1.5), resolve current
      phase, ask scheduler for next actor (B1.3), evaluate gates when actors are exhausted,
      transition. Scoped without FOR UPDATE (B1.5's own job) and with actor resolution
      fully injected (`next_actor_fn`) rather than built here — see design notes for why.
- [x] Gate evaluation: `on:` event gates, `when:` CEL over session state, `else` fallback;
      deterministic order (declaration order).
- [x] Effects execution on transition: `set` with CEL over `state.*`; effects are part of
      the transition event (atomic with it).
- [x] Session state: typed variables from `state:` declarations, defaults applied at
      session start, validated on every write. "Validated" = explicit re-typing against
      the declared type on every effect write (see design notes — this is stricter than
      just "shaped like JSON", it's exactly the type the DSL declared).
- [x] Transition = one transaction: state update + `session_event(phase_transition)` +
      checkpoint hook (B1.4). Checkpoint hook is an optional injected no-op today — B1.4
      doesn't exist yet; the seam is fixed, the real write isn't built here.
- [x] `flags` surfaced to callers (the assembler will read `mechanical` in Phase 2).
      `AdvanceResult.flags` on every return path.
- [x] Structured errors: an interpreter fault pauses the session (`status='paused'`) with a
      diagnostic event; never a stuck lock.

## Acceptance criteria
- [x] The 3-phase MVP definition runs a scripted session end to end (stub agent), producing
  the expected event sequence — golden test.
  `test_mvp_flow_runs_a_scripted_session_and_produces_the_expected_event_sequence`: 6
  interpreter steps (turn/transition x3, one full lap of the cyclic
  arbiter_narrate -> player_act -> resolve -> arbiter_narrate flow), asserting the exact
  `session_event` kind/seq/payload sequence, final `session.state`, and all three
  message bodies.
- [x] The §5.2 example's `resolution` phase branches to `feedback_loop` on
  `round % 3 == 0` and to `open_discussion` otherwise (CEL gate test).
  Two tests seed `resolution` directly with `state.round` at 5 and 6, run one interpreter
  step, and assert the exact branch taken — plus assert the stored `pending_feedback` is a
  real Python `bool`, not celpy's `BoolType` (see the JSON-serialization bug below).
- [x] Kill the process mid-turn; the session resumes from persisted state without
  duplicate side effects (with T0.7 idempotency).
  `test_run_actor_turn_resumes_after_the_side_effect_but_before_the_final_commit`
  faithfully simulates the exact crash window: the idempotent side effect (`execute_turn`)
  already completed and its own transaction committed, but `_run_actor_turn`'s wrapping
  commit (message/event/`next_event_seq`) never ran. A resumed call reuses the cached
  result — `execute_turn` is not re-invoked — and still correctly commits exactly one
  message. `test_resumed_turn_with_the_same_peeked_event_seq_does_not_reexecute_the_
  side_effect` proves the same property at the idempotent-unit level directly.

## Design decisions

- **A real idempotency bug found by reasoning through the resume acceptance criterion,
  not by observing a test failure:** the first draft claimed (incremented and committed)
  `next_event_seq` in an isolated transaction *before* the idempotent-wrapped
  `execute_turn` call. A crash between that claim and the final message/event commit meant
  a retry would peek a *new*, higher `next_event_seq`, derive a *different* idempotency
  key (`turn:{session_id}:{event_seq}`), and re-run `execute_turn` anyway — silently
  defeating the entire point of keying it at all. Fixed: `next_event_seq` is only
  *peeked* before the idempotent call and only actually claimed (incremented + committed)
  in the same transaction as the message/event it belongs to, so a crash-and-retry before
  that commit peeks the *same* value, derives the *same* key, and gets the cached result.
  A defensive re-check (`row.next_event_seq != event_seq` -> `InterpreterFaultError`)
  guards the single-writer assumption this relies on until B1.5 lands real locking.
- **A second, independent bug found the same way, in `advance_session`'s own return
  value:** when `max_steps` is reached immediately after a transition (via `continue`),
  the loop exits without another top-of-loop re-read, so the local `phase_key` variable
  used to build the final `AdvanceResult` was one transition stale. Fixed by re-reading
  `current_phase` fresh from the DB before constructing the "active" result rather than
  trusting loop-local state that a same-iteration transition can invalidate. Caught by the
  CEL gate tests (`max_steps=1`, transition-then-immediately-report), not the golden test
  (whose final step happens to be a turn, not a transition) — a reminder that "the happy
  path golden test passed" doesn't mean every return path was exercised.
- **CEL evaluation results are explicitly re-typed against the DSL's own declared `state:`
  types before being stored, not stored as whatever celpy's internal type happens to be.**
  Found while writing the CEL gate test: celpy's `BoolType` subclasses Python `int`, not
  `bool` — `json.dumps(BoolType(True))` serialises as `1`, not `true`. Storing a CEL
  boolean result straight into the JSONB `state` column would have silently corrupted a
  `boolean` state variable into an integer the moment it was next read back (and the next
  CEL evaluation referencing it would have seen an int, not a bool — a live footgun for
  every `when:` gate checking a boolean flag). `_apply_effects` coerces every effect's
  result through `_COERCE_BY_TYPE[declared_type]` before writing it into state.
- **Actor resolution is entirely injected (`next_actor_fn`), not implemented here — not a
  simplification, a hard dependency-order constraint.** The `agent` table has no
  `agent_role` column yet (that's B1.7's job), so this module *cannot* query "which agents
  have role X" even if it tried; and turn ordering/cursor persistence is B1.3's whole
  remaining job, not something to half-build inline just because B1.2 runs first in the
  dependency graph. `next_actor_fn`/`execute_turn`/`checkpoint_hook` are the fixed seams
  B1.3/B1.7/B1.4 slot real implementations into, mirroring T0.8's own
  `model_provider_factory`/`on_chunk` injection for the identical reason (core must not
  depend on an adapter, or here, on schema that doesn't exist yet).
- **`core.process.skeleton` (T0.8) is untouched and still powers the live `/sessions` HTTP
  flow.** This task's own file scope is `packages/core/process/interpreter.py`; wiring a
  real HTTP endpoint to the new interpreter needs B1.7's agent runtime (for `execute_turn`)
  and B1.3's scheduler (for `next_actor_fn`), so rewiring the API now would mean wiring it
  to stubs, then rewiring it twice more. Mirrors how A1.6 built `search_and_budget` fully
  before C1.2 ever calls it — complete and tested, not yet load-bearing.
- **`session` gained three new columns** (`state` JSONB, `process_definition_id`,
  `process_definition_version`) and `current_phase` was widened from `String(16)` (T0.8's
  `prompt`/`respond` fit; a real DSL's `facilitator_frame` doesn't) to `String(63)` —
  extending T0.8's schema in place, the same pattern its own docstring already promised,
  just one increment earlier than B1.4's fuller extension (`actor_cursor`, optimistic
  `version` lock). All new columns nullable so T0.8-skeleton sessions keep working
  unmodified — confirmed live (`test_skeleton.py`, `test_sessions_flow.py` still green).
- **A registration-order bug found while first running the new tests, not designed for
  upfront:** `session.process_definition_id` FKs to `process_definition.id` by string
  reference; SQLAlchemy only resolves that at mapper-configuration time, which needs
  `ProcessDefinitionRow`'s module imported by *something* first. A test importing only
  `core.process.interpreter` (never anything that pulls in `core.process.models`) hit
  `NoReferencedTableError`. Fixed by having `core.sessions.models` import
  `core.process.models` directly (matching why `migrations/env.py` explicitly imports
  every model module for the identical reason) — robust regardless of what any given
  caller happens to import.
