# C1.8 — Citation validation

**Phase:** 1 · **Track:** C · **Est:** 3d · **Status:** done
**Depends on:** C1.3 · **Blocks:** D1.4 (citation links)
**Plan refs:** §6.5 (req 6)

## Goal
Agents cite `[k7]`-style knowledge IDs; a cheap post-generation validator checks citations
against the manifest so "why did the Arbiter rule that way" is answerable at the pinned
version, forever.

## Subtasks
- [x] Citation syntax in the knowledge envelope + system instruction to cite entry IDs when
      a ruling depends on one.
- [x] Post-generation validator: every cited ID must exist in the message's manifest;
      hallucinated citations flagged on the message (`moderation_flags.bad_citation`).
- [x] `requires_citation` phase flag (DSL, B1.1 already parses `flags`): a ruling-type reply
      with zero citations in such a phase → flagged.
- [x] Persist the validated citation set on `message.citations` as
      `(entry_key, source_id, version_id)` — version-pinned.
- [x] API: resolve a citation to the entry content **at the pinned version** (UI renders as
      a link; still correct after the rulebook changes).

## Acceptance criteria
- A reply citing an ID absent from the manifest is flagged (test).
  → `test_a_reply_citing_an_id_absent_from_the_manifest_is_flagged`
- Citation resolution returns the pinned version's text even after two subsequent publishes
  (test).
  → `test_citation_resolution_returns_the_pinned_versions_text_after_two_more_publishes`
  (unit level), `test_message_citations_endpoint_resolves_the_pinned_version` (API level,
  publishes again *between* validation and the API call)
- Validator adds no model call and negligible latency.
  → structural: `validate_citations` does zero I/O -- a regex scan over the reply text
    plus a dict lookup per cited id against the (already-in-memory) manifest entries.

## Design decisions
- **Citation ids reuse C1.2's own `ManifestEntry.citation_id`** (`k1`, `k2`, ...) rather
  than inventing a second id scheme -- the envelope already assigns these at render time
  (§6.5's own example, `<knowledge id="k7" ...>`), so the system instruction just has to
  tell the agent to cite that same id, and validation is a lookup against the manifest
  entries already stored as JSON (`core.assembler.manifest`'s `_entry_to_json` shape).
- **`message.citations` records `(citation_id, entry_key, source_id, version_id)` at
  generation time, not resolved content** -- resolving happens lazily, on read
  (`resolve_citation`), always against that exact pinned `version_id`. This is what makes
  "why did the Arbiter rule that way" answerable *forever*: two more publishes after the
  citation was recorded don't change what it resolves to, proven by publishing a source
  three times and confirming a citation pinned to the first version still returns that
  version's text (both at the unit level and through the actual API endpoint).
- **`bad_citation` (hallucinated ids) and `missing_required_citation` (a `requires_citation`
  phase, zero valid citations) are independent, both possible on the same message** --
  a reply can cite one real id and one fabricated one, or cite nothing at all in a phase
  that requires it; `apply_citation_validation` sets whichever flags actually apply,
  never assuming they're mutually exclusive.
- **`message.citations` is always written, even when empty** -- unlike C1.7's
  `flag_contradictions` (a no-op when there's nothing to flag), a citations list is a
  real, meaningful fact about every reply ("cited nothing" is itself informative), so
  there's no "skip the write" case here.
- **New repo lookup, `get_entry_by_key_and_version`**, added to `core.knowledge.repo`
  (INV-1: only `core.assembler`/`core.overseer` may import it) rather than raw SQL in
  `citations.py` -- matches C1.2's own precedent of adding small, real repo functions
  instead of duplicating queries at the call site.
