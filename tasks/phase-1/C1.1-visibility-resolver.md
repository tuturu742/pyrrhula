# C1.1 — VisibilityResolver ★

**Phase:** 1 · **Track:** C · **Est:** 4d · **Status:** done
**Depends on:** T0.2, B1.1 · **Blocks:** C1.2, E2.1, G4.5
**Plan refs:** §7.2, §11.4 (req 13)

## Goal
The single component that answers "which scope keys may this principal read in this phase?"
— consumed by retrieval, context assembly, and (via the EXPORT pseudo-phase) export.

## Subtasks
- [x] `scope` table per §12.6 (`kind: public|role|group|private`, `members` JSONB,
      `UNIQUE(workspace_id, key)`); RLS + isolation tests; default scopes seeded per
      workspace (`workspace_public`, `facilitator_only`).
- [x] `scopes_for(principal, phase, session) -> frozenset[str]`: intersect the phase's
      `visibility.scopes` declaration with the principal's memberships (role scopes via
      workspace role; group/private via `members`); agents resolve through their principal.
- [x] Private scopes: `agent_private:<id>` convention for per-principal compartments
      (groundwork for secrets in Phase 2).
- [x] **`EXPORT` pseudo-phase:** `scopes_for(principal, phase=EXPORT, session=None)` returns
      the principal's full legitimate scope set independent of any process definition —
      export must reuse this, never reimplement visibility (§11.4).
- [x] Result is the mandatory input to every retrieval call (INV-4) — wire the type so a
      scope set can only be obtained from the resolver (newtype/branded set).

## Acceptance criteria
- Matrix test: (facilitator, participant, viewer, agent) × (phases with differing
  `visibility.scopes`) → exact expected scope sets.
  → `test_scope_matrix_across_roles_and_phases`, `test_phase_declaring_no_scopes_yields_only_the_private_compartment`
- A principal outside a `private` scope's members never receives its key, in any phase.
  → `test_principal_outside_private_scope_members_never_receives_its_key`,
    `test_no_principal_ever_receives_anothers_private_compartment_key`,
    `test_principal_with_no_workspace_relationship_gets_nothing`
- EXPORT pseudo-phase returns held scopes only — golden test shared with G4.5 later.
  → `test_export_returns_full_legitimate_scope_set_independent_of_any_phase`,
    `test_export_matches_phase_scoped_result_when_phase_declares_everything`

## Design decisions
- **`scopes_for` takes `visibility: VisibilitySpec | Literal["EXPORT"]`, not a `Phase`
  object.** The plan's signature is `scopes_for(principal, phase, session)`, but the only
  thing this function actually needs from a phase is its declared `visibility.scopes`
  list. Taking the `VisibilitySpec` directly (extracted by the caller from a
  `ProcessDefinitionDSL`'s `PhaseSpec.visibility`) keeps C1.1 decoupled from the
  interpreter (B1.2) — this task only depends on B1.1's DSL schema, not B1.2.
- **`members` JSONB shape**, since the plan's §12.6 snippet only says "principal/role
  refs" without pinning down the concrete structure: `kind='role'` → `{"roles": [...]}`,
  matched against `WorkspaceMembership.role` (human/service) or `Agent.agent_role`
  (agents) — deliberately the same string vocabulary where they overlap (`'facilitator'`
  means the same thing in both places). `kind='group'|'private'` → `{"principal_ids":
  [...]}`. Documented in `core.assembler.models`'s module docstring, the one place both
  the writer (`seed_default_scopes`) and reader (`scopes_for`) must agree on it.
- **`agent_private:<principal_id>` needs no `scope` row.** It's a structural convention:
  any principal with a role in the workspace is always granted their own compartment, in
  every phase including EXPORT, independent of whether it's declared in
  `visibility.scopes` — a process author can't enumerate per-principal keys they don't
  know at authoring time, and the convention can never leak (a principal can only ever
  compute *their own* id's key; `test_no_principal_ever_receives_anothers_private_compartment_key`
  proves declaring someone else's key in a phase's scope list still grants nothing extra).
- **A principal with no relationship to the workspace at all gets an empty `ScopeSet`**,
  not even their own private compartment — `_resolve_role` returning `None` short-circuits
  before the private-key grant. Distinguishes "no role" from "a role that doesn't match
  anything declared."
- **`ScopeSet` (the branded return type) lives in `core.ports.scope`, not
  `core.assembler`.** Putting it inside `core.assembler` would force
  `core.knowledge.retrieval.*` (which also needs to type its `scope_keys`/`scope_set`
  parameters against it, per the "mandatory input to every retrieval call" subtask) to
  import from `core.assembler` — the reverse of INV-1's whole import-graph shape
  (assembler/overseer depend on knowledge, never the other way). `core.ports` is already a
  dependency-free layer both sides import today. `dense.py`, `sparse.py`, `assemble.py`,
  and `cache.py`'s `CacheKey.scope_set` now type against `ScopeSet` instead of a bare
  `frozenset[str]` — a pure type-annotation change (`ScopeSet` *is* a `frozenset[str]`
  subclass) with zero runtime behaviour difference; mypy catches any call site that still
  builds a hand-rolled `frozenset` instead of going through the resolver. Left the generic
  `VectorStore` port (T0.3/`adapters/vector/pgvector`) untouched — it's a domain-agnostic
  port for any future non-knowledge consumer, not part of the retrieval cascade C1.1's
  subtask is about wiring.
- **`seed_default_scopes` is wired into `seed_dev_tenant`**, called only after that
  function's own `tenant_scope()` transaction commits (it opens its own separate
  transaction) — calling it from inside the still-open outer transaction would mean its FK
  to `workspace.id` can't yet see the just-created, uncommitted workspace row. No real
  "create workspace" API exists yet in this codebase (D-track UI work, still pending), so
  this is the one and only place workspace creation happens today.
- **`session_id` is accepted but unused.** A forward seam for a future session-scoped
  compartment (Phase 2: who has been *told* something *in this session*) — kept as a
  required parameter (not defaulted away) so call sites state explicitly whether they have
  a session or not (EXPORT always passes `None`), matching this project's established
  "no silent defaults on correctness-relevant parameters" discipline.
