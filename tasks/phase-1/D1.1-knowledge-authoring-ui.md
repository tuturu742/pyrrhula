# D1.1 — Knowledge authoring UI

**Phase:** 1 · **Track:** D · **Est:** 8d · **Status:** done
**Depends on:** T0.9, A1.8 · **Blocks:** —
**Plan refs:** §6.1, §6.4

## Goal
Author and manage Knowledge Sources: sources, entries, activation fields, versions, diffs.

## Subtasks
- [x] Source list per workspace: class badge (label via vocabulary overlay), attachment
      controls (enable, scope, priority weight, version pin vs follow-latest).
- [x] Entry editor: markdown body, title, class, scope picker; activation fields (keys,
      secondary keys, logic, regex toggle, constant, sticky/cooldown/delay, trigger %,
      inclusion group, position) with inline help.
- [x] Upload/ingestion flow: file drop → job progress (from A1.2's job states) → entry
      review/re-split.
- [x] Version history: list versions, publish draft with change note, entry-level diff view
      (added/removed/changed from A1.8's endpoint) with text diffs.
- [x] Fork-from-version action (incl. library-source fork-on-edit affordance from A1.10).
- [x] Library sources visibly badged read-only ("editing creates your own copy").

## Acceptance criteria
- Full authoring loop without touching the API directly: create source → add/upload entries
  → set activation fields → publish → attach to a second workspace with a different priority.
  → `KnowledgeSourceDetailPage` composes `EntryEditor`/`UploadPanel`/`VersionsPanel`/
    `AttachmentsPanel`; the identical sequence is proven server-side by
    `test_own_source_is_not_library_and_entry_activation_fields_round_trip` +
    `test_attach_same_source_to_two_workspaces_over_http` (523 backend tests green,
    twice, for repeatability).
- Diff view matches A1.8's golden fixtures.
  → `VersionsPanel`'s `DiffView` renders `VersionDiffResponse` (added/removed/changed +
    text_diff) directly, no client-side recomputation — A1.8's own fixture tests already
    prove the endpoint's shape; this just renders it.
- All nouns resolved through the vocabulary layer (a rules source shows "Rulebook" under
  `rpg_v1`).
  → added `class.rules`/`class.lore`/`class.misc` to `RPG_V1_LABELS`; every source/entry
    class badge in the new components goes through `t()`, never a hardcoded string.

## Design decisions
- **The generated API schema (`web/src/lib/api-client/schema.ts`) was stale** —
  generated only against T0.8/T0.9's session/workspace surface, missing every route
  added since (knowledge, process-definitions, usage, citations). Regenerated against
  the live server before writing any frontend code; `openapi-typescript`'s own
  URL-fetch mode hit a Node `fetch`/`undici` headers-timeout against `localhost` in this
  sandbox (curl to the same URL was instant) — worked around by `curl`-ing
  `/openapi.json` to a file first and pointing `openapi-typescript` at that file
  instead of a URL, which is instant. Not a code change, just how the schema gets
  regenerated in this environment.
- **Three small, genuinely necessary backend additions**, found while building the
  screens their own acceptance criteria need:
  - `SourceResponse.is_library` — nothing exposed whether a source was library-owned
    (D13/A1.10's RLS disjunct makes library sources visible under any tenant's session,
    but indistinguishably from the tenant's own, since the response never carried
    `tenant_id`). Needed for the "library sources visibly badged read-only" criterion.
  - `EntryResponse` gained the same activation fields `EntryRequest` already accepted on
    write (`keys`, `secondary_keys`, `logic`, `use_regex`, `constant`, `sticky`,
    `cooldown`, `delay`, `trigger_pct`, `inclusion_group`, `position`,
    `insertion_order`) — the response was missing all of them, which made editing an
    *existing* entry unable to round-trip its own activation state.
  - `GET /knowledge/sources/{id}/versions` (+ `core.knowledge.authoring.list_versions`)
    and `GET /knowledge/sources/{id}/attachments` (+ `list_source_attachments`) — neither
    existed; A1.8/A1.1's own endpoints never needed "list all versions of a source" or
    "list all workspaces a source is attached to" as their own acceptance criteria, but
    D1.1's version history and attachments panels structurally need both. Each backed
    by a real test (`test_list_versions_endpoint_returns_newest_first`, the extended
    `test_attach_same_source_to_two_workspaces_over_http`), not just added to satisfy
    the frontend silently.
- **Upload uses a `FormData` body directly** through `openapi-fetch`, which skips JSON
  serialization for `FormData` instances and lets the browser set the multipart
  `Content-Type` (with boundary) itself — matches the backend's existing
  `File`/`Form`-based endpoint without inventing a second upload path.
- **No interactive browser click-through was possible in this sandbox** — no browser
  automation tool is available. Verified instead: `tsc -b --noEmit` and `eslint .` both
  clean; the Vite dev server serves the app shell and every new component file
  transpiles successfully (200, no syntax/transform errors) when fetched directly; and
  the exact same API contract the UI calls is fully exercised by the backend's own
  `TestClient`-based HTTP tests. Flagged honestly per this session's own standing rule
  (say so explicitly rather than claim success) rather than assumed working.
