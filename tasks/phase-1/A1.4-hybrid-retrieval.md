# A1.4 — Hybrid retrieval

**Phase:** 1 · **Track:** A · **Est:** 4d · **Status:** done
**Depends on:** A1.3 · **Blocks:** A1.6
**Plan refs:** §6.3 step 3, §7.2, INV-4

## Goal
Dense + lexical search primitives with scope filtering pushed down into the query — the leak-
and recall-critical retrieval layer.

## Subtasks
- [x] Dense: pgvector HNSW cosine search; `tenant_id`, `scope_keys` (defaultless, required),
      `class_` all applied in the SQL WHERE. (Not through the `VectorStore` port — see design
      note below on why that plan changed.)
- [x] Sparse: `tsvector` + `ts_rank_cd` query with identical filter signature.
- [x] Both return `(chunk_id, entry_id, source_id, version_id, rank, score)` — ranks are
      what WRRF consumes (A1.6).
- [x] k=64 per list per class; configurable.
- [x] **Pushdown asserted by test:** EXPLAIN-based test proving the scope/class predicate is
      inside the plan, not applied in Python; plus a negative test that out-of-scope chunks
      never appear even with adversarial query text.
- [x] Query embedding path (embed the query once per turn, cached).

## Acceptance criteria
- [x] Calling either search without `scope_keys` is a type error (mypy) and a runtime error.
  `scope_keys` is a required keyword-only parameter with no default (mypy flags a missing
  call); an empty `frozenset()` is a distinct case, rejected at runtime with `ValueError`
  (`test_empty_scope_keys_raises` in both `test_dense.py`/`test_sparse.py`) — INV-4 requires
  both "missing" and "empty" to fail, since an empty set is otherwise indistinguishable from
  "no filter."
- [x] Out-of-scope content is absent from results in the negative test.
  `test_out_of_scope_chunk_never_appears_even_as_exact_match` (dense) constructs the
  worst case directly: the out-of-scope chunk's embedding is *identical* to the query
  vector (the best possible match by cosine similarity) and still never appears.
  `test_out_of_scope_chunk_never_appears_despite_matching_keywords` (sparse) does the
  lexical equivalent.
- [x] p95 latency on a 100k-chunk synthetic corpus recorded as a baseline (informational,
  not a gate): **p50 = 419.2ms, p95 = 477.2ms** (`scripts/bench_dense_retrieval.py`,
  50 queries against 100k chunks with uniformly random 1024-dim vectors and the default
  HNSW build parameters). Caveat: random, non-clustered vectors are close to a worst case
  for HNSW's approximate search — real embeddings cluster semantically, so production
  latency on real content is expected to be at or below this baseline, not above it.

## Design decisions

- **Doesn't reuse the `VectorStore` port/`PgVectorStore` adapter**, despite that adapter's
  own docstring (T0.3) saying A1.4 would "point [it] at the real `knowledge_chunk` table."
  `VectorSearchResult(payload: dict)` assumes a single JSONB payload column
  (`vector_store_item`); `knowledge_chunk`'s useful fields are several real columns plus a
  join for `source_id`, and WRRF (A1.6) needs `rank` (position within one query's ordered
  list), which the generic port has no place for. Resolved with dedicated,
  richer-shaped functions (`core/knowledge/retrieval/{dense,sparse}.py`) instead of
  contorting the generic port to fit; updated `PgVectorStore`'s docstring so it doesn't
  keep pointing at a plan that changed. The port/adapter still stand for any future
  non-knowledge vector-store consumer.
- **`version_id` on a hit reflects the chunk's current entry state** (almost always
  `NULL` — the mutable draft, since A1.8/versioning hasn't landed yet). Resolving "which
  version does this workspace's session actually read" (pin vs. follow-latest) is A1.8's
  job, not retrieval's; A1.4 returns whatever's there and lets a later layer resolve it.
- **The production query text is a shared module constant**
  (`DENSE_SEARCH_SQL`/`SPARSE_SEARCH_SQL`), not just inlined in the function — the
  pushdown test runs `EXPLAIN (FORMAT JSON)` against that *exact* string, so the test
  can't silently drift from what's actually executed by hand-copying an approximation of
  the query.
- **Query embedding cache is a per-turn, in-process object**
  (`core/knowledge/retrieval/query_embedding.py`), not Redis — "embed the query once per
  turn" only requires memoizing within one turn's several per-class dense searches
  (A1.6's bucketing calls the same query text multiple times); the persistent, cross-turn
  `(query_hash, scope_set, class, version_set)` cache is explicitly A1.9's separate job.
