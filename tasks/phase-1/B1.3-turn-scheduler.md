# B1.3 — Turn scheduler

**Phase:** 1 · **Track:** B · **Est:** 3d · **Status:** done
**Depends on:** B1.2 · **Blocks:** —
**Plan refs:** §5.2 actors, §5.3

## Goal
Actor ordering within a phase: who acts next, in what order, until when.

## Subtasks
- [x] `declared` order: actors act in list order.
- [x] `initiative` order: read an entity field (e.g. `entity_field("initiative")`) per actor
      at phase entry, sort desc, stable tiebreak; field path comes from the DSL, core never
      knows what "initiative" means. Field *values* are resolved by an injected function
      (no `entity` table exists in Phase 1 at all — see design notes); the sort/tiebreak
      mechanics themselves are real and tested.
- [x] `free` mode: any eligible actor may act; `max_turns` cap per phase; actor eligibility
      = phase's `actors` spec ∩ workspace membership. Read literally: `order: free`, not
      `mode: free` — see design notes on why these are two different, orthogonal fields.
- [x] `actor_cursor` persisted on the session (survives resume; part of checkpoints).
      New `session.actor_cursor` JSONB column (checkpoints themselves are B1.4).
- [x] Humans as actors: `mode: free` turns wait for human input (full await semantics in
      B1.6); `mode: generate` actors trigger the agent runtime. `mode` is passed through
      on the returned `ActorRef` untouched; B1.2's interpreter/B1.7's runtime act on it,
      this module only decides *who*, never *how*.
- [x] Scheduler exhaustion signals the interpreter to evaluate gates. Structural: returning
      `None` from a `NextActorFn` is exactly what B1.2's loop already treats as "exhausted,
      evaluate gates" — no new signal needed, the two modules share the contract as designed.

## Acceptance criteria
- [x] Table-driven tests per mode, including initiative ties and mid-phase actor removal.
  `test_scheduler.py`: declared (order + max_turns cap), initiative (descending sort +
  stable-tiebreak-by-declared-position), free (deterministic pick + max_turns cap, empty
  pool), and a dedicated mid-phase-removal test proving a candidate present in the
  originally-resolved order but absent from a later fresh resolve is skipped without
  consuming a turn and without blocking the candidates after it.
- [x] Cursor survives kill/resume mid-rotation without skipping or double-acting (test).
  `test_cursor_survives_simulated_kill_and_resume_mid_rotation`: takes one turn with a
  `make_scheduler(...)` closure, then builds a **second, independent** closure (no shared
  in-memory state at all — the only thing carried over is the DB-persisted
  `session.actor_cursor`) and confirms it continues from exactly the next candidate,
  neither repeating nor skipping. `test_cursor_resets_on_entering_a_different_phase`
  additionally proves a phase change starts the rotation over, not mid-way through a
  stale cursor. `test_scheduler_plugs_directly_into_advance_session_as_next_actor_fn`
  proves the composed result is a real `NextActorFn` B1.2 accepts unmodified, not just a
  same-shaped lookalike.

## Design decisions

- **Candidate resolution is split between real and injected, by what actually exists —
  the same constraint B1.2 hit one layer up.** `human_participant`/`any_of`'s human
  tokens resolve against a real `workspace_membership` query (that table exists, T0.2).
  Agent-role tokens (`agent_role`, `any_of`'s `"<role>_agent"` entries) and initiative
  order's entity-field *values* are injected: `agent.agent_role` doesn't exist as a column
  until B1.7, and there is no `entity`/`entity_schema` table anywhere in Phase 1's task
  list at all (checked: no task in phase-1 creates one — entities are a later phase).
  `make_default_candidate_resolver` is the real-today half (humans); its
  `agent_candidate_resolver` parameter is the seam B1.7 fills in.
- **`order` (declared/initiative/free) and `mode` (free/generate/generate_as) are
  orthogonal fields the DSL schema (B1.1) keeps deliberately separate, and it matters:**
  the subtask list's own phrasing ("`free` mode: any eligible actor may act") reads
  naturally as being about `mode: free`, but the acceptance criteria's "table-driven tests
  per mode" and the plan's own actor-spec vocabulary (`order: declared|initiative|free`)
  make clear the free-vs-fixed-order *scheduling algorithm* is selected by `order`, not
  `mode` — a `mode: generate` actor can still have `order: free` (e.g. "any available
  informational agent may answer"). This module reads `order` exclusively for scheduling
  and passes `mode` through untouched on the `ActorRef`, never inspecting it itself.
- **`order: free`'s eligibility-among-humans vs. actual turn-taking are different
  concerns, on purpose.** A human `mode: free` actor being "selected" by this scheduler
  only means they're the next eligible candidate in rotation — whether the interpreter
  actually *waits* for that specific human's input, or proceeds once *any* input arrives,
  is B1.6's full await/satisfaction semantics, explicitly out of this task's scope per its
  own subtask wording ("full await semantics in B1.6"). This module answers "who could act
  next," not "has anyone actually acted."
- **Mid-phase removal is answered by re-resolving fresh on every call, not by diffing
  against a cached set.** `declared`/`initiative` order is fixed once per phase-visit (a
  list of principal-id strings, cached in the cursor) so the *order* itself doesn't
  reshuffle turn to turn — but eligibility is re-checked against a *fresh* resolver call
  every time before advancing the cursor, so a candidate who becomes ineligible mid-visit
  is silently skipped (not given a turn, not blocking the candidates behind them) the next
  time their position comes up, without needing to explicitly detect *why* they dropped
  out (membership revoked, or anything else a future resolver might check).
- **`actor_cursor`'s persisted shape is per-phase-visit, keyed on `phase_key` plus which
  `actors[]` entry is currently active plus that entry's own sub-cursor** (`resolved_order`
  for declared/initiative, `turn_index`, `turns_taken`). A cursor whose `phase_key` doesn't
  match the session's *current* phase is treated identically to "no cursor yet" — this is
  what makes a phase re-entry (a cyclic flow revisiting the same phase key) start its
  rotation over rather than resuming a stale position from a previous visit.
