# B1.7 — Agent runtime

**Phase:** 1 · **Track:** B · **Est:** 5d · **Status:** done
**Depends on:** T0.3 · **Blocks:** D1.3, D1.5, G4.4, G4.12
**Plan refs:** §12.4, §13.6

## Goal
The runtime that executes one agent turn: provider call, streaming, internal tool loop,
retries and fallback, usage metering.

## Subtasks
- [x] `agent` + `model_profile` tables per §12.4 (agents ARE principals — create the
      principal row with the agent; `credential_ref` only, never keys); RLS + isolation tests.
      (`agent`/`model_profile` already existed from T0.8; this task extends them in place
      with `agent.agent_role` and `model_profile.fallback_profile_id` — migration
      `6a3d9e5c1f84_agent_runtime_fields`.)
- [x] Turn execution: takes a rendered context (a plain `list[dict[str, str]]` message list
      today — a stub seam until C1.2's `ContextManifest` exists), calls
      `ModelProvider.generate(purpose='generation')`, streams chunks via `on_chunk`, persists
      the final message with `context_manifest_id` (nullable FK-less column, populated once
      C1.3 exists).
- [x] Tool loop: model emits tool calls → dispatch via `core.agents.tools.ToolRegistry`
      (empty by default — no tools hardcoded; C1.6 registers the real ones) → results
      appended to the conversation → continue until final text or loop cap
      (`max_tool_loop`, default 8, raises `ToolLoopExceededError`).
- [x] Retries with backoff on provider errors; **fallback profile**
      (`model_profile.fallback_profile_id`) tried once after `max_retries` primary
      failures; tool dispatch (not the provider call) is idempotency-keyed (T0.7) so
      retries/resumes never double-execute a tool's side effect.
- [x] Usage metering: one `usage_record` per provider call in the loop (including
      tool-loop intermediate calls), written in the same transaction as the final message
      and session_event — all or nothing.
- [x] Agent role types (`facilitator|participant|informational`) carried on
      `agent.agent_role` (CHECK constraint), default `participant`; the scheduler/assembler
      read this field once they exist (B1.3/B1.6 both found the column missing and
      deferred it here).

## Acceptance criteria
- A scripted turn with two tool calls produces: streamed output, one message row, N usage
  rows, tool results recorded — all or nothing transactionally.
  → `test_scripted_turn_with_two_tool_calls_commits_message_and_usage_atomically`
- Provider failure → retry → fallback profile path covered by tests; tenant is never
  double-charged (idempotency assertion on the tool loop).
  → `test_provider_failure_retries_then_falls_back`, `test_all_profiles_exhausted_raises`,
    `test_retried_tool_dispatch_with_the_same_idempotency_key_does_not_reexecute`
- Token counts in `usage_record` match provider-reported usage (LiteLLM normalisation).
  → `test_usage_record_token_counts_match_provider_reported_usage` (against a deterministic
    test-double provider; see Design decisions — the real LiteLLM streaming accumulation
    path is implemented but not exercised live in this sandbox)

## Design decisions
- **`session_id` is mandatory, not `Optional`, on `run_agent_turn`.** `MessageRow.session_id`
  is a NOT NULL FK to `session.id`; an earlier draft tried to support session-less turns
  with a placeholder UUID, which would violate the FK constraint on commit. There is no
  real caller that needs a session-less turn today, so the seam was removed rather than
  worked around.
- **Idempotency wraps tool dispatch, not the provider call.** Retrying a *failed* provider
  call is what retry-with-backoff means — nothing to protect there. A tool call that
  already *succeeded* is a real side effect (dice rolls, entity mutations, future MCP
  calls) that must not re-run if the turn is retried/resumed after a crash, so only
  `_dispatch_tool_idempotent` is wrapped in `@idempotent`, keyed on
  `f"{idempotency_key}:tool:{tool_call.id}"`. Mirrors B1.2's own scoping decision one
  layer up.
- **Only the final answer becomes a `MessageRow`.** Intermediate tool-calling turns
  (assistant text alongside tool_calls, and the tool result messages fed back) live only
  in the in-memory `conversation` list for that one `run_agent_turn` call, not as separate
  rows — matching the plan's "one message per turn" framing; the full exchange is
  reconstructable from provider call logs/tracing if ever needed, not from `message`.
- **`ToolRegistry` ships empty.** No tools are hardcoded in `core.agents.tools` — C1.6
  (Resolution Service) is the first real caller that registers any. The runtime only ever
  depends on the registry's `specs()`/`dispatch()` interface.
- **LiteLLM tool-call streaming accumulation is implemented but unverified against a live
  provider.** `packages/adapters/models/litellm/provider.py` accumulates
  `delta.tool_calls` fragments by index per the standard OpenAI-compatible streaming
  format LiteLLM normalises every provider to, yielding a populated `Chunk.tool_calls`
  only on `finish_reason == "tool_calls"`. No Ollama/API credentials are available in this
  sandbox to exercise it live; the agent runtime's own test suite instead uses a
  deterministic `_ScriptedProvider` test double that implements the same `ModelProvider`
  protocol. Flagged honestly rather than silently assumed correct.
- **No new tenant-scoped table.** B1.7 only added columns to `agent`, `model_profile`, and
  `message` (all already tenant-scoped, already covered by existing RLS/isolation tests),
  so no new entry was needed in `tests/isolation/`.
