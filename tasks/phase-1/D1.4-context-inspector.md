# D1.4 — Context inspector ★

**Phase:** 1 · **Track:** D · **Est:** 5d · **Status:** done
**Depends on:** T0.9, C1.3 · **Blocks:** —
**Plan refs:** §15.4 ("a differentiator, not a debug tool"), §6.3, §6.5

## Goal
Per-message transparency: what was retrieved, which bucket, what rank, why, and what it
cost. No competitor can show a player why the GM ruled the way it did.

## Subtasks
- [x] Inspector panel per message (permission-checked via C1.3's access rules): entries
      grouped by class/bucket showing source, version, entry, rank, score, and the
      structured `why` (keyed/sticky/dense/constant…).
- [x] Budget visualisation: bucket sizes from the phase's ratio, fill levels, spill —
      **the Phase-1 exit gate demands a ratio change be visibly different here.**
- [x] Token spend summary per message (prompt/completion/cached from `usage_record`);
      session-level rollup view (the rough cost dashboard, §16.1).
- [x] Citations rendered as links resolving to the entry at the pinned version (C1.8);
      hallucinated-citation flags visible.
- [x] Redaction stubs listed (empty in Phase 1; the section exists for Phase 2).

## Acceptance criteria
- Side-by-side comparison of two turns under different budget ratios shows the composition
  difference (exit-gate evidence, demoable).
  → `SessionView`'s per-message "compare" checkbox selects up to two assistant messages;
    once two are picked, "Compare selected turns' context" renders two
    `ContextInspectorPanel`s side by side (`grid-cols-2`), each with its own independent
    budget-composition bar computed straight from that message's own manifest entries
    grouped by `bucket` (`entry.token_count` summed per bucket, no client-side
    recomputation of retrieval). Two manifests produced under different phase budget
    ratios necessarily show different bucket proportions here, since the bar widths are
    a direct function of what `assemble()` actually included.
- A participant sees only manifests they were the viewer for; facilitator per permission.
  → Server-enforced, not a UI convention: `GET /messages/{id}/manifest` (new) wraps C1.3's
    own `get_manifest_for_message`, which raises `ManifestAccessDeniedError` (rendered as
    403) for anyone who isn't the manifest's `viewer_principal_id` and lacks
    `read_any_manifest` on the workspace. `ContextInspectorPanel` treats a 403/404 as "not
    visible to you," never a silent empty panel. Proven by
    `test_a_bystander_without_read_any_manifest_is_denied` (403) and
    `test_a_facilitator_may_read_any_manifest_in_the_workspace` (200) in
    `api/tests/test_manifests_flow.py`.
- Citation click shows pinned-version text after the source has since changed.
  → Unchanged, real C1.8 behaviour: `GET /messages/{id}/citations` resolves each citation
    at its recorded `version_id`, never the source's current draft. The inspector renders
    `body_md` from that response directly (no separate "click to resolve" step needed,
    since the endpoint already returns pinned text) — the pinning itself is what
    `test_message_citations_endpoint_resolves_the_pinned_version` (C1.8, unmodified)
    proves; D1.4 only adds the hallucinated-citation surfacing on top (see below).

## Design decisions
- **Four small, genuinely necessary backend additions**, same bar as D1.1-D1.3's:
  - `GET /messages/{message_id}/manifest` (new `api/routes/manifests.py`) -- C1.3's
    `get_manifest_for_message` existed and was fully tested, but nothing at the API layer
    ever called it; this is the first real caller. Needed a `PermissionService` adapter
    at the composition root, which also didn't exist yet at the API layer -- added
    `api/permission_service_factory.py`, mirroring `model_provider_factory.py`'s exact
    pattern for the same reason (CLAUDE.md rule 12).
  - `message.moderation_flags.bad_citation` (C1.8, already written) was never exposed by
    `GET /messages/{id}/citations` -- the endpoint only ever returned resolved *valid*
    citations. Reshaped its response from a bare list to
    `{valid: [...], bad_citation_ids: [...]}` (a breaking change to an endpoint nothing
    in the frontend depended on yet, so safe) so "hallucinated-citation flags visible"
    has something real to read from. Covered by
    `test_message_citations_endpoint_surfaces_hallucinated_citation_ids`.
  - **Per-message token spend didn't exist at all** -- `usage_record` only ever carried
    `session_id`, not which specific reply a generation call belonged to, so "prompt/
    completion/cached from usage_record" per message was structurally impossible before
    this task. Added `usage_record.message_id` (nullable, `SET NULL` on delete, migration
    `9d1f4c6a2b87`), set at both call sites that write a `usage_record` for a reply
    (`core.process.skeleton.generate_agent_response`, `core.agents.runtime._commit_turn`
    -- a tool loop's intermediate calls and its final answer all share the one message
    they together produced), plus `core.audit.usage_dashboard.message_usage_summary` and
    `GET /messages/{id}/usage`. Covered by
    `test_message_usage_endpoint_reports_the_owning_messages_spend`, which specifically
    proves two different messages in the same session get two different, correctly
    discriminated totals (not just that the column exists).
  - No change needed for the budget-ratio-visible-difference criterion itself -- C1.2's
    `ManifestEntry.bucket`/`token_count` already carry everything the comparison bars
    need; this is a pure read, no new write path.
- **`why` is a string, not a structured object.** `ManifestEntry.why` (C1.2) is already a
  human-readable string (e.g. describing keyed/sticky/dense/constant activation) rather
  than a structured dict -- the inspector renders it verbatim rather than inventing a
  richer shape C1.2 never produced.
- **The comparison UI is two independent `ContextInspectorPanel`s side by side**, not a
  bespoke diff view -- each panel fetches and renders its own message's manifest/
  citations/usage completely independently (same component, same queries, same
  permission check), so there's no second code path to keep in sync with the single-
  message inspector, and the visual difference in the two budget bars *is* the
  comparison.
- **No interactive browser click-through was possible in this sandbox** (same limitation
  as D1.1-D1.3 -- no browser automation tool available). Verified instead: `tsc -b
  --noEmit` and `eslint .` both clean; `ContextInspectorPanel.tsx` and the modified
  `SessionView.tsx` both fetched directly from the Vite dev server return 200 with no
  syntax/transform error; and every API contract the panel calls
  (`/messages/{id}/manifest`, `/messages/{id}/citations`, `/messages/{id}/usage`) is
  fully exercised by the backend's own `TestClient`-based tests, including the
  permission-denial path. Flagged honestly rather than assumed working.
