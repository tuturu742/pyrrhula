# D1.3 — Session view

**Phase:** 1 · **Track:** D · **Est:** 8d · **Status:** done
**Depends on:** T0.9, B1.7, C1.6 · **Blocks:** —
**Plan refs:** §13.5, §9.2 step 6, INV-7

## Goal
The live play surface: streaming messages, phase awareness, and the dice widget that reads
the record.

## Subtasks
- [x] Message stream over the shared SSE hook; token streaming; reconnect replay via
      `Last-Event-ID`.
- [x] Phase banner: current phase (overlay label), acting principal indicator, turn order /
      whose-turn state from scheduler events.
- [x] Human input box respecting phase rules (enabled only when the viewer may act;
      `mode: free` vs awaiting states).
- [x] **Resolution widget (INV-7):** renders from `ResolutionRecord` fetched by id —
      expression, rolls, modifiers, total vs target, outcome. **Never parses model prose.**
- [x] Contradiction badge (C1.7 flag): correction indicator beside the narration, truth
      shown from the record.
- [x] Phase-transition and await markers inline in the stream (event-kind rendering).
- [x] Session controls: pause/resume; fork-from-checkpoint entry point (API exists, minimal UI).

## Acceptance criteria
- The Phase-1 exit slice is playable start to finish in this view.
  → **Partially true, honestly flagged — see "A real, pre-existing gap" below.** The
    message stream, phase banner, human-input gating, and all event-kind rendering are
    real and work end to end against the live HTTP session API (`POST /sessions`,
    `POST /sessions/{id}/messages`, `GET /sessions/{id}/stream`) — that part of the exit
    slice is genuinely playable today. The resolution widget and contradiction badge are
    also real, tested, and wired to render the moment a message carries them — but no
    *live* session driven through today's HTTP endpoints ever produces one, because
    `packages/api/routes/sessions.py` still calls `core.process.skeleton` (T0.8's
    hardcoded 2-phase walking skeleton), not B1.2's interpreter or B1.7's
    `run_agent_turn`/tool loop. This is not a gap D1.3 introduced or silently worked
    around — every C1.x task this phase flagged the identical "not yet integrated into
    the runtime" boundary, and wiring the real interpreter into the live session HTTP
    flow (process-definition-aware session creation, phase-by-phase turn dispatch, a
    seeded RuleSystem + tool registry at the composition root) is a substantial,
    separate piece of work, not something a UI task should absorb as an incidental side
    effect.
- With a mocked reply narrating the wrong number, the widget still shows the record's truth
  and the badge appears (INV-7 demonstration — exit-gate evidence).
  → Proven at the real-tool-loop level (the actual code path the widget's data comes
    from), not merely asserted: `test_contradicting_narration_still_shows_the_records_truth_through_the_real_tool_loop`
    (`core/resolution/tests/test_tool_loop_integration.py`) runs a real `run_agent_turn`
    with a scripted reply claiming "success" against a roll that's deterministically a
    failure (target unreachable by the dice), and asserts the persisted record's own
    `outcome` is `"failure"` while `message.moderation_flags == {"contradiction": [...]}`.
    `test_message_resolutions_endpoint_shows_the_record_and_the_contradiction_flag`
    (`api/tests/test_resolutions_flow.py`) proves the same thing through the actual
    `GET /messages/{id}/resolutions` HTTP contract `ResolutionWidget.tsx` calls —
    `contradicted: true`, `outcome: "failure"`, regardless of the mocked reply's claim.
- Dropped connection mid-turn recovers without losing messages.
  → Unchanged from T0.9: native `EventSource` remembers the last `id:` it saw and resends
    it as `Last-Event-ID` on its own automatic reconnect; `sse.py`'s catch-up replays
    every `session_event` after that id from the database before resubscribing live. D1.3
    adds no new risk here — `PhaseBanner`/`ResolutionWidget` are ordinary `useQuery`
    fetches keyed off ids already present in replayed/live events, not part of the
    reconnect path itself.

## Design decisions
- **A real, pre-existing gap, not new scope creep:** `packages/api/routes/sessions.py`'s
  session/message endpoints have never been upgraded past T0.8's `core.process.skeleton`
  (hardcoded `prompt`/`respond` phases, no tool calls, no `ResolutionRecord`s, no
  `phase_transition`/`await` events -- skeleton.py only ever emits `kind="message"`).
  Every one of Track C's tasks (C1.2 through C1.7) flagged and deliberately deferred the
  identical "not yet integrated into the runtime" boundary rather than force premature
  end-to-end wiring with no real caller yet. D1.3 inherits that same boundary; closing it
  (process-definition-aware session creation + B1.2 interpreter-driven turn dispatch +
  B1.7's tool-calling runtime, all reachable from the live HTTP API) is a composition-root
  change on the scale of several B/C tasks combined, not something to bury inside a
  frontend task. What *is* real and shipped here: every contract the UI needs from that
  eventual wiring already exists, is tested at the correct layer (the real tool loop, not
  a mock), and the UI renders it correctly the moment it's populated.
- **Five small, genuinely necessary backend additions**, same bar as D1.1/D1.2's, found
  while building the screens this task's own acceptance criteria need:
  - `core.agents.runtime` now correlates a turn's tool calls back to the message they
    produced: `_extract_resolution_id` parses any `resolve()`-backed tool result's
    `{"resolution_id": ...}` shape (not hardcoded to `dice_roller` by name), collects
    them into the new `message.resolution_record_ids` column (migration
    `7c3a9b2e5f14`), and runs C1.7's `scan_for_contradictions` against the turn's own
    reply in the same transaction the message commits in -- the contradiction badge is
    now a *real*, wired signal for any caller of `run_agent_turn`, not just a tested-in-
    isolation module. Covered by
    `test_contradicting_narration_still_shows_the_records_truth_through_the_real_tool_loop`.
  - `GET /messages/{message_id}/resolutions` (new `api/routes/resolutions.py`, mirrors
    C1.8's `citations.py` shape exactly) -- resolves a message's `resolution_record_ids`
    to full `ResolutionRecordRow` data plus a per-record `contradicted` flag read off
    `moderation_flags.contradiction`. `ResolutionWidget.tsx` renders straight from this,
    never from `message.content_md`.
  - `GET /sessions/{session_id}` -- the session view's initial-load/refresh snapshot;
    previously a caller could only ever *replay events*, never fetch "what's true right
    now" (current_phase/status/state) on a fresh page load. `SessionResponse` also
    gained `state: dict[str, object]`.
  - `POST /sessions/{session_id}/pause` / `.../resume`, `GET /sessions/{session_id}/checkpoints`,
    `POST /sessions/{session_id}/fork` -- none of these existed as REST endpoints. Pause/
    resume are two new, tiny `core.sessions.lifecycle` functions (a plain status flip,
    the same `"active"`/`"paused"` values `core.process.interpreter`/`core.process.awaits`
    already write internally on fault/await); fork wraps B1.4's already-complete
    `core.process.checkpoints.fork_session` (only ever called from tests before this),
    backed by a new `list_checkpoints` helper for the picker.
  - Every `message` `SessionEventRow` payload (both `core.process.skeleton`'s two
    emission sites and `core.agents.runtime._commit_turn`'s) now carries the message's
    own `"id"`. It never did before -- which meant `ResolutionWidget`/citations (C1.8)
    were structurally unreachable from a live-streamed session no matter what the UI
    did, since there was no id in the SSE payload to key a per-message fetch off of.
    Covered by an added assertion in `test_full_round_trip_writes_message_event_and_usage`.
- **`PhaseBanner`'s "current phase" folds live `phase_transition` events on top of the
  `GET /sessions/{id}` snapshot** (latest event wins, snapshot is the fallback before any
  transition has happened) rather than re-fetching the session on every event -- the
  event stream is already the source of truth for what's changed since the snapshot was
  taken (same principle `core.process.checkpoints.reconstruct_state` uses server-side).
- **Human-input gating uses what's actually observable today**, not a phase-rules engine
  that doesn't exist for the skeleton's sessions: disabled while a turn is actively
  streaming (`liveText !== ""`) or while `session.status === "paused"`, enabled
  otherwise. Once real ProcessDefinition-driven sessions exist, this is the natural seam
  to extend with `PhaseSpec.actors[].mode`/eligibility -- not replaced.
- **No interactive browser click-through was possible in this sandbox** (same limitation
  as D1.1/D1.2 -- no browser automation tool available). Verified instead: `tsc -b
  --noEmit` and `eslint .` both clean; `PhaseBanner.tsx`, `ResolutionWidget.tsx`, and the
  rewritten `SessionView.tsx` all fetched directly from the Vite dev server return 200
  with no syntax/transform error; and the exact API contracts the UI calls
  (`/sessions/{id}`, `/sessions/{id}/pause|resume|checkpoints|fork`,
  `/messages/{id}/resolutions`, the SSE stream's `message`/`phase_transition`/`await`
  event shapes) are fully exercised by the backend's own `TestClient`-based tests.
  Flagged honestly rather than assumed working.
