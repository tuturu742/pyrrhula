# B1.1 — ProcessDefinition DSL schema + validator

**Phase:** 1 · **Track:** B · **Est:** 5d · **Status:** done
**Depends on:** T0.3 · **Blocks:** B1.2, C1.1, D1.2
**Plan refs:** §5.2, §12.2 (D1)

## Goal
The declarative, versioned JSON DSL for Process Definitions, with static validation strict
enough that the interpreter can trust its input.

## Subtasks
- [x] Pydantic/JSON Schema model of the DSL per §5.2: `state` (typed session vars),
      `initial_phase`, `phases{}` with `label_key`, `actors[]` (agent_role/any_of; `mode:
      free|generate|generate_as`; `order: declared|initiative from entity_field|free`;
      `max_turns`), `visibility` (knowledge_classes, scopes, entity_fields, secrets),
      `budget` (ratio, max_tokens, spill), `gates[]` (`on:`/`when:` CEL/`else`), `effects[]`
      (`set` with CEL), `await` (type, timeout, on_timeout), `flags` (e.g. `mechanical`),
      `tools[]`, `on_complete`.
- [x] Static validation on save: initial phase exists; all transition targets exist; every
      phase reachable; no undeclared loops; **`visibility` block mandatory — a phase without
      one fails validation, no default**; budget ratios sum ≈ 1; actor roles known.
- [x] CEL compile check (`celpy`) for every expression at save time; errors mapped to
      field paths for the editor (D1.2 consumes these).
- [x] `process_definition` table (versioned JSONB, `validated_at`, `validation_errors`);
      publish = new immutable version.
- [x] CRUD + validate API endpoints; validation errors as structured JSON.
- [x] Ship the §5.2 "Standard Session Flow" example and a minimal 3-phase MVP definition
      (`arbiter_narrate → player_act → resolve` — core-neutral keys, RPG labels via overlay)
      as fixtures.

## Acceptance criteria
- [x] The §5.2 example round-trips: parse → validate → serialize identically.
  `test_standard_session_flow_round_trips_parse_validate_serialize`: parse -> dump -> re-
  parse -> re-dump reaches a fixed point. See design notes for why "round-trips" means
  fixed-point stability of this module's own canonical JSON form, not byte-identity with
  the plan's illustrative YAML (which isn't valid, re-parseable syntax to begin with).
- [x] Each validation rule has a failing fixture (missing visibility, unreachable phase, bad
  CEL, dangling transition) with a precise, field-addressed error.
  `test_validator.py`: all four named cases plus six more (dangling await target, unknown
  initial_phase, budget ratio sum, gates+on_complete both set, misplaced `else` gate),
  each asserting the exact `field_path`.
- [x] A definition that validates cannot make the interpreter throw on structural grounds
  (fuzz/property test over generated valid definitions).
  `test_property.py`: a Hypothesis strategy generates random reachable/cyclic phase graphs
  (200 examples/property), asserting every one both passes `validate_definition` with zero
  issues and satisfies the two structural guarantees B1.2's loop will lean on hardest —
  every transition target dereferences to a real phase, every present budget's ratios sum
  to 1.0. B1.2 doesn't exist yet so this can't literally run the interpreter; it proves the
  thing that actually determines whether one can trust its input.

## Design decisions

- **The plan's §5.2 YAML block is illustrative prose, not literal syntax.** It uses
  `-> target_phase` as informal transition shorthand, and a gate entry shaped like
  `{ on: actor_declares_action, -> action_phase }` isn't valid YAML/JSON at all (a mapping
  entry needs `key: value`; a bare `-> action_phase` isn't one). `schema.py` defines a
  concrete, unambiguous, actually re-parseable JSON shape carrying the *same semantic
  content* — transitions are always an explicit `to:` field. This is also why the round-
  trip acceptance criterion is checked as "parse -> dump -> re-parse -> re-dump is a fixed
  point," not "matches the plan's snippet byte-for-byte" — the latter isn't achievable
  because the snippet was never meant to be parsed as-is.
- **A real gap found by fuzz-testing against the plan's own example, not a generated one:**
  `action_phase`'s actor entry (`{ order: initiative, from: entity_field("initiative"),
  mode: generate }`) has *no* `agent_role`/`any_of`/`human_participant` selector at all —
  eligibility is implicit ("whoever has this entity field"). My first schema draft required
  exactly one selector always, which rejected the plan's own canonical example. Fixed:
  at most one selector may be set; if none is set, `order` must be `initiative` (initiative
  order is inherently its own selector). Documented in `ActorSpec._selector_shape`.
- **"No loops except declared ones" (§5.2) is not a separate validator rule.** The DSL has
  no implicit iteration construct — the only way a cycle can exist is an author's own
  `gates`/`on_complete`/`await.on_timeout` explicitly pointing back at an earlier phase,
  which is precisely what "declared" means. The plan's own example is itself cyclic
  (`open_discussion` <-> `action_phase` <-> `resolution`, `resolution` -> `feedback_loop`
  -> `open_discussion`) and must validate cleanly, so "reject cycles" would be a bug. What
  dangling-transition + reachability checking already guarantees (every edge in any cycle
  points at a real, reachable phase) is all "declared-ness" could mean structurally.
  Explained at length in `validator.py`'s module docstring rather than silently omitted.
- **CEL "compile check" is parse + one evaluation against a synthetic dummy state, not
  just parsing.** Empirically, celpy's `Environment.compile()` only catches *syntax*
  errors — a reference to an undeclared name (anything outside `state.<declared var>`
  plus CEL's own operators) parses fine and only fails at evaluation time. So
  `compile_check` evaluates the expression once against an activation built from the
  DSL's own declared `state:` block (a representative dummy value per declared type);
  an undeclared reference then surfaces as `CELEvalError`, treated identically to a
  syntax error. Documented limitation: this can't catch value-dependent runtime failures
  (e.g. a divide-by-zero that only fires for one specific state value) — out of scope for
  a static validator, backstopped by the interpreter's own fault handling (B1.2).
- **Two rules added beyond the subtask list, both because an ambiguity would otherwise
  reach the interpreter silently:** (1) a phase may declare `gates` or `on_complete`, not
  both — having both is an unresolvable "which one wins" question, not a feature; (2) an
  `else` gate must be the last gate in its list, since gates evaluate in declaration order
  with first-match-wins semantics and an early `else` makes everything after it dead code.
- **No draft/publish split at the DB layer, unlike A1.1's knowledge entries.**
  `create_definition` validates and rejects *before* touching the database — an invalid
  document is never persisted, so there is no mutable draft row to accidentally read; every
  row in `process_definition` is one the interpreter can trust by construction. "Publish"
  and "create a new version" are the same operation. In-progress edits before submission
  are the editor's (D1.2) problem, not this table's.
- **`UNIQUE(workspace_id, key, version)` (the plan's literal schema) doesn't actually
  enforce uniqueness for tenant-template rows.** Postgres treats every NULL as distinct in
  a unique constraint, so two different `workspace_id IS NULL` rows could share the same
  `key`/`version` without ever violating a bare constraint on that shape. Replaced with two
  partial unique indexes: one for workspace-scoped rows (the plan's literal constraint,
  `WHERE workspace_id IS NOT NULL`), one keyed on `tenant_id` instead for tenant-template
  rows (`WHERE workspace_id IS NULL`) — the only scope a NULL-workspace row actually has.
  Declared on the ORM model (`Index(..., postgresql_where=...)`, matching A1.1's exact
  fix for the same class of problem) so `alembic check` doesn't flag them as a spurious
  autogenerate diff.
- **`process_definition` is not marked append-only (‡).** Unlike `knowledge_source_
  version`, the plan's §12.2 schema block doesn't mark this table `‡`; "publish = new
  immutable version" is read as an application-level convention (the authoring layer
  always INSERTs, never UPDATEs), not a grant-level restriction — no `REVOKE UPDATE,
  DELETE` in the migration.
- **`hypothesis` added as a dev-only dependency** for the fuzz/property test the
  acceptance criteria explicitly ask for; not present in the codebase before this task.
  **`cel-python` (the `celpy` package) added as a real dependency** — listed in CLAUDE.md's
  stack section but never actually installed until now.
