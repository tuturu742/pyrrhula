# A1.1 — Knowledge schema

**Phase:** 1 · **Track:** A · **Est:** 4d · **Status:** done

## Goal
The four-level content model: Source → Version (immutable, content-addressed) → Entry (unit
of authorship, stable key) → Chunk (unit of retrieval, derived).

## Acceptance criteria
- [x] Creating a source, adding entries, and publishing produces an immutable version whose
  `content_hash` is reproducible from its entries. Verified both in `packages/core/
  knowledge/tests/test_authoring.py` and over real HTTP against the containerized stack
  (create source → add draft entry → publish → `content_hash` is a stable 64-hex sha256,
  reproducible from `list_version_entries`'s output).
- [x] Attaching the same source to two workspaces with different `priority_weight`/`scope_key`
  works — the workspace's opinion lives on the attachment row (reqs 3+4). Verified in
  `test_authoring.py` and `packages/api/tests/test_knowledge_flow.py`.
- [x] `tests/isolation/` covers all five tables; chunk queries without scope filter are
  impossible through the port (INV-4, verified fully in A1.4). All five tables added to
  `tests/isolation/test_knowledge_filter_omission.py` and `test_coverage_guard.py`'s
  `_COVERED_TABLES`; `test_rls_catalog.py`'s catalog scan (any table with a `tenant_id`
  column must have FORCE RLS) picks all five up automatically. `knowledge_chunk` itself has
  no query interface yet — A1.4 owns the actual scoped `VectorStore` wiring.

## Design decisions and scope boundary with A1.8

- **Draft vs. published, reconciled with the append-only constraint.** The plan's §12.3
  sketch implies `knowledge_entry.version_id` is `NOT NULL`, but CLAUDE.md's append-only
  rule means `knowledge_source_version` never gets an UPDATE once inserted — so a
  "mutable draft version" row that gets its `content_hash` filled in later isn't possible.
  Resolved by making `version_id` **nullable**: `NULL` = the current mutable draft (freely
  edited via `upsert_draft_entry`), non-`NULL` = an immutable snapshot. `publish_version`
  computes the final `content_hash` up front and INSERTs the version row once, fully
  formed, then copies the draft entries into new rows stamped with that version id —
  the original draft rows are left in place for the next edit round. Entry-key uniqueness
  is therefore two partial unique indexes (`WHERE version_id IS NOT NULL` /
  `WHERE version_id IS NULL`), declared as `Index(..., postgresql_where=...)` so
  autogenerate recognizes them, created via raw SQL in the migration (same as every other
  index here).
- **`knowledge_source_version` gained a `tenant_id` column** the plan's sketch doesn't
  show. CLAUDE.md rule 4 ("every tenant-scoped table gets tenant_id + RLS with FORCE") and
  `tests/isolation/test_rls_catalog.py`'s catalog-driven check (any table with a
  `tenant_id` column must have forced RLS) both assume a direct column, not a join through
  `knowledge_source`. Denormalising it keeps the RLS predicate join-free, consistent with
  every other child table in this schema (e.g. `identity.tenant_id`, T0.2).
- **`knowledge_source.current_version_id` has no FK at the SQLAlchemy declaration** in the
  usual sense — it's declared with `use_alter=True` on `ForeignKeyConstraint`, added via a
  separate `ALTER TABLE` in the migration after both tables exist, since `knowledge_source`
  and `knowledge_source_version` reference each other.
- **Overlap with A1.8 ("Versioning + diff"), flagged rather than silently resolved:** A1.1's
  own acceptance criterion requires "publishing" to exist and be testable, so this task
  implements the minimal `publish_version` (compute hash, INSERT version, copy entries,
  advance `current_version_id`). A1.8's subtask list also names "Publish flow" as its own
  first bullet — that overlap is real, not a copy-paste error, but split as: A1.1 owns the
  publish mechanism itself (needed to prove the schema/hash design), A1.8 owns entry-level
  diffing, fork-from-version, and — importantly — **pin-vs-follow resolution** (which
  version a workspace/session actually reads given `version_pin` vs. a source's
  `current_version_id`). That resolution logic does not exist yet; `version_pin` is just a
  stored column so far.
- **`core/knowledge/repo.py` vs. `core/knowledge/authoring.py`:** INV-1 (T0.5's
  import-graph lint) restricts `core.knowledge.repo` to `core.assembler`/`core.overseer`
  because it protects the "stored text reaches a model" path — not authoring/CRUD, which is
  a human editing their own tenant's content through the UI. `repo.py` therefore only gets
  the minimal read functions the future assembler needs (`get_current_version_id`,
  `list_published_entries`); all create/update/publish/attach logic lives in the freely
  importable `authoring.py`, which `api/routes/knowledge.py` calls directly.

## Bugs found and fixed along the way
- Two of my own new indexes and the circular FK initially showed up as spurious
  `alembic check` diffs (declared only in raw SQL, not on the ORM model) — the same
  category of bug T0.3/T0.7/T0.8 hit. Fixed by declaring both partial unique indexes and
  the `use_alter` FK on the ORM model too, matching the physical migration DDL. (Ran
  `alembic check` and found the *pre-existing* T0.8 gap — `message`/`session_event`/
  `usage_record` indexes were never declared on those ORM models — left alone: not
  something this task touched, and not CI-blocking since CI doesn't run `alembic check`.)
- `priority_weight` is `Numeric` on the ORM model but the port-level function signature
  takes a plain `float` for caller convenience; mypy caught the implicit float→Decimal
  assignment. Fixed with an explicit `Decimal(str(priority_weight))` at the boundary.
