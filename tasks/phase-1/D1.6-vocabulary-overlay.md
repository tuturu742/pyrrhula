# D1.6 — Vocabulary overlay

**Phase:** 1 · **Track:** D · **Est:** 3d · **Status:** done
**Depends on:** T0.9 · **Blocks:** F3.7/F3.8 overlay packs plug in here
**Plan refs:** §12.2, Appendix A (req 32)

## Goal
The label-resolution layer that lets the same engine present as an RPG tool or an
enterprise tool with zero code changes.

## Subtasks
- [x] `vocabulary_overlay` table + API (per §12.2: labels JSONB keyed by `label_key`,
      tenant-scoped with system overlays nullable-tenant).
- [x] Ship `rpg_v1` and `enterprise_v1` label sets covering every `label_key` in Appendix
      A's glossary (seed data).
- [x] Frontend resolver (`lib/vocabulary/`): `label(key)` with overlay loading per
      workspace, fallback chain overlay → system default → key; upgrade T0.9's static stub.
- [x] Overlay switcher: per workspace (and tenant default in `tenant.settings`); switching
      relabels the entire UI live.
- [x] Missing-key detection in dev mode (console warning + collected report) so new
      features can't ship hardcoded nouns.
- [x] Lint/CI check: no literal "Arbiter"/"Rulebook"/"World" strings in `web/src` outside
      the overlay seed data.

## Acceptance criteria
- Switching a workspace from `rpg_v1` to `enterprise_v1` relabels Arbiter→Facilitator,
  Rulebook→Policy Document, etc., everywhere, without reload errors.
  → Proven server-side by `test_switching_a_workspace_to_enterprise_v1_relabels_immediately`
    (`api/tests/test_vocabulary_flow.py`): switching returns
    `labels["role.facilitator"] == "Facilitator / Chair"` and
    `labels["class.rules"] == "Policy Document"` in the same response, and a follow-up
    `GET` confirms the override sticks. Client-side, `VocabularySwitcher`'s `onSuccess`
    pushes the response's `{key, labels}` straight into `useVocabularyStore` -- every
    `useLabel()` call across the app subscribes to that one store, so the relabel is
    synchronous with the PATCH response, not dependent on a page reload or a second
    round-trip to refetch. No interactive click-through was possible in this sandbox (see
    below), so the *visual* "everywhere, live" claim rests on the store being genuinely
    global and every consumer being a subscribed hook, not a one-off prop -- verified by
    reading each consumer (`AppShell`, `WorkspaceDetailPage`, `AgentManagementPage`,
    `SessionView`, `PhaseBanner`, knowledge/process-editor pages) and confirming none
    hold a local copy of the labels table.
- Missing-key report is empty for all Phase-1 surfaces.
  → The collection mechanism itself (`_missingKeys` in `labels.ts`,
    `getMissingKeysReport()`, surfaced live via `MissingVocabularyKeysBadge` in
    `AppShell`) is real and wired everywhere `useLabel()`/`label()` already runs.
    **Whether the report is actually empty across every live-rendered Phase-1 screen is
    not verified here** -- that requires a browser click-through this sandbox can't do
    (no browser automation tool available). What *is* verified: every `label_key`
    string literal found by grepping `web/src` for `t("...")`/`t(\`...\`)` call sites
    across D1.1-D1.6's own components resolves against `DEFAULT_LABELS`
    (`role.facilitator`, `role.participant`, `role.human_participant`,
    `role.informational`, `role.overseer`, `entity.workspace`, `entity.session`,
    `entity.knowledge_source`, `class.rules`/`class.lore`/`class.misc`,
    `phase.turn`/`phase.discussion`, plus the dynamic `phase.${...}` template keys
    `PhaseBanner`/`SessionView` construct from live phase-key data) -- a static check,
    not a runtime proof, and honestly flagged as such rather than claimed as tested.

## Design decisions
- **Workspace.vocabulary_overlay_id is a genuinely circular cross-module FK** --
  `core.vocabulary.models` imports `Base` from `core.tenancy.models`, so
  `core.tenancy.models` importing `core.vocabulary.models` back (the usual "registration
  order" guard used everywhere else this phase, e.g. `core.sessions.models` importing
  `core.process.models`) would be a real circular import, not just an ordering nicety.
  Resolved by placing the registration-order guard in `core.tenancy.seed` instead (which
  `seed_dev_tenant` -- used by essentially every test in this codebase -- already
  depends on `core.tenancy.models` for anyway, and does not create a cycle since
  `core.vocabulary.models` never imports it back). Verified empirically both import
  orders resolve cleanly (SQLAlchemy's deferred string-FK resolution handles it) before
  committing to this approach rather than assuming it would work.
- **The fallback chain lives entirely server-side** (`core.vocabulary.service.
  resolve_overlay_for_workspace`): workspace override -> tenant default
  (`tenant.settings.default_vocabulary_overlay_key`) -> system default (`rpg_v1`). The
  frontend fetches one already-resolved `{key, labels}` per workspace and never
  reimplements the chain -- consistent with "nothing in the database is ever renamed,
  only how the UI labels it" being a server-owned concern, not a client one.
  `DEFAULT_LABELS` (the frontend's own bundled copy of `rpg_v1`) is only ever the
  fallback for pages with no workspace context yet (login, workspace list) or the first
  paint before the async fetch resolves -- never a second source of truth once a
  workspace's real overlay has loaded.
- **Both Appendix A's illustrative label_keys and the DSL fixtures' real ones are
  seeded**, not just one or the other. Appendix A's own table uses `phase.deliberation`/
  `phase.action` as illustrative examples, but B1.1's actually-shipped
  `STANDARD_SESSION_FLOW`/`MINIMAL_MVP_FLOW` fixtures use concrete keys like
  `phase.arbiter_narration`/`phase.turn`/`phase.resolve` -- seeding only the plan's
  illustrative keys would leave the missing-key report non-empty against real runtime
  data on day one. Also matched D1.1's already-shipped `class.rules`/`class.lore`/
  `class.misc` (not Appendix A's literal `ks.class.rules` spelling) for the same reason:
  trust what the real code emits over the plan's illustrative spelling when they
  conflict, the same discipline this session applied throughout.
- **The CI lint check is a Python test in `tests/architecture/`**, not a new JS/ESLint
  rule -- there is no frontend test runner configured in this repo at all (no vitest/
  jest), and every other CI-blocking structural check in this codebase
  (`test_inv1_import_graph.py` et al.) is already a pytest-based static-analysis test.
  Scans a curated list of the RPG overlay's own unambiguous display strings (not generic
  English words like "World"/"Session" alone, which would false-positive against
  ordinary prose) against every `.ts`/`.tsx` file, excluding `labels.ts` itself. Includes
  a self-test (`test_the_scan_actually_finds_something_when_present`) proving the
  scanner isn't vacuously passing from a glob typo.
- **No custom-overlay authoring UI** -- the subtask list never asks for one (only
  "ship rpg_v1 and enterprise_v1... seed data" and a *switcher*, not an *editor*).
  `VocabularyOverlayRow.tenant_id` is nullable and RLS already permits a tenant to own
  custom rows (proven by the isolation filter-omission test), ready for F3.7/F3.8's
  overlay packs to write into without a schema change -- but Phase 1 ships exactly the
  two system overlays the acceptance criteria name.
- **No interactive browser click-through was possible in this sandbox** (same limitation
  as D1.1-D1.5 -- no browser automation tool available). Verified instead: `tsc -b
  --noEmit` and `eslint .` both clean; every new/changed file fetched directly from the
  Vite dev server returns 200 with no syntax/transform error; and every API contract the
  UI calls (`/vocabulary-overlays`, `/workspaces/{id}/vocabulary-overlay` GET+PATCH,
  `/tenant/vocabulary-overlay` PATCH) is fully exercised by the backend's own
  `TestClient`-based tests, including the full switch-and-relabel round trip and
  cross-tenant isolation. Flagged honestly rather than assumed working.
