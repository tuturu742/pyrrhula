# A1.8 — Versioning + diff

**Phase:** 1 · **Track:** A · **Est:** 4d · **Status:** done
**Depends on:** A1.1 · **Blocks:** A1.10, D1.1, F3.12
**Plan refs:** §6.1, §5.4 (req 5)

## Goal
Entry-level version history, diffing, pin-vs-follow semantics, and fork-from-version — how
rules iterate without breaking active sessions.

## Subtasks
- [x] Publish flow: draft entries → immutable `knowledge_source_version` (content-addressed,
      `parent_version_id` set); `current_version_id` advanced. (Already built in A1.1,
      which needed a minimal publish to make its own acceptance criteria testable — see
      A1.1's task file. This task extends it: `parent_version_override` for fork
      provenance, plus the new `delete_draft_entry` needed to make "removed" reachable at
      all — see design notes.)
- [x] Entry-level diff between any two versions using stable `entry_key`: added / removed /
      changed (changed = same key, different content hash); API endpoint returning the
      3-way set with per-entry text diffs.
- [x] Pin vs follow: `workspace_knowledge_attachment.version_pin` (NULL = follow latest);
      retrieval resolves the effective version per workspace; active sessions pin the
      version they started with unless the workspace opts into `follow_latest`.
- [x] Fork-from-version: create a new source (same tenant) rooted at any version, copying
      entries; provenance recorded (`parent_version_id` across the fork).
- [x] Re-embedding on publish delegated to the content-hash-skip path (A1.2/A1.3) —
      unchanged entries keep vectors. (Structural, not new code: fork copies *entries*
      only, not chunks; a forked entry with identical content reproduces the identical
      chunk `content_hash` the moment anything re-derives its chunks, so A1.3's
      cache-by-content-hash mechanism reuses the embedding for free.)

## Acceptance criteria
- [x] Editing a source while a session runs does not change that session's retrieval
  (pin test). Scoped to what the schema actually has: `workspace_knowledge_attachment.
  version_pin` (workspace-level, not a separate per-session field — see design note).
  `test_editing_a_source_after_pinning_does_not_change_the_resolved_version`: pins to v1,
  republishes 3 more times, confirms `resolve_effective_version_id` still returns v1
  throughout.
- [x] Diff of v3→v5 on a seeded source returns the exact expected added/removed/changed
  sets. `test_diff_across_several_versions_returns_exact_expected_sets` seeds a source
  through two publishes with an added, a removed, and a changed entry in the same diff,
  and asserts the exact three sets.
- [x] Fork produces an independent, editable copy whose provenance chain is queryable.
  `test_fork_copies_entries_and_publishes_with_provenance` confirms the fork's first
  version's `parent_version_id` points at the *origin's* version (a cross-source
  provenance link — schema-legal since that FK only targets a version id, not a specific
  source). `test_fork_is_independently_editable_without_touching_the_origin` edits only
  the fork and confirms the origin's published entries are untouched.

## Design decisions

- **A real gap found while writing the diff tests: there was no way to remove a draft
  entry.** `core.knowledge.authoring` only had create/update (`upsert_draft_entry`) —
  nothing could ever make an entry disappear between versions, which meant "removed" was
  an acceptance criterion this task couldn't actually reach. Added
  `delete_draft_entry(tenant_id, knowledge_source_id, entry_key)` — deletes only the draft
  row (`version_id IS NULL`); a published entry is never touched (nothing this function
  does can select a non-NULL `version_id` row).
- **Per-entry content hash isn't a stored column** (only the whole-version hash and each
  chunk's hash are, per A1.1's schema) — `diff.py` computes it on the fly, reusing
  `core.knowledge.hashing.entry_content_payload`, the exact same shape the version-level
  hash is built from. "Changed" means precisely what the version's own content-addressing
  already means.
- **Pin-vs-follow resolves at the workspace level, not per-session** — that's the
  granularity `workspace_knowledge_attachment.version_pin` actually has (A1.1's schema);
  no session object has a "which version did I start with" field, because B1.4's
  session/checkpoint model (which would own that) doesn't exist yet. The plan's "an active
  session pins the version it started with" is achieved *today* by a workspace operator
  setting `version_pin` before a session starts; true independent per-session pinning
  (two concurrent sessions in the same workspace pinned to different versions) would need
  a schema addition once B1.4 exists — flagged, not silently assumed solved.
- **`publish_version` (A1.1) gained `parent_version_override`** — a fresh fork's first
  publish needs its `parent_version_id` to point at the *origin's* version being forked
  from, not `None` (a brand-new source's own `current_version_id`, which doesn't exist
  yet). Small, backward-compatible extension (defaults preserve A1.1's original
  behaviour).
- **Fork copies entries, not chunks.** "An independent, editable copy" only requires
  entries; chunking a source is ingestion's job (A1.2), not forking's. This is also *why*
  content-hash-skip applies automatically — a forked entry re-chunked later reproduces
  identical chunk text, hence identical `content_hash`, hence A1.3's cache reuses the
  origin's embedding without a real inference call.
