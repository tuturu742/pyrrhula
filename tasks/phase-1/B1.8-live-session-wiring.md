# B1.8 — Wire the real interpreter + agent runtime into the live HTTP session flow

**Phase:** 1 · **Track:** B · **Est:** — (found during Phase 1 exit-gate audit) · **Status:** done
**Depends on:** B1.1, B1.2, B1.3, B1.4, B1.6, B1.7, C1.2, C1.5, C1.6 · **Blocks:** Phase 2
**Plan refs:** §5, §9, §15.2, §15.4; `tasks/phase-1/EXIT-GATE.md` item 1

## Goal

Every engine piece (interpreter, scheduler, checkpoints, awaits, tool-calling agent
runtime, budget-aware context assembler, rule system + resolution service) is complete
and individually tested — but `packages/api/routes/sessions.py` still runs only T0.8's
hardcoded two-phase walking skeleton. No task file owned wiring them together; this one
does. Additive only: the existing skeleton path (no `process_definition_id` supplied at
session creation) is untouched.

## Subtasks

- [x] `core.agents.runtime.run_agent_turn`/`_commit_turn`: optional `event_seq`
      override so an external caller (the interpreter) can be the sole allocator of the
      event-log slot a turn claims.
- [x] `core.process.interpreter`: `InterpreterContext.event_seq`, widened
      `ActorTurnResult` (`already_persisted`, `message_id`), `HumanTurnPendingError` +
      `'awaiting_human'` status for free-mode human actors with no `await` block,
      `OnEvent`-threaded live SSE publishing (`advance_session`/`_transition`/
      `_run_actor_turn`), `submit_human_turn`.
- [x] `core.process.awaits`: `on_event` on `satisfy_await`/`resolve_timeout`.
- [x] `core.actions.idempotency.clear_failed_operation` + `resume_session` wiring, so a
      transient provider failure inside a turn doesn't permanently stall a session.
- [x] `core.resolution.rule_system.get_or_create_default_rule_system` (one tenant-wide
      default `RuleSystemDefinition` — no per-ProcessDefinition link needed yet).
- [x] `core.agents.scheduling.make_agent_candidate_resolver` — the real
      `agent_role`-based candidate resolver `core.process.scheduler`'s own
      `agent_candidate_resolver` seam has been waiting for since B1.3.
- [x] `core.process.live_session.run_process_definition_session` — the composition-root
      glue: builds `next_actor_fn`/`execute_turn`/`checkpoint_hook`/`on_await` and calls
      `advance_session`. `execute_turn` assembles context via `ContextAssembler.
      assemble()` (this is what makes a budget-ratio change visible in a live session),

      for a `mode: free` actor).
- [x] `packages/api/routes/sessions.py`: `CreateSessionRequest.process_definition_id`
      (optional); when set, starts and drives the session through the real interpreter
      instead of the skeleton. New `POST /sessions/{id}/await/satisfy`.

## Acceptance criteria (= `EXIT-GATE.md` item 1's own wording)

- The §15.2 slice runs end to end: one tenant, one workspace, one Arbiter agent, one
  human player; a 3-phase ProcessDefinition (shape: `arbiter_narrate → player_act →
  resolve`) runs through real phase transitions, a real human turn, and a real agent
  turn, proven by a real, non-stubbed `advance_session`/`run_agent_turn` call chain, not
  a direct-call-only test.
- Changing a budget ratio between two runs of the same phase produces a different
  `ContextManifest` composition (already proven at the retrieval layer by A1.6/D1.4;
  this task's job is only that a *live* turn actually calls `assemble()` with the
  phase's real `budget.ratio`, not a hardcoded one).
- `dice_roller`, reached through a live turn's tool loop (not a direct `resolve()`
  call), still writes a real `ResolutionRecord` and rejects a false modifier.

## Design decisions

- **`execute_turn` and `run_agent_turn`'s commit are reconciled via an injectable
  `event_seq`, not two independent claimers.** `_run_actor_turn` peeks the slot before
  calling `execute_turn`; the adapter passes that same value into
  `run_agent_turn(event_seq=...)`, which claims it in its own `_commit_turn` transaction
  and returns `ActorTurnResult(already_persisted=True, message_id=...)`.
  `_run_actor_turn` then skips its own write and instead asserts the slot was actually
  claimed (`next_event_seq == event_seq + 1`) -- a sanity check, not blind trust. This
  was the plan's own alternative-considered-and-rejected: reimplementing the tool loop
  inline inside `execute_turn` would have duplicated B1.7's already-tested retry/
  fallback/usage-metering logic for no reason.
- **Live SSE delivery is a threaded `on_event` hook (4 call sites: `_transition`,
  `_run_actor_turn`, `satisfy_await`, `resolve_timeout`), not a poll-after-`advance_
  session` wrapper.** `advance_session` can run many steps per call (an agent turn, a
  transition, another agent turn...) -- polling only after the whole call returns would
  mean nothing reaches a connected client until the *entire* multi-step advance
  finishes, which is a real loss of live streaming for exactly the multi-actor scenario
  this system exists for, not just a narrow reconnect-race edge case.
- **A free-mode human actor with no `await` block (`MINIMAL_MVP_FLOW`'s own
  `player_act` phase -- the exit gate's own named slice) needed a new mechanism**:
  `execute_turn` raises `HumanTurnPendingError` for `mode in ("free", "generate_as")`;
  `advance_session` catches it and returns `'awaiting_human'` without pausing/faulting.
  This only works because `core.process.scheduler.make_scheduler`'s `next_actor`
  persists the advanced cursor as a side effect of being *called*, before
  `_run_actor_turn` does anything with the result -- so the human's slot in the
  rotation is already durably consumed by the time the exception propagates, and a
  later `submit_human_turn` + re-`advance_session` resumes correctly without re-
  offering or skipping the turn. Verified, not assumed: `test_live_session.py` drives
  two full rounds through exactly this mechanism.
- **Idempotency-failure recovery is a narrow escape hatch
  (`clear_failed_operation`), not a redesign.** `@idempotent` marks a key permanently
  `"failed"` on any exception -- fine for a genuine duplicate-side-effect guard, a real
  problem once the wrapped operation (a full multi-provider-retry tool loop, reached
  through the interpreter's own turn-execution key) can fail *transiently*.
  `resume_session` now clears the failed record for the session's current turn before
  flipping status back to active, so a transient-failure pause can actually be retried.
  `execute_turn` also translates `AllRetriesExhaustedError`/`ToolLoopExceededError`
  into `InterpreterFaultError`, restoring `advance_session`'s "never a stuck lock"
  guarantee for this case (neither exception is naturally an `InterpreterFaultError`).
- **One tenant-wide default `RuleSystemDefinition`, not a per-ProcessDefinition link.**
  No such link exists in the schema, and the exit gate's slice doesn't need more than
  one rule system. `get_or_create_default_rule_system` is a named call to
  `create_rule_system`'s own already-idempotent upsert -- calling it once per live turn
  never creates a second row or drifts an existing one.
- **`actor_fields_resolver` stays a fixed-dict stub** (no Entity system exists anywhere
  in Phase 1 -- F3.6 is Phase 3), matching every existing C1.6 test's own stub. This is
  the one sub-claim of EXIT-GATE.md item 3 ("the entity's actual STR") that remains a
  documented, honest limitation rather than a real per-character read.
- **Session creation auto-kicks the first advance.** A process-definition-backed
  session's initial phase might not need human input at all (`arbiter_narrate` is
  agent-only) -- the interpreter, not a human message, decides who goes first, so
  `create_session_endpoint` schedules the first `run_process_definition_session`
  background task itself rather than leaving the session idle until a client happens
  to `POST` a message.
- **No frontend changes.** D1.3's `SessionView`/`PhaseBanner` already render
  `message`/`phase_transition`/`await` events generically (built against the real
  event-kind shapes the interpreter/awaits modules emit, per those tasks' own design);
  nothing about this wiring changes those shapes. The exit-gate proof is at the
  engine/HTTP-contract level (per `EXIT-GATE.md`'s own "each with a test", not
  necessarily a browser demo), consistent with D1.1-D1.6's own no-browser-automation
  limitation, unchanged by this task.
