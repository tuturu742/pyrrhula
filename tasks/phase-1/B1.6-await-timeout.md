# B1.6 — Await + timeout

**Phase:** 1 · **Track:** B · **Est:** 3d · **Status:** done
**Depends on:** B1.4 · **Blocks:** G4.3, H5.9
**Plan refs:** §5.2 `await`, §12.7 `await_state`

## Goal
The interrupt primitive: a phase can suspend for human input (or an external result) with a
timeout transition — the mechanism behind play-by-post pacing and, later, enterprise
approval gates.

## Subtasks
- [x] `await_state` rows per §12.7: kind, `expected_from`, `timeout_at`,
      `on_timeout_phase`, `satisfied_at`; session `status='awaiting'`. `tenant_id` added
      beyond the plan's literal (gap-y) snippet — see design notes; `outcome` added too,
      needed for the atomic race-resolution the acceptance criteria requires.
- [x] Engine yields when a phase's `await` is unsatisfied; persists and returns (no held
      resources). New `OnAwaitHook` seam on `advance_session` (mirrors `CheckpointHook`'s
      exact pattern); `None` (default) preserves B1.2's original plain-status-flip
      behaviour exactly, so no existing test broke.
- [x] Satisfaction: matching input event (from an expected principal) marks satisfied and
      re-enqueues the session for advancing. `satisfy_await` — see design notes for why it
      performs a full phase transition (not just a status flip) and what "matching...
      expected principal" is and isn't scoped to cover yet.
- [x] Timeout job (worker, via `JobQueue`): fire `on_timeout` transition when `timeout_at`
      passes; idempotent (a satisfied await never times out — race handled transactionally).
      Not a `JobQueue` handler — a dedicated periodic sweep (`packages/worker/timeouts.py`)
      — see design notes for why cross-tenant reach couldn't go through `JobQueue` as
      literally specified.
- [x] Timeouts expressed in the DSL (`timeout: 72h`) parsed and validated in B1.1.
      Already true — `AwaitSpec.timeout`/`parse_duration_seconds` shipped with B1.1;
      reused here unmodified.

## Acceptance criteria
- [x] A `feedback_loop`-style phase suspends, resumes on human input, and takes the timeout
  transition when input never arrives (time-warped test).
  `test_feedback_loop_suspends_and_creates_a_real_await_state_row` (suspend),
  `test_satisfying_the_await_resumes_the_session_and_leaves_the_awaiting_phase` (resume via
  `satisfy_await`, lands on `feedback_loop`'s real `on_complete` target),
  `test_timeout_takes_the_on_timeout_transition_when_input_never_arrives` (time-warped: an
  already-past `timeout_at` set directly rather than sleeping 72h — `resolve_timeout`
  doesn't care how the row got that way, only that `timeout_at < now()`, matching exactly
  what the real worker sweep checks).
- [x] Satisfy-vs-timeout race: exactly one outcome wins, deterministically (transactional
  test). `test_satisfy_vs_timeout_race_exactly_one_outcome_wins` and
  `test_timeout_vs_satisfy_race_the_other_direction` (both orderings): whichever call's
  atomic `UPDATE ... WHERE outcome IS NULL` executes first wins; the other's UPDATE affects
  zero rows and returns `False`/`None` rather than raising or corrupting the row.
- [x] An awaiting session holds no locks and no worker slots.
  `test_an_awaiting_session_holds_no_locks`: a concurrent plain read of the session row
  immediately after `create_await` succeeds without hanging (would block/time out if
  `create_await` left a transaction open). `test_an_awaiting_session_occupies_no_worker_slot`:
  confirms zero `job` rows exist for the tenant after `create_await` — nothing enqueues a
  job to "hold a slot" for the wait; the timeout sweep discovers due awaits by scanning
  `timeout_at`, not by a worker sitting on a claimed job for up to 72h.

## Design decisions

- **`tenant_id` added to `await_state`, beyond the plan's own literal §12.7 snippet.**
  The plan's schema block for `await_state` omits `tenant_id` — every neighbouring table
  in that same section (e.g. `resolution_record`, right below it) has one. Treated as a
  documentation gap, not a deliberate exception: CLAUDE.md's tenancy rule is unconditional,
  and its no-RLS allowlist is a closed, three-table list (`tenant`, `role_permission`,
  `job`) with `job`'s exception specifically justified by cross-tenant worker polling —
  `await_state` has no comparable justification. Matches the same reasoning already applied
  to A1.10's `UNIQUE(workspace_id, key, version)` and B1.1's `process_definition` unique
  constraint: the plan's literal schema loses to CLAUDE.md's hard rule when they conflict.
- **The cross-tenant timeout sweep does not extend the no-RLS allowlist and does not go
  through `JobQueue`.** The natural first instinct — reuse `JobQueue` (already cross-tenant-
  safe by design) to schedule timeout jobs — doesn't work as-is: `JobQueue.enqueue()`/
  `claim_one()` has no delay/scheduled-for concept (checked the actual adapter schema, not
  assumed), so a job enqueued at await-creation time would be claimed and executed
  immediately, not 72 hours later. Making `await_state` itself RLS-exempt (like `job`) was
  the other option, rejected because CLAUDE.md's allowlist is a closed, specifically-named
  three-table list, not something to casually extend per-task. Instead,
  `sweep_expired_awaits` reads the tenant list from `unscoped_session()` (`tenant` is
  already one of the three legitimate exceptions) and scopes its actual `await_state` query
  per-tenant via `tenant_scope(tenant_id)` — O(tenants) queries per sweep tick, fully
  RLS-respecting throughout, at a scaling cost that's a documented, deliberate trade-off for
  a per-tenant SaaS system (not planet-scale), not a hidden one.
- **A real design gap found by reasoning through the "resumes on human input" acceptance
  criterion carefully, not by a failing test:** an early version of `satisfy_await` only
  flipped `session.status` back to `'active'` without moving `current_phase` anywhere. The
  next `advance_session` call on that session would re-read the *same* awaiting phase, see
  the same exhausted actors, and re-enter the *same* await — creating a duplicate
  `await_state` row with no memory that the first one was ever satisfied. Fixed by making
  `satisfy_await` perform the *same* transition the interpreter would have performed had
  actors exhausted normally (`apply_effects` + `evaluate_gates`, using the phase's own
  `on_complete`/`gates` — both promoted from `interpreter.py` private helpers to public
  functions for this reuse) — mirroring `resolve_timeout`'s existing direct jump to
  `on_timeout_phase`. Both outcomes are now symmetric, self-contained phase advances that
  never require the interpreter to revisit the awaiting phase at all. The asymmetry that
  *does* remain (satisfy evaluates gates; timeout takes a fixed bypass target) is
  deliberate, not an oversight — documented at length in both functions' docstrings.
- **`expected_from` is a descriptive record, not an authorization check, flagged
  explicitly.** `AwaitSpec` (B1.1) has no "who satisfies this" field of its own — it's
  derived from the phase's actor specs at await-creation time, for audit/UI purposes only.
  `satisfy_await` does not verify the calling principal is actually one of them; that
  enforcement belongs at the HTTP layer (the same workspace-membership check B1.3's
  scheduler already does for eligibility), which doesn't exist yet for this interpreter
  (still `core.process.skeleton`'s job today, per B1.2's own documented boundary). Noted so
  a caller wiring the real endpoint doesn't assume this module already handles it.
