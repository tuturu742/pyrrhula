# C1.6 — ResolutionService ★ (critical path)

**Phase:** 1 · **Track:** C · **Est:** 5d · **Status:** done
**Depends on:** C1.5 · **Blocks:** C1.7, D1.3, G4.13
**Plan refs:** §9.1, §9.2 (D5), §12.7, INV-7

## Goal
The trust chain for mechanical results: request → validate → seeded execute → immutable
record → system-authored fact. The model never reports a result; the database does.

## Subtasks
- [x] `ToolDefinition` registry (§9.1): `key`, `kind: deterministic|effectful`,
      input/output JSON Schemas, `impl_ref`, `validation_ref`, `determinism`. Register
      once — internal function-calling now; the MCP façade (G4.13) reuses the registry.
- [x] Request handling from the agent tool loop (B1.7): parse `{expression, against, actor,
      reason}`; **validate via C1.5 against actual entity state** — invalid returns a
      structured error to the model, never a silent fix-up.
- [x] Seeded execution: `seed = HMAC(session_secret, session_id || event_seq || expression)`;
      CSPRNG from seed; per-session secret stored server-side, revealable post-session for
      player verification.
- [x] `resolution_record` (append-only, per §12.7) with `prev_hash`/`row_hash` chain per
      session; written in the same transaction as the tool result.
- [x] **System-authored fact injection:** result enters context as
      `<resolution id=".." authoritative="true">…</resolution>` with the "narrate, don't
      contradict or restate the number" instruction; `manifest.resolution_ids` updated.
- [x] Replay: same seed + expression → identical rolls (INV-10 contribution).
- [x] Idempotency: retried tool calls (same idempotency key) return the stored record —
      never re-roll.

## Acceptance criteria
- A model asserting a false modifier is rejected (integration test through the tool loop —
  Phase-1 exit gate).
  → `test_model_claiming_a_false_modifier_is_rejected_through_the_real_tool_loop`
  (real `run_agent_turn()`, real `ToolRegistry`, real `dice_roller` handler)
- Seed disclosure reproduces the recorded rolls exactly (verification test).
  → `test_seed_disclosure_reproduces_the_recorded_rolls_exactly`
- Hash chain verifier detects a tampered record (superuser tamper test).
  → `test_hash_chain_verifier_detects_a_tampered_record` (admin-role UPDATE, mirroring
    `test_service_and_verify.py`'s identical pattern for `audit_log`)
- Retry storm produces exactly one record per logical roll.
  → `test_retry_storm_produces_exactly_one_record_per_logical_roll` (10 concurrent
    `asyncio.gather()`'d calls to `resolve()` with the same `event_seq`)

## Design decisions
- **Idempotency is layered, not singular.** B1.7's `_dispatch_tool_idempotent` already
  guarantees a retried tool call never re-runs the wrapped handler at all -- so through
  the real tool loop, `resolve()` is never even called a second time on retry.
  `resolve()` carries its *own*, independent guarantee too (an advisory lock +
  existing-row check keyed on `(session_id, event_seq)`) -- defense in depth, and the
  only guarantee that exists for a caller reaching `resolve()` some other way (the future
  MCP façade, G4.13, won't go through B1.7's tool loop at all).
- **Hash chain reuses `core.audit.hashing`'s `compute_row_hash`/`canonical_json`
  directly** (the same primitive `audit_log` uses), chained *per session*
  (`session_id`, ordered by `event_seq`) rather than per tenant like `audit_log` -- a
  resolution record's natural predecessor is "the last roll in this session."
  `verify_resolution_chain` takes an already-`tenant_scope`'d session (unlike
  `core.audit.verify.verify_chain`, which opens its own) so a caller verifying inside a
  larger transaction doesn't need a second connection.
- **`actor_fields` is caller-injected, never taken from the tool call's own arguments.**
  If the model could supply its own stats in the tool call, that would just move the
  hallucination vector from "claimed modifier" to "claimed stats" -- the entire point of
  the trust chain is that *trusted* state (today: an injected `ActorFieldsResolver`
  closure; after F3.6, a real Entity read) computes the modifier, never anything the
  model asserts. `make_dice_roller_handler` takes this resolver as a required parameter,
  matching every other C1.x injection seam.
- **`roll_dice` is a pure function of `(parsed_expression, modifier, seed)`** -- no
  wall-clock, no unseeded global RNG state, nothing but its three arguments. That purity
  *is* the INV-10 replay property: `test_seed_disclosure_reproduces_the_recorded_rolls_exactly`
  calls it a second time, independently, from nothing but the disclosed seed, and gets
  byte-identical rolls.
- **`render_resolution_fact` is complete and tested but not yet wired into
  `assemble()`'s render pipeline.** No caller in Phase 1 assembles a context that also
  runs a resolution in the same turn yet -- C1.2 through C1.5 all flagged the identical
  "not yet integrated into the runtime" gap for their own pieces. `manifest.resolution_ids`
  stays empty until that wiring lands (a natural D1.3/G4.13-era follow-up, not a redesign).
- **`ToolDefinition` is descriptive metadata, not a dispatch mechanism.** `impl_ref`
  values like `"builtin:dice_roller"` are documentation of which real Python handler
  implements a tool -- this module never reads `impl_ref` and looks up/executes code
  from it (CLAUDE.md rule 10: no user-authored code, ever). Actual dispatch stays exactly
  where B1.7 put it: a `core.agents.tools.ToolRegistry` mapping wired at the composition
  root.
