# F3.9 — INV-9 pack test ★

**Phase:** 3 · **Track:** F · **Est:** 3d · **Status:** done
**Depends on:** F3.7, F3.8 · **Blocks:** F3.14
**Plan refs:** §4.2 INV-9, §15.6, §15.10 bottleneck 3

## Goal
The operational definition of "generic": CI boots the RPG and enterprise packs, runs a smoke
session in each, and asserts **zero core diffs**. Without this test, genericity is an
aspiration. F3.14 extends the same harness to the swdev pack — build the harness
pack-count-agnostic from the start.

## Subtasks
- [x] `tests/packs/` harness: for each shipped pack — load (schemas, FSMs, axes, overlay,
      rule systems, tools, processes validate through the standard loaders), provision a
      test tenant, run a scripted smoke session (a deterministic tool call through the
      unmodified `ResolutionService`, an entity mutation, and an FSM transition — see
      scope note on "retrieval" and "a phase transition"), assert completion.
- [x] **Zero-core-diff assertion**: the harness runs against the installed core with no
      pack-conditional code paths — enforced by (a) the packs-independence lint (no core
      imports in packs) and (b) a new core-side lint (`tests/architecture/
      test_pack_literal_lint.py`) that no module under `packages/core/` references a
      pack identifier (`rpg`, `enterprise`, `swdev`) as a code-level string literal
      (AST-based, so it doesn't flag a docstring *explaining* the rule).
- [x] Pack registry drives the matrix: `pathlib.Path("packs").iterdir()`, discovered at
      collection time and `pytest.mark.parametrize`'d — adding a pack directory adds a
      test case (F3.14 is a two-file addition: a schema/process/etc. directory plus a
      `smoke.json`, never an edit to this harness).
- [x] CI-blocking from this task onward: `tests/packs/` now has real tests, so
      `run-blocking-suite.sh`'s exit-5-tolerance (empty suite) never triggers again;
      also added the `packs` CI job's missing Postgres service + migration step (it
      had none — silently vacuous even once real tests landed).

> **Scope note.** "A few turns exercising retrieval" is not literally exercised (no
> knowledge sources are attached in the smoke fixtures — retrieval needs a live
> embedding provider this environment doesn't have, the same "not yet wired into the
> runtime" gap already documented pervasively elsewhere in this codebase, e.g. C1.2's
> own docstring). "A phase transition" is interpreted as the entity's own FSM
> transition (`core.entities.mutation.transition`) rather than the process engine's
> phase graph, since driving `advance_session` needs a real actor-turn executor no
> smoke test here wires up; F3.8's own test already proves the process phase graph is
> structurally traversable via the unmodified interpreter. Each pack ships its own
> `<pack>/smoke.json` (schema key, entity data, mutation changes, a resolution request,
> an FSM transition) — the harness itself contains zero pack-specific logic, only
> generic interpretation of whichever smoke-fixture keys are present.

## Acceptance criteria
- Both packs load and complete their smoke sessions in CI on an unmodified core.
  → `test_all_shipped_packs_boot_and_run_smoke_sessions`
- A deliberately-planted core reference to a pack literal fails the core-side lint.
  → `test_core_referencing_a_pack_literal_fails_lint`
- A deliberately-planted pack import of `packages/core` fails the packs-independence lint.
  → `test_pack_importing_core_fails_lint`

## Design decisions
- **The matrix is data-driven so F3.14 is two lines, not a fork.** The invariant was
  reworded in plan v1.2 to "every shipped pack"; a harness hardcoding two pack names would
  re-encode the old wording as structure.
