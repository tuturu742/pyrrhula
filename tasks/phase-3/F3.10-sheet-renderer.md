# F3.10 — Sheet renderer

**Phase:** 3 · **Track:** F · **Est:** 8d · **Status:** done (partial — see scope note)
**Depends on:** F3.4 · **Blocks:** —
**Plan refs:** §10.4, req 19

## Goal
Auto-generated graphical entity representation (req 19): the tag→widget React components and
`ViewDef`-driven layout that turn any schema into a sheet — bars for `resource`, chips for
`status_set`, attribute+modifier blocks, progression meters, and history charts from
`entity_state_change`. A pure function of schema + data; zero domain knowledge in the
components.

## Subtasks
- [x] `web/src/features/entity-sheets/` widget set, one component per core tag contract:
      `resource` bar (uses `max_ref`, `low_threshold` colour break), `status_set` chip row,
      `attribute` (+`modifier_source` computed modifier display), `progression`
      progress-to-next (via `curve_ref`), `identity`/`descriptor` text blocks,
      `relationship` links.
- [x] `ViewDef` layout engine: grouping, ordering, tabs; unknown-to-ViewDef fields fall into
      a default group rather than disappearing.
- [x] History charts from `entity_state_change` (per-field timeline; the progression chart
      is the same component as any numeric field's — literally `HistoryChart`, parameterised
      by `fieldPath`, not two components).
- [x] `private`-tagged fields render only for viewers whose scope allows — driven by the
      API's already-filtered response, never by client-side hiding (new
      `GET /entities/{id}` endpoint, reusing F3.6's `visible_fields` filter rather than
      reimplementing it).
- [x] Live updates over the existing SSE hook when a session mutates the entity.
- [x] All labels through the vocabulary resolver (`label_key`); hardcoding "Hit Points" in
      a component is a bug (agent-guide §7) — every widget takes a `labelKey` prop and
      calls `useLabel()`, never a literal string.

> **Scope note.** The `modifier_source` "computed modifier display" needed a small,
> honest backend addition beyond the task's own file list: `GET /entities/{id}` now also
> evaluates a `modifier_source` field's `tag_metadata.modifier_formula` server-side (the
> same "the engine computes, the client never does" discipline as F3.1's derived fields)
> and returns it as `modifier` — without this, the frontend would have needed to
> evaluate CEL itself, which no frontend code in this repo does or should.
> `progression`'s "progress-to-next via `curve_ref`" is not implemented: no curve-
> evaluation mechanism exists anywhere in this codebase (a `curve_ref` is presently just
> an opaque string in `tag_metadata`), so `ProgressionMeter` renders the raw value (and,
> when a caller supplies one, a value/threshold ratio) but never resolves a curve --
> a real gap, not silently patched over. Live SSE updates are wired and tested
> (`EntitySheetContainer` invalidates its query on an `entity_state_changed` event for
> this entity's id), but no backend code emits that event kind yet -- the same "seam
> built, backend emission deferred to a live turn loop" pattern this codebase uses
> throughout (e.g. `core.assembler.context_assembler`'s own injection seams).
