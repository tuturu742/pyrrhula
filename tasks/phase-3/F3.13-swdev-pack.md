# F3.13 — swdev pack ★ (D15)

**Phase:** 3 · **Track:** F · **Est:** 6d · **Status:** done (partial — see scope note)
**Depends on:** F3.4, C1.5, E2.3 · **Blocks:** F3.14, G4.16
**Plan refs:** §14.5 (D15), §10.4, §15.6

## Goal
The software-development pack: work-item/PR/build entity schemas with lifecycles as FSMs,
engineering process templates, the `swdev_v1` overlay, an swdev axis pack, and the
`checklist_v1` rule system — the swdev analogue of the dice roll, keeping the D5/INV-7
trust chain exercised in a third domain. Pure content, zero core imports (rule 9): if
modelling a software team needs a core change, D15's premise is wrong and Phase 3 is when
to find out.

## Subtasks
- [x] `packs/swdev/schemas/`: `work_item` (FSM backlog→ready→in_progress→in_review→
      changes_requested→approved→merged→done, plus `blocked` reachable from any active
      state; tags: lifecycle `[status_set]`, remaining estimate `[resource]`, story-point
      rollup `[progression]`, assignee/reviewer `[relationship]`, `[identity]`,
      `[descriptor]`); `pull_request` (draft→open→changes_requested→approved→merged|closed;
      `[relationship]` to its work item); `build` (queued→running→passed|failed;
      `[modifier_source]` for merge-gate guards).
- [x] **Pure-CEL merge guard** — `pull_request` may enter `approved` only when its linked
      `build` FSM state is `passed`: a cross-entity guard written entirely in the
      declarative vocabulary, proving D7 suffices for real engineering policy.
- [x] `packs/swdev/processes/`: `triage` (propose→prioritise→assign),
      `plan → implement → review → merge` (the `implement` stage declares a delegation
      `await` — satisfied by G4.16 later; in this phase the smoke test injects the outcome),
      `standup` (round-robin status).
- [x] `packs/swdev/rule_systems/checklist_v1/`: deterministic definition-of-done /
      review-rubric evaluation — CEL predicates over entity state + declared inputs,
      executed by the unchanged `ResolutionService` (C1.5/C1.6), producing a
      `ResolutionRecord` per evaluation. The model *requests* a checklist run; the engine
      computes the verdict.
- [x] `packs/swdev/tools/`: `checklist_eval`, `estimate_rollup` (pure aggregations →
      `ResolutionRecord`).
- [x] `packs/swdev/axes/`: `review_strictness` (low-stakes, banded prompt directives — "you
      wave things through" → "you block on nits"), `escalation_propensity` (binds toward
      `await`), `risk_tolerance` (**`stakes: high` ⇒ gate binding** — exercising E2.3's
      enforcement in a third domain).
- [x] `overlay/swdev_v1.json` per the Appendix-A column (Engineering Manager / Engineer /
      Work Item / Embargoed Info / …).
- [x] `packs/swdev/seed/`: a small **original** engineering handbook + review rubric into
      the library tenant (D13) — original text, no licensing pass needed (unlike the SRD).

> **Scope note.** Four honest simplifications, each forced by an existing core primitive
> that doesn't (yet) support the literal thing the subtask names, resolved the same way
> this codebase has resolved every such gap all session: pick the closest real primitive,
> document the gap, never fake it.
> 1. **No cross-entity guard primitive exists.** `core.entities.fsm`'s guards evaluate
>    only against the transitioning entity's own `fields.*` — there is no mechanism for
>    one entity's transition to read another entity's state. The merge guard is
>    therefore `fields.build_status == 'passed'` on `pull_request` itself, where
>    `build_status` is a plain mirrored field, not a live reference to the `build`
>    entity. `test_merge_guard_is_pure_cel_over_the_generic_interpreter` drives both
>    entities' real FSMs and mutates the mirror field between them, standing in for the
>    sync a real delegation/webhook integration (G4.16) would eventually automate.
> 2. **`AwaitSpec.type` is `Literal["human_input"]` only** (`core/process/dsl/schema.py`)
>    — there is no `"delegation"` await type today. The `implement` phase's await uses
>    `"human_input"` as the delegation placeholder, exactly as the task's own design
>    decision anticipates ("the delegation await ships before delegation exists").
> 3. **`GateSpec.on` is a closed vocabulary** (`"actor_declares_action"` or
>    `"timeout(<duration>)"` only, `core/process/dsl/schema.py`) — a gate cannot branch
>    on an arbitrary decision name like `"approved"`/`"changes_requested"` the way the
>    subtask's prose implies. `review`'s gates use `actor_declares_action`/`timeout(72h)`
>    (mirroring the RPG/enterprise fixtures' own only-available shape) rather than
>    inventing a new gate-event vocabulary, which would be a core change this task isn't
>    scoped for.
> 4. **`estimate_rollup` got its own `rule_systems/estimate_rollup_v1/` directory**
>    (`outcome_bands` are global to a rule system, not per-`check_type` — sharing
>    `checklist_v1`'s pass/fail bands with a raw-sum aggregation would have collided
>    ranges) rather than living inside `checklist_v1/` as the subtask's own wording
>    implies. Not independently acceptance-tested; `checklist_eval`/`checklist_v1` are.
>
> Also: `packs/swdev/overlay/swdev_v1.json` needed a **new** migration
> (`f7b2e9c4a1d6`, a fresh `INSERT`), not an `UPDATE`-merge like F3.7/F3.8's overlay
> migrations — D1.6's base seeding migration never pre-seeded a `swdev_v1` row (D15
> postdates Phase 1).

## Acceptance criteria
(all in `tests/isolation/test_swdev_pack.py`)
- A `pull_request` whose linked `build` is not `passed` cannot transition to `approved`;
  flipping the build to `passed` allows it — both through the generic FSM interpreter, no
  core changes.
  → `test_merge_guard_is_pure_cel_over_the_generic_interpreter`
- `checklist_eval` writes a `ResolutionRecord` and the verdict renders from the record
  (INV-7) — a model asserting "all checks passed" contrary to the record is decoration,
  flagged by C1.7's existing check.
  → `test_checklist_verdict_renders_from_resolution_record_not_prose`
- `risk_tolerance` without a gate binding fails pack validation (E2.3's rule fires on swdev
  content).
  → `test_swdev_high_stakes_axis_requires_gate_binding`
- Zero imports from `packages/core/`; no core module references a swdev literal.
  → `test_swdev_pack_has_zero_core_imports`

## Design decisions
- **A checklist is the swdev dice roll.** The alternative — no RuleSystem for swdev — would
  leave the trust chain (D5) unexercised by the third pack and invite review verdicts to
  live in model prose. A deterministic rubric evaluation is nearly free and keeps INV-7
  meaningful in the domain where this project will dogfood itself.
- **`pull_request` and `build` are pack schemas, not core nouns.** The forbidden-word rule
  (CLAUDE.md rule 1, extended in v1.2) applies to core; this pack is exactly where those
  words belong.
- **The delegation `await` ships before delegation exists.** The process template declares
  the interface (suspend at `implement`, resume on outcome); G4.16 fills it. F3.14's smoke
  injects the outcome so the pack is testable a phase early.
