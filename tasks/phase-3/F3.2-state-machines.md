# F3.2 — State machines

**Phase:** 3 · **Track:** F · **Est:** 6d · **Status:** done
**Depends on:** F3.1 · **Blocks:** F3.5
**Plan refs:** §10.3, §12.5

## Goal
Declarative FSMs on entity schemas: states with tags and enter/exit effects, transitions
with CEL guards and triggers. The req-18 bet in one definition shape:
`healthy → bloodied → unconscious → dead` and
`draft → submitted → in_review → approved → archived` are the same structure. Every state
change lands in the append-only `entity_state_change`.

## Subtasks
- [x] `StateMachineDef` model: `key`; `states: [{key, label_key, tags[], on_enter: [Effect],
      on_exit: [Effect]}]`; `initial`; `transitions: [{from, to, trigger, guard: CEL,
      effects: [Effect]}]`.
- [x] `Effect` vocabulary: `set_field` | `emit_event` | `invoke_tool` | `apply_modifier` |
      `transition_other` — declarative only, validated at save (an effect referencing a
      nonexistent field/machine fails schema validation).
- [x] Progression pattern: derived field + `on_change` trigger (level-up fires when the
      derived `level` crosses a threshold) — a fixture proving no special-cased
      "progression engine" exists. Implemented as a plain trigger-name *convention*
      (`"on_change:<field>"`) rather than new interpreter logic: whatever computes a new
      derived value (F3.5) calls the same `evaluate_and_record_transition` with that
      trigger string — no separate code path exists for it.
      → `test_progression_pattern_is_a_trigger_convention_not_a_special_engine`
- [x] `entity_state_change` ‡ (append-only, no UPDATE/DELETE grant): `entity_id`,
      `session_id` (nullable — G4.2 writes outside sessions), `event_seq`, `field_path`,
      `old_value`, `new_value`, `cause` ∈ tool|fsm|human|agent|import, `cause_ref`. RLS +
      isolation tests in this PR.
- [x] Static validation: reachability from `initial`, no transition to undeclared states,
      guards compile (reuses B1.1's validator patterns and F3.1's CEL check).

> **Scope note.** `evaluate_and_record_transition` provides the guard-check + append-row
> step in isolation, matching F3.5's own task description ("row lock semantics deferred
> to F3.5 -- this task owns shape, not mutation policy"): no transaction locking, effect
> execution, or idempotency wraps it yet. F3.5's `EntityMutationService.transition()`
> wraps this exact function with `SELECT ... FOR UPDATE`, effect execution, and the
> idempotency key check, per `docs/phase-workflow.md`'s "build the tested piece, defer
> full-pipeline wiring" pattern. `entity_state_change.entity_id` has no FK yet (the
> `entity` table doesn't exist until F3.3, which adds it via `ALTER TABLE`).

## Acceptance criteria
- A guarded transition with a false CEL guard is refused and leaves no state-change row; a
  true guard transitions and appends exactly one row with `cause='fsm'`.
  → `test_guard_refusal_writes_nothing_and_success_writes_one_change_row`
- The HP-style and ticket-style fixtures run through the identical interpreter code path
  (coverage assertion, no domain branches).
  → `test_health_and_ticket_lifecycles_share_the_interpreter_path`
- The app role cannot UPDATE/DELETE `entity_state_change` (grants, not convention).
  → `test_entity_state_change_is_append_only_as_grants`
- A machine with an unreachable state or dangling transition target fails validation with
  the state named.
  → `test_unreachable_state_and_dangling_target_fail_validation`

## Design decisions
- **Effects are declarative because rule 10 is absolute.** `invoke_tool` names a registered
  deterministic tool; it does not carry code. Anything a pack "needs" beyond this vocabulary
  is a missing core abstraction to raise, not to work around (rule 9).
