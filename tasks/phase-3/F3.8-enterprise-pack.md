# F3.8 — Enterprise pack ★

**Phase:** 3 · **Track:** F · **Est:** 6d · **Status:** done
**Depends on:** F3.4 · **Blocks:** F3.9
**Plan refs:** §10.4, §14.1, §15.6, §15.10 bottleneck 3

## Goal
The pack that exists to falsify the genericity bet. It has no customer, no revenue, and it
will feel like a distraction — it is the phase's most important task. Ticket-lifecycle and
project-status schemas, the brainstorm→critique→revise→decide process, the enterprise axis
pack, a policy-lookup tool, and the `enterprise_v1` overlay — all with zero core diffs. If
this cannot be done without core changes, that is the most important negative result the
project can produce, and Phase 3 is when to learn it — not Phase 5.

## Subtasks
- [x] `packs/enterprise/schemas/`: ticket lifecycle
      (draft→submitted→in_review→approved→archived as an FSM, plus a request_changes
      back-edge in_review→submitted), project-status schema (`budget_remaining
      [resource]`, `blockers [status_set]`, owner `[relationship]`) — deliberately
      reusing the exact tags the RPG pack uses, because that reuse *is* the test.
- [x] `packs/enterprise/processes/`: brainstorm → critique → revise → decide, with
      per-phase visibility (critique phase narrows `entity_fields` to a smaller set —
      the closest existing lever to "hides authorship"; see scope note) and an `await`
      decision node that loops back to `brainstorm`.
- [x] `packs/enterprise/axes/`: the §8.7 mapping as pack data — concession threshold,
      uncertainty disclosure, escalation propensity (stakes:high + gate binding — see
      scope note on "binding to `await`"), position advocacy; the high-stakes entry
      carries a gate binding (E2.3's validation enforces, fires on enterprise content
      exactly as it does on RPG content).
- [x] `packs/enterprise/tools/`: policy-lookup as a `DeterministicTool` (pure lookup →
      `ResolutionRecord`, citable) — expressed as a `RuleSystem` with a 1-sided "die"
      (always rolls 1) and a CEL modifier resolver encoding the actual lookup logic, so
      it goes through the exact same `ResolutionService.resolve()` as a dice roll.
- [x] `overlay/enterprise_v1.json` (pack-owned labels, merged into the existing system
      overlay via migration, mirroring F3.7's rpg_v1 approach).

> **Scope note.** "Escalation propensity (binding to `await`)" — `await` isn't one of
> E2.3's five fixed binding kinds (`prompt_directive`/`gate`/`retrieval_bias`/
> `sampling`/`tool_policy`); the closed taxonomy is authoritative, so this axis is
> `stakes: high` with a `gate` binding instead (same pattern RPG's `secret_disclosure_
> propensity`/`deception_propensity` use). "Critique phase hides authorship" has no
> literal field-hiding primitive in the DSL beyond `visibility.entity_fields`'s named-
> field-list form, used here as the closest available lever — a real per-message
> authorship-hiding mechanism (if the product needs one) is a process-engine feature to
> raise, not something this pack can express on its own.

## Acceptance criteria
- The brainstorm→critique→revise→decide process runs a smoke session end to end with zero
  diffs under `packages/core/` (asserted by F3.9's mechanism; this task provides the
  session fixture).
  → `test_enterprise_process_smoke_session_runs_with_zero_core_diffs`
- The project-status sheet renders through the same tag→widget registry entries as the RPG
  sheet — budget bar and HP bar are one component.
  → `test_project_status_renders_via_the_same_resource_widget`
- Policy lookup produces a `ResolutionRecord` rendered from the record (INV-7), citable in
  a reply.
  → `test_policy_lookup_writes_and_renders_from_resolution_record`
- Zero imports from `packages/core/` (packs-independence lint).
  → `test_enterprise_pack_has_zero_core_imports`

## Design decisions
- **Do not let this slip** (§15.10). Every pressure in the phase will push it to "after the
  RPG pack polish". The RPG pack proves the floor is comfortable; this pack proves the
  architecture is generic. Only the second claim is load-bearing for the company (Q1 made
  the overlay the business model).
