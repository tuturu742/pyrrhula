# F3.5 — Entity mutation service

**Phase:** 3 · **Track:** F · **Est:** 4d · **Status:** done
**Depends on:** F3.2 · **Blocks:** F3.6, G4.2, G4.16
**Plan refs:** §10.3, §5.6, §12.5

## Goal
The single write path for entity data and FSM transitions: row locking, guard evaluation,
effect execution, `entity_state_change` append, and idempotency — one service that every
caller (tools, process effects, human edits, imports, and later G4.16's delegation
outcomes) goes through.

## Subtasks
- [x] `EntityMutationService`: `mutate(principal, entity_id, changes, cause, cause_ref,
      idempotency_key)` and `transition(principal, entity_id, machine_key, trigger, ...)` —
      permission-checked via `PermissionService`, never inline role logic (rule 12).
      Function-based, not a class (matches `core.resolution.service.resolve`'s
      established module-function style over a stateless service object).
- [x] Concurrency: `SELECT ... FOR UPDATE` on the entity row + optimistic `version` bump;
      concurrent mutation of the same entity serialises, stale-version writes are rejected
      (proven against a real Postgres with two genuinely concurrent `asyncio.gather()`
      callers, not mocked locking).
- [x] FSM path: evaluate guard (CEL, against locked current state) → apply transition →
      run effects in order → append `entity_state_change` rows — all one transaction.
- [x] Idempotency (CLAUDE.md rule 8): reuses `core.actions.idempotency.idempotent`
      (the same claim-before-execute primitive every other side-effecting call site
      uses) rather than a second implementation; the caller supplies the
      `(session_id, event_seq, attempt_target)` key directly, per this task's own
      `mutate(..., idempotency_key)` signature.
- [x] Out-of-session mutations (G4.2's future callers): `session_id` nullable on the change
      row, `cause` ∈ tool|fsm|human|agent|import covers the provenance.

> **Scope note.** `emit_event`/`invoke_tool` effects have no wired consumer yet (no
> event bus, no tool registry reachable from `core.entities` without inventing one) --
> recorded into the mutation result's `side_effects` list rather than silently dropped
> or executed against fabricated infrastructure. `transition_other` (an effect
> transitioning a *different* machine on the same entity) is likewise recorded, not
> executed recursively -- real cross-machine effect execution is additive once a real
> caller needs it. Seeded a new `entity:mutate` role_permission action (granted to
> `facilitator`/`participant`, mirroring `secret:author`'s shape) since none existed.

## Acceptance criteria
- Two concurrent transitions on one entity serialise: exactly one state-change row per
  applied transition, versions strictly monotonic, no lost update.
  → `test_concurrent_transitions_serialise_without_lost_updates`
- Replaying a mutation with the same idempotency key executes nothing and returns the
  original result.
  → `test_replayed_mutation_is_a_noop_returning_recorded_result`
- Guard, transition, effects, and change rows commit atomically — a planted effect failure
  rolls back the transition entirely.
  → `test_failed_effect_rolls_back_the_whole_transition`
- A mutation without permission is rejected before the row lock is taken.
  → `test_permission_denied_before_locking`
