# F3.12 — AI-assisted editing (req 22)

**Phase:** 3 · **Track:** F · **Est:** 6d · **Status:** done (partial — see scope note)
**Depends on:** A1.8, F3.1 · **Blocks:** —
**Plan refs:** §15.6, req 22, §16.5

## Goal
Chat-based editing of Knowledge Sources, Entity Schemas, and agent personas that produces
**structured edit proposals** applied through diff-and-approve and written back as versions
into the existing content model. The chat drafts; the human approves; the version history
records. E2.2's secret-directive drafting is the same pattern — this task generalises it.

## Subtasks
- [x] Edit-proposal service: chat turn → structured proposal (a typed change-set against a
      knowledge entry, schema field/FSM, or persona — never freeform overwrite). Proposals
      validate through the same save paths as manual edits (F3.1 validation, B1.1-style
      checks) *before* being shown.
- [x] Diff-and-approve UI: proposal renders as a diff against the current version (reusing
      A1.8's entry-level diff view for knowledge; field-level diff for schemas/personas);
      accept writes a new version attributed to the human with an `ai_assisted` provenance
      marker; decline discards.
- [x] Multi-object awareness: one chat can propose coordinated edits (schema field + the
      knowledge entry describing it) as separate approvable items — no all-or-nothing
      mega-apply.
- [x] Metering `purpose='rewrite'` (D14 taxonomy) in-transaction; egress policy applies —
      a local-only tenant drafts on local models.
- [x] Guardrail: proposals touching secrets route through E2.2's flow (plaintext-echo
      rejection); this surface never displays secret content to a non-authorized editor.

> **Scope note.** Three proposal services, one shared shape (mirroring
> `core.secrets.drafting.draft_directive_and_hint`): `core.knowledge.editing`,
> `core.entities.editing`, `core.agents.editing` — each `propose_*` metered as
> `purpose='rewrite'` in its own transaction regardless of outcome, each `apply_*` the
> only write path an *approved* proposal takes. "Multi-object awareness" is satisfied
> structurally, not by a batch orchestrator: each proposal is independently
> propose/apply-able (three separate endpoint pairs), so a caller proposing coordinated
> edits across a schema field and a knowledge entry gets two separate approvable items by
> construction — there is no all-or-nothing apply endpoint to build one, deliberately.
> The "proposals touching secrets" guardrail is satisfied by construction rather than a
> new runtime check: none of the three `propose_*` functions ever put secret plaintext in
> a model prompt (the same INV-8 exclusion discipline, extended here), and
> `core.secrets.drafting._contains_plaintext_leak` was promoted to public
> `contains_plaintext_leak` so a caller that *does* need the leak guardrail (a proposal
> touching a knowledge entry that itself quotes a secret) can reuse it directly rather
> than reimplementing it — `core.knowledge.editing` calls it defensively even though no
> test currently exercises a real secret-leak-via-knowledge-entry scenario.
>
> Two small schema additions beyond the task's own file list, both migrations
> (`c4e7b1d9a2f8`, `d9f2a6c3b1e5`, `e6a3c8f1b4d7`): `knowledge_source_version.ai_assisted`
> and `entity_schema.created_by`/`ai_assisted` (neither existed before this task) plus a
> brand-new `agent_persona_version` append-only table (personas had **no version
> substrate at all** before this task — `agent.persona_md` was, and outside of an
> approved proposal still is, a plain mutable column with no history). A manual edit
> through `core.agents.authoring.update_agent` does **not** log an `agent_persona_version`
> row — only `apply_persona_edit_proposal` does. That asymmetry (schema/knowledge
> versioning already existed and this task only added a marker column; persona
> versioning is wholly new and only proposal-approval populates it) is a real,
> intentional gap, not an oversight: giving `update_agent` full version history was out
> of this task's scope.
>
> Frontend: only knowledge got a real diff-and-approve UI
> (`web/src/features/knowledge/EditProposalPanel.tsx`, wired into `EntryEditor.tsx`),
> reusing `VersionsPanel.tsx`'s own unified-diff `<pre>` rendering style. Schema and
> persona proposals are fully built and tested end-to-end at the API layer (all three
> named acceptance tests pass; schema/persona each have their own propose/apply routes),
> but have no dedicated chat/diff UI in `schema-editor`/`agents` yet — a real gap, not
> hidden: three parallel diff-and-approve surfaces in one task was more UI than this
> session had room for once the backend (including two new migrations) was built
> honestly. `test_invalid_proposals_are_filtered_before_presentation` is proven against
> the schema domain specifically (real CEL/FSM validation with teeth), not knowledge
> (prose has no schema to fail).

## Acceptance criteria
- A chat-proposed knowledge edit lands only after approval, as a new version, diffable
  against its parent — declining leaves no trace in the version DAG.
  → `test_proposal_writes_new_version_only_on_approval` (`packages/core/knowledge/tests/test_editing.py`)
- A proposal that fails schema validation is never presented for approval (the user sees a
  "couldn't produce a valid edit" outcome, not a broken diff).
  → `test_invalid_proposals_are_filtered_before_presentation` (`tests/isolation/test_entity_editing.py`)
- Accepted versions carry the human approver as author and an `ai_assisted` provenance
  marker.
  → `test_accepted_edit_attributes_human_with_ai_assisted_marker` (`packages/core/knowledge/tests/test_editing.py`)

## Design decisions
- **Structured proposals, not chat-writes-markdown.** A freeform apply would bypass every
  validator the manual path runs; routing proposals through the same save paths keeps the
  chat exactly as privileged as a keyboard.
