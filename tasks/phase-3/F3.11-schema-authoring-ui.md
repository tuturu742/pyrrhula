# F3.11 — Schema authoring UI

**Phase:** 3 · **Track:** F · **Est:** 8d · **Status:** done (partial — see scope note)
**Depends on:** F3.1 · **Blocks:** —
**Plan refs:** §10.1, §16.5, §15.6

## Goal
The authoring surface for EntitySchemas: field editor, FSM editor (reusing D1.2's React Flow
canvas), semantic-tag picker, and a CEL editor with live validation. **Templates only —
never an empty schema** (§16.5): the median user starts from a pack template and tweaks;
the blank-canvas field builder is the generic-platform trap this product refuses.

## Subtasks
- [x] `web/src/features/schema-editor/`: field list editor (type, enum values, ranges,
      `indexed` flag), tag picker constrained to F3.4's nine tags with per-tag metadata
      forms (`max_ref` picker for `resource`, formula editor for `modifier_source`, …).
- [x] FSM editor on the D1.2 React Flow canvas — states as nodes, transitions as edges,
      guard/effect inspectors; validation surfacing inline (unreachable state, dangling
      target) exactly as the process editor surfaces B1.1 errors.
- [x] CEL editor with live compile feedback (server-side compile check endpoint; errors
      anchored to the expression).
- [x] Template-first flow: "new schema" opens the template gallery (pack-provided schemas +
      workspace copies); "start from blank" exists but is explicitly secondary and starts
      with a guided minimal template, not an empty field list.
- [x] Versioning: edits save as new schema versions; entities pin their schema version;
      the version history reuses the A1.8/D1.1 presentation pattern (see scope note on the
      "diff view" half of this subtask).

> **Scope note.** Two small, honest additions beyond the task's own file list, both
> mirroring precedent this codebase already set: (1) `core.entities.repo.list_schema_
> versions()` + `GET /entities/schemas/versions` — `list_latest_schemas` (F3.1)
> deliberately collapses to one row per key, so it structurally cannot serve a version
> history panel; without a distinct query, "version history" would have shown only the
> latest version, which isn't history at all. (2) The extracted `web/src/features/
> process-editor/FlowCanvas.tsx` shared module (the acceptance test's own subject) — it
> didn't exist before this task; `ProcessCanvas.tsx` was refactored to render through it
> too, so both graph editors now share one `<ReactFlow>` shell rather than the FSM editor
> importing a module that only *coincidentally* looked reusable.
>
> **Real gaps, not silently patched over:** the version history panel is view/restore
> only — no structured diff between two versions exists anywhere in this codebase yet
> (A1.8/D1.1's own panels are the same "list + restore," no diff), so "diff view" in this
> subtask's original wording is aspirational, not delivered. The FSM canvas does not
> persist dragged node positions (unlike `ProcessCanvas`, which has a localStorage
> layout key convention keyed by workspace+defKey) — positions recompute from a fixed
> grid layout on every render; a real gap to close if hand-tuned FSM layouts turn out to
> matter, not a hidden shortcut. Guard/effect inspectors are plain forms, not the
> process editor's richer `PhaseInspector` (no actor/budget-equivalent concepts exist on
> an FSM transition to warrant that), but every field `EffectDef`/`TransitionDef` accepts
> is editable and validation-anchored.
