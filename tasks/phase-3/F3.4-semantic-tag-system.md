# F3.4 — Semantic tag system ★

**Phase:** 3 · **Track:** F · **Est:** 4d · **Status:** done
**Depends on:** F3.1 · **Blocks:** F3.7, F3.8, F3.10, F3.13
**Plan refs:** §10.4 (D7), §15.6

## Goal
How a generic engine renders an HP bar without knowing what HP is: fields carry semantic
tags from a **fixed core vocabulary**, and a tag→widget registry maps them to render
behaviour. `hit_points [resource]` and `budget_remaining [resource]` and a work item's
remaining estimate are the same bar. Tags, not field names, drive rendering (D7).

## Subtasks
- [x] The fixed core tag vocabulary — exactly these nine, closed set: `resource`,
      `attribute`, `status_set`, `progression`, `identity`, `descriptor`, `relationship`,
      `modifier_source`, `private`. A pack inventing a tag fails schema validation; a tag
      the core doesn't ship is a core change to propose, not pack data.
- [x] Per-tag metadata contracts: `resource` → `{max_ref, low_threshold}`;
      `attribute`+`modifier_source` → `{modifier_formula}` (CEL);
      `progression` → `{curve_ref}`; `status_set` → enum-array field; `private` → per-field
      `scope_key` participation.
- [x] Tag→widget registry (data, not switch statements): tag → widget identifier; the
      React components land in F3.10 — this task defines the registry contract and core-side
      validation.
- [x] `ViewDef` model: layout (grouping, ordering, tabs) referencing fields by key —
      making an RPG sheet *feel* native is a ViewDef content problem, not an engine problem.
- [x] Tag validation in F3.1's save path: unknown tags, missing required tag-metadata, or a
      `resource` whose `max_ref` doesn't resolve → field-level errors.

> **Scope note.** `modifier_formula` (the `modifier_source` contract) is also CEL
> compile-checked at save time, reusing F3.1's `core.entities.cel.compile_check` against
> the schema's own field types — not explicitly named in the subtask list but a direct
> consequence of "CEL for logic because it's bounded" applying uniformly. `ViewDef`
> dangling-reference validation (a group/tab referencing an undeclared field/group) is
> hooked in alongside tag validation, mirroring F3.2's dangling-transition check.

## Acceptance criteria
- A pack schema using an unknown tag is rejected at load with the tag and field named.
  → `test_unknown_semantic_tag_fails_schema_validation`
- The registry maps every core tag to a widget id and contains no domain-conditional logic
  (static inspection: no references to pack content).
  → `test_tag_widget_registry_is_total_and_domain_blind`
- Three `resource` fixtures — HP, budget-remaining, work-item remaining-estimate — produce
  identical registry lookups differing only in metadata values.
  → `test_three_domains_resolve_resource_to_the_same_widget`

## Design decisions
- **A closed set on purpose.** An open tag vocabulary quietly becomes field-name semantics
  again, and the renderer grows a switch per pack — exactly what D7 forbids. Nine tags
  covered every schema in §10.4's analysis across all three overlays; the tenth tag is a
  deliberate core decision when a real pack proves the need (INV-9 keeps everyone honest).
