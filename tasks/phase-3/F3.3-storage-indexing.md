# F3.3 — Storage + indexing

**Phase:** 3 · **Track:** F · **Est:** 4d · **Status:** done
**Depends on:** F3.1 · **Blocks:** —
**Plan refs:** §10.5, §12.5

## Goal
Entity storage: JSONB data validated against the schema on write, `fsm_states` JSONB, and
**generated columns** hoisted per-schema for fields marked `indexed: true` — JSONB
flexibility with real index performance on the two or three fields a workspace actually
queries (initiative, status, owner).

## Subtasks
- [x] `entity` table: `tenant_id`†, `workspace_id`, `schema_id`, `key`, `name`, `scope_key`,
      `data` JSONB, `fsm_states` JSONB (`{"health": "bloodied", "quest": "active"}`),
      `version INT`, `updated_at`; RLS + isolation tests in this PR. Also ALTERs
      `entity_state_change.entity_id` to add the FK F3.2 deliberately left off (the
      `entity` table didn't exist yet).
- [x] Per-schema migration generator: `indexed: true` fields produce Postgres generated
      columns + btree indexes via an Alembic-emitting helper; removing the flag drops them.
      Generated-column names are derived and namespaced (`gc_<field>_<schema-id-hash>`) --
      the schema-id hash suffix (beyond just avoiding collision with the `entity` table's
      own real columns) is what lets two *different* schemas each index a field with the
      same key without their generated columns colliding. Each column's expression and its
      partial index are schema-conditional (`CASE WHEN schema_id = ... `/`WHERE schema_id
      = ...`) since every schema's entities share this one table.
- [x] Scope: `entity.scope_key` (and per-field `scope_key` where the schema declares one)
      participates in the same visibility model as knowledge (§7.2) — required, defaultless
      on every entity query the assembler makes (INV-4 discipline).
- [x] Write path: validate against schema version → compute derived (transient, for
      constraint-checking only, F3.1) → bump optimistic `version` → row lock semantics
      deferred to F3.5 (this task owns shape, not mutation policy).

> **Scope note.** The generator needs `ALTER TABLE`/`CREATE INDEX` privileges the
> RLS-restricted `pyrrhula_app` role doesn't have (and shouldn't be granted — a DDL grant
> is a much bigger blast radius than the DML an app role needs). Added
> `core.tenancy.scope.admin_ddl_session()`, a second, narrow, explicitly-documented
> exception alongside `unscoped_session()` — connects as the migration/admin role for
> schema DDL only, never for tenant data. `indexed: true` on an `array`-typed field is
> rejected (a scalar generated column can't represent one; that would need a GIN/JSONB-
> path index, a different mechanism this task doesn't build). F3.2's own test fixtures
> used synthetic (non-existent) `entity_id`s since no `entity` table existed at the time
> — amended forward in this PR (`tests/isolation/test_entity_state_change.py` now creates
> real `entity` rows) now that the FK exists to enforce against them, per
> `docs/phase-workflow.md`'s "fix it there and amend forward" rule.

## Acceptance criteria
- Marking a field `indexed: true` and running the generator yields a generated column whose
  query plan uses the new index (EXPLAIN assertion on the fixture).
  → `test_indexed_field_produces_generated_column_used_by_planner`
- The generator's migrations are reversible (upgrade → downgrade → upgrade clean).
  → `test_index_generator_migrations_are_reversible`
- Entity queries without a `scope_key` argument do not typecheck/construct — the parameter
  is required and defaultless.
  → `test_entity_queries_require_scope_key_with_no_default`
