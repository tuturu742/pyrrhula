# F3.1 — EntitySchema

**Phase:** 3 · **Track:** F · **Est:** 6d · **Status:** done
**Depends on:** T0.3 · **Blocks:** F3.2, F3.3, F3.4, F3.11, F3.12
**Plan refs:** §10.1, §10.2 (D7), §12.5

## Goal
The generic Entity Schema: typed fields as a JSON Schema 2020-12 subset, derived fields and
cross-field constraints as CEL, versioned per workspace (or pack-provided). D&D characters
and support tickets and work items are the same object; nothing in core knows what HP is.
No user-authored code, ever (D7, CLAUDE.md rule 10).

## Subtasks
- [x] `entity_schema` table: `tenant_id`†, `workspace_id` (nullable → pack-provided),
      `key`, `version`, `fields` JSONB, `derived` JSONB, `state_machines` JSONB,
      `views` JSONB, `constraints` JSONB; `UNIQUE(tenant_id, workspace_id, key, version)`
      (tenant_id added to the plan's literal wording — a bare `(workspace_id, key,
      version)` would let two different tenants' pack-provided schemas, both with
      `workspace_id IS NULL`, collide); RLS + isolation tests in this PR.
- [x] Pydantic models for the composition object: `fields: [FieldDef]` (the 2020-12
      subset — types, enums, arrays, ranges; no `$ref` recursion, no remote refs),
      `derived: [DerivedDef]` (CEL over fields, e.g.
      `level = ceil(sqrt(fields.xp / 100))`), `constraints: [CEL predicate]`
      (e.g. `fields.dexterity >= 13 && fields.level >= 3`).
- [x] CEL compile-check at save time via `celpy` (the same discipline as B1.1's process
      validation); bounded evaluation, no I/O — a schema whose expressions don't compile is
      rejected with field-level errors.
- [x] Validation-on-write service: entity data validates against its schema version; derived
      fields are computed, never stored as authored values; constraint violations reject the
      write with the failing predicate named.
- [x] Explicitly rejected alternatives documented in the module docstring, per §10.2:
      RestrictedPython (sandbox escapes are not a boundary), JsonLogic (too weak), Starlark
      (Q8's fallback — revisit in this phase's exit review with pack-author evidence, not
      before).

> **Scope note.** `state_machines`/`views` are typed here as loose JSON placeholders
> (`list[dict[str, object]]`) — F3.2 (`StateMachineDef`) and F3.4 (`ViewDef`, tag
> validation) replace the placeholder types and add their own save-time validation in
> place, per `docs/phase-workflow.md`'s "amend forward" pattern. Tag vocabulary
> validation for `FieldDef.tags`/`tag_metadata` is likewise F3.4's hookup, not this task's.

## Acceptance criteria
- A schema with an uncompilable CEL derived field is rejected at save with the offending
  expression named; a valid schema round-trips through the API typed.
  → `test_bad_cel_rejected_at_save_with_field_level_error`
- Writing entity data violating a constraint fails with the predicate identified; a
  compliant write computes derived fields server-side.
  → `test_constraint_violation_rejected_and_derived_fields_computed_on_write`
- The same schema machinery expresses an RPG attribute block and a ticket record with no
  core branching on domain (fixture pair, one per overlay family).
  → `test_rpg_and_ticket_schemas_use_identical_core_paths`
- Cross-tenant schema reads return zero rows with the ORM filter omitted.
  → `test_entity_schema_cross_tenant_filter_omission_returns_zero_rows`

## Design decisions
- **JSON Schema for fields because it's boring**: standard validators, JSON round-trip, and
  free form generation for F3.11. **CEL for logic because it's bounded**: non-Turing-complete,
  no I/O, safe for untrusted expressions in a shared process.
- **Derived is computed, not cached-authored.** Storing a derived value invites drift; the
  cost of recomputation is trivial at entity scale.
