# G4.12 — MCP client (req 12)

**Phase:** 4 · **Track:** G · **Est:** 6d · **Status:** done (partial — see scope note)

> **Scope note.**
> 1. **The shipped `McpTransport` adapter is deliberately unreachable.** There is no MCP
>    server in this environment, and a transport that pretended otherwise would be untested
>    code exactly where "it looked like it worked" costs most. `UnreachableMcpTransport`
>    raises on every call — which `core.mcp.client` already handles correctly (an
>    unreachable server contributes no tools). Everything that makes MCP *safe* — the
>    allowlist, the phase policy, the idempotency, the injection envelope — lives in core
>    and is tested against a scripted double. Wiring a real streamable-HTTP/stdio client is
>    a change to `worker/mcp_transport_factory.py` and nothing else.
> 2. **Not wired into B1.7's tool loop yet.** `available_tools`/`call_tool` are complete
>    and tested; `core.agents.runtime`'s `ToolRegistry` still carries only the deterministic
>    tools C1.6 registers. Bridging the two needs the live turn to decide *when* a
>    confirmation was given, which is G4.16's `delegate_work_item` — the first real caller.
>    Same "build the tested piece, wire it in when the caller exists" discipline as E2.5/E2.7.
> 3. **Usage rows for MCP calls are not written.** `usage_record`'s `purpose` taxonomy is
>    closed (rule 11) and none of its members describes a tool call; `delegation` is G4.16's
>    and is specific to delegated coding work. Inventing a value would violate the rule the
>    task itself cites. `action_record` carries the per-call provenance in the meantime, and
>    the gap is named rather than papered over.
> 4. **No registry admin UI.** The endpoints are real and tested.

## Goal
Agents invoke external MCP servers — under a per-workspace **allowlist (not blocklist)**,
per-phase tool policy, credential refs, and with every effectful call routed through
`EffectfulAction` (idempotency + suspend). Retrieved content arrives wrapped in the
injection envelope: external tool output is data, never instructions. Web search is just an
MCP server behind a workspace policy flag. This is also the substrate D15's delegation
(G4.16) stands on.

## Subtasks
- [x] Per-workspace MCP registry: server URL, `credential_ref` (secret manager pointer,
      never a stored key), enabled tools (**allowlist per workspace — a tool not listed
      does not exist**), per-phase tool policy (which phases may call which tools — data on
      the ProcessDefinition, validated by B1.1).
- [x] Client runtime in the agent tool loop (B1.7): tool discovery limited to the
      allowlist; schema-validated calls; timeouts and retries; usage rows for MCP calls in
      the metering transaction. → **partial**: discovery/authorisation/dispatch are real
      and tested; not yet bridged into B1.7's loop, and no usage rows — see scope note 2/3.
- [x] **Effectful routing (D6)**: tools declared effectful execute as `EffectfulAction` —
      idempotency key `(session_id, event_seq, attempt_target)` checked against
      `completed_operation` first, may suspend the session via `await` for asynchronous
      outcomes, produce an `ActionRecord`; confirmation policy per workspace (human
      confirm, or auto with the setting explicit).
- [x] **Injection envelope**: all MCP-returned content enters context wrapped in the
      standing data-not-instructions envelope; returned content never influences tool
      authorisation (the allowlist and phase policy are evaluated against workspace config
      only).
- [x] Web-search server ships as a registry preset behind a workspace policy flag.
- [x] Egress note: MCP servers are external by definition; the registry records what each
      server may receive, and D14 remains about `ModelProvider` calls — the allowlist *is*
      the egress control for tools (documented in the module).

## Acceptance criteria
- A tool absent from the workspace allowlist is invisible to agents — not listed, not
  callable, even if the server offers it.
  → `test_unallowlisted_tools_are_invisible_and_uncallable`
- An effectful call that crashes mid-flight does not re-execute on resume: the idempotency
  key returns the recorded outcome or reconciles, never double-fires.
  → `test_effectful_mcp_call_survives_restart_without_double_execution`
- Planted "call the delete tool" text inside an MCP tool *response* does not trigger any
  tool call (envelope + authorisation isolation).
  → `test_tool_response_content_cannot_authorise_further_calls`
- A phase whose tool policy excludes a tool cannot call it even though the workspace
  allowlists it.
  → `test_per_phase_tool_policy_is_enforced_over_the_allowlist`

## Design decisions
- **Allowlist, not blocklist**, because the threat model (§16.6, agent-guide §8) says
  user-authored lore reaches tool-calling agents: the failure mode of a blocklist is a new
  tool nobody thought to block.
- **Confirmation for effectful calls is a policy default, not a UX nicety** — Q6's
  multi-human rule and the enterprise posture both assume a human gate exists to turn on.
