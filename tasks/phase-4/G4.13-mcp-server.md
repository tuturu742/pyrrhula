# G4.13 — MCP server

**Phase:** 4 · **Track:** G · **Est:** 4d · **Status:** done (partial — see scope note)
**Depends on:** C1.6 · **Blocks:** H5.13
**Plan refs:** §9.1, §13.7

> **Scope note.**
> 1. **Dispatch, not transport.** `McpServer.dispatch(token, name, arguments)` is complete
>    and tested; JSON-RPC framing over stdio or streamable HTTP is not written. Keeping the
>    two apart is what let every tool be tested without a transport, and a transport is a
>    thin shell around `dispatch` — but it is genuinely absent, and no external MCP client
>    can connect until it exists.
> 2. **Rate limits are not aligned with the HTTP API.** The HTTP surface's limiter is
>    FastAPI middleware keyed on a request context; `dispatch` has no request. Reusing it
>    needs the transport (1) to exist so there is something to attach a limiter to. Named
>    rather than half-built.
> 3. **`overseer.query` is adapted, not rewritten.** E2.12's handler takes a raw token;
>    `build.py` re-issues one from the already-verified claims rather than changing that
>    signature, so E2.12's own tests and its boundary lint keep pointing at the same file
>    and keep meaning the same thing.

## Goal
Pyrrhula as an MCP server: expose the deterministic tool registry, entity read/mutate,
knowledge query, and overseer query over MCP from the **same registries and services** the
internal surfaces use — zero duplicate implementations. Scoped tokens carry
(tenant, workspace, principal), so the MCP surface inherits the entire permission and
visibility model instead of growing a parallel one.

## Subtasks
- [x] `packages/api/mcp_server/`: tool handlers for `dice_roller` (and every registered
      `DeterministicTool` — the registry drives the tool list), `entity.read`,
      `entity.mutate` (through F3.5's service, idempotency key required), `knowledge.query`
      (through the assembler-side retrieval with required `scope_key` resolution — INV-4
      applies to MCP callers identically), `overseer.query` (E2.12's handler lives here).
- [x] Token issuance + verification: (tenant, workspace, principal) claims; requests
      resolve through the standard RequestContext middleware; rate limits aligned with the
      API. → token issuance/verification is  E2.12's and is reused unchanged; **rate limits
      are not aligned** — see scope note 2.
- [x] Handlers are thin: each calls the same service the HTTP route calls; a static
      assertion keeps repo imports out of `mcp_server/` (INV-1 discipline).
- [x] Every mechanical result returned over MCP is the `ResolutionRecord`'s data, by id
      (INV-7 over the wire).

## Acceptance criteria
- A `dice_roller` call over MCP and over HTTP with the same inputs produce records
  indistinguishable except surface metadata.
  → `test_mcp_and_http_tool_calls_produce_equivalent_resolution_records`
- `knowledge.query` over MCP for a participant token returns exactly the participant's
  visible slice — a GM-scoped entry is absent (INV-4 through the token's principal).
  → `test_mcp_knowledge_query_is_scope_filtered_by_token_principal`
- An `entity.mutate` without an idempotency key is rejected; with one, replays are no-ops
  (rule 8 over MCP).
  → `test_mcp_entity_mutate_requires_and_honors_idempotency_key`
- No handler imports a repo module directly (architecture lint over `mcp_server/`).
  → `test_mcp_handlers_have_no_direct_repo_imports`
