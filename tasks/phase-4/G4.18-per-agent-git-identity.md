# G4.18 — Per-agent git identity (distinct bots for review & merge)

**Phase:** 4 · **Track:** G (D15 swdev) · **Est:** 3–4d · **Status:** in-progress (m1 adapters, m2 storage, m3 worker/automerge and m4 credential-binding UI are all done; only the live-token spike remains)
**Depends on:** G4.16 (coding-agent delegation), portability git remotes
**Blocks:** a real GitHub review→approve→merge gate for the swdev workflow
**Plan refs:** D15

> **Why this is not cosmetic.** Today a repo registration carries **one** access token
> (`RepoRow.credential_ref` → a single sealed `provider_credential`), so every push, PR,
> comment and merge is one "platform" identity. The GitHub adapter already documents the
> wall this builds: *"GitHub refuses formal reviews from the PR's own author, which the
> platform token is"* (`adapters/gitremote/github.py`). With one identity the reviewer
> agent can only leave **issue comments** — never a formal Approve / Request-changes — so
> the swdev review loop can be *narrated* but never *enforced* by the host's own gate.
> Giving each acting persona its own token makes engineer-bot open the PR, reviewer-bot
> file a real approving review, and manager-bot merge — attribution becomes true and the
> approval gate becomes real. This is the swdev face of Pyrrhula's thesis: who-did-what
> enforced by identity, not asserted in prose.

## Goal
Let a persona act on a hosted git remote (GitHub/GitLab/Gitea) under **its own** provider
identity, resolved per action, falling back to the repo's default token when a persona has
none. Add the two remote actions that only become meaningful with distinct identities —
**submit a formal review** and **merge** — and surface per-persona token binding in the UI.
No adapter rewrite: the `GitRemote` protocol already threads `token` per call.

## Acceptance criteria

- A persona with its own bound credential opens/comments/reviews/merges under **that**
  identity on GitHub; a persona with none uses the repo default. Verified against a
  recorded-HTTP fixture asserting the `Authorization` token per call matches the resolved
  identity.
  → `test_remote_action_uses_acting_persona_token_with_repo_fallback`
- The reviewer persona files a **formal** Approve/Request-changes review when it is not the
  PR author, and falls back to an issue comment (no 422) when it is.
  → `test_formal_review_when_reviewer_differs_from_author_else_comment`
- A merge order performed by the merger persona merges under that identity; a repo whose
  branch protection requires an approving review is mergeable only after the reviewer bot's
  approval lands.
  → `test_merge_order_merges_as_merger_identity`
- `persona_git_credential` is in the isolation negative-test suite and returns zero rows
  cross-tenant with the app filter omitted (CLAUDE.md rule 4).
  → `tests/isolation/test_filter_omission_matrix.py` (new row) + coverage guard
- No token appears in any table, log, or the UI read path — sealed `provider_credential`
  only; the picker is write-only.
  → `tests/leak/` scan for token-shaped strings on this path

## Operator note: creating the bots on GitHub

- **Machine users (recommended for distinct identities).** Ordinary accounts created for
  automation (GitHub ToS permits them); each gets a fine-grained PAT scoped to the repo and
  shows as a **distinct** commenter/reviewer/merger. On a **private org repo each is a paid
  seat**; on public repos they are free.
- **GitHub App(s).** One App = one bot identity (`app[bot]`), fine-grained perms, **no seat
  cost** — but no per-agent distinction unless you run one App per identity (heavier).
- Trade-off in one line: **machine users buy per-agent distinction at a per-seat cost; a
  GitHub App buys no seat cost but no per-agent distinction.** For "see who did what and
  gate merges on a real review," machine users win. Branch protection must grant the
  reviewer bot write access (and it must not be the PR author) for the approval to gate.
