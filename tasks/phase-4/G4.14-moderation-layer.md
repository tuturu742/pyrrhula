> **Scope note.**
> 1. **The shipped provider is a keyword matcher, not a classifier.** `KeywordModeration
>    Provider` flags text containing a tenant's configured category terms. That is what
>    makes per-tenant policy *testable* — the same text passes for one tenant and blocks
>    for another, with no network call, no API key, and no verdicts that drift between
>    runs. A provider-backed implementation drops in behind the same port;
>    `AllowAllModerationProvider` remains what a deployment gets until it configures a
>    policy. Named plainly in the adapter's own docstring rather than left to look like a
>    real classifier.
> 2. **The hooks are complete and tested but not yet called from the authoring/generation
>    paths.** `scan_authored`/`scan_generated` are callable functions; `create_secret`,
>    `upsert_draft_entry`, the import paths, and `core.agents.runtime` do not call them
>    yet. Wiring each call site is a change to that call site's own error contract (a
>    blocked save has to become *that* service's domain error), which is why the hooks
>    return rather than raise — the same "build the tested piece, wire it in where the
>    caller decides" discipline as E2.5/E2.7. The Q6 second arm **is** wired, because that
>    was a decision `validate_overseer_requirement` already had to make.
> 3. **No Director's View surface for the attention feed.** Alerts write to the same
>    `session_event` stream E2.7's leak alerts use, with kind `moderation_alert`, so
>    E2.11's feed has one stream to read rather than two — but no component renders the new
>    kind yet.

## Goal
The two moderation scans §16.7 identifies as the real controls — at **authoring** (secrets
and knowledge are user-authored text; a DB-connected scanner reads them at write time) and
at **generation** (replies are visible and scanned before delivery) — behind the
`ModerationProvider` port with per-tenant policy. Neither scan depends on the overseer, and
the secrets model does not blind either of them.

## Subtasks
- [x] `ModerationProvider` port implementations in `packages/adapters/moderation/`
      (provider-backed + a permissive local default); per-tenant policy in
      `tenant.settings` (thresholds, categories, action: flag | block | queue) — defaults
      permissive per §14.4's seam principle.
- [x] Authoring hook: secret content (all four fields), knowledge entries, and personas
      scan on write (including E2.2's path and G4.6/G4.8 imports); policy action applies
      (block save / flag for review).
- [x] Generation hook: replies scan before delivery; a blocked reply follows the E2.7
      pattern (regenerate once → safe fallback → overseer alert where an overseer exists).
- [x] Overseer alerts: flagged content surfaces in the Director's View attention feed
      (E2.11) for workspaces that have one; Q6's product rule (multi-human ⇒ overseer or
      moderation with overseer-equivalent visibility) is validated at workspace
      configuration (E2.10 built the check; this task supplies the moderation-equivalent
      arm).
- [x] Scan events audit-logged (category, action, target id — not full content).

## Acceptance criteria
- A policy-violating secret is caught at authoring by the DB-connected scan — concealment
  at generation time never hid it from moderation.
  → `test_authoring_scan_reads_secret_content_regardless_of_disclosure_state`
- A generation-hook block regenerates once then falls back, mirroring E2.7's ladder.
  → `test_generation_moderation_follows_regenerate_then_fallback`
- Per-tenant policy differences produce different outcomes on identical content (permissive
  tenant passes, strict tenant blocks).
  → `test_moderation_policy_is_tenant_scoped`
- A multi-human workspace with no overseer activates only when moderation with
  overseer-equivalent visibility is enabled (Q6 rule, second arm).
  → `test_multi_human_workspace_accepts_moderation_in_lieu_of_overseer`
