# G4.1 — Session resume + history repopulation (req 20)

**Phase:** 4 · **Track:** G · **Est:** 5d · **Status:** done (partial — see scope note)
**Depends on:** B1.4 · **Blocks:** G4.16
**Plan refs:** §5.4, §12.7, req 20

> **Scope note.**
> 1. **Prose is not viewer-filtered; the fact frame is.** The per-viewer acceptance
>    criterion is met through the fact frame (entity state changes filtered by the
>    entity's own `scope_key` through `scopes_for`, disclosures filtered by
>    `disclosed_to` / `secret:inspect`). `message` rows carry no scope column and a
>    session transcript is shared by construction — every principal in the session saw
>    every message live — so there is nothing to filter prose *on*. Inventing a
>    per-message scope here to make the filter look symmetrical would fabricate a
>    distinction the rest of the system does not make. Stated in
>    `core/sessions/history.py`'s docstring, not hidden.
> 2. **Not auto-invoked on resume yet.** `summarise_history` is complete, tested, and
>    registered as a worker job (`kind="summarise_history"`), and the assembler takes the
>    summary through a typed seam (`assemble(history_summary=...)`) that records its
>    provenance on the manifest. Nothing *automatically* enqueues it when a dormant
>    session wakes: that entry point is G4.3's "resume-into-context" subtask (a human
>    acting on a digest link lands in the session view with this summary path serving it).
>    Same "build the tested piece, wire it in when the caller exists" discipline as E2.5/
>    E2.7 (`docs/phase-workflow.md` §4).

## Goal
Resume an old session with its history usefully repopulated into working context: restore
from checkpoint, summarise elapsed history into the context under an explicit token budget,
and keep the summary honest — structured facts come from records, not from re-summarised
prose.

## Subtasks
- [x] Checkpoint restore path hardened for long-dormant sessions: `state`, `actor_cursor`,
      `entity_versions`, `knowledge_version_pins` reapplied; process-definition version
      pinned (a definition edited since the checkpoint does not silently apply — resume uses
      the pinned version, upgrade is an explicit action).
- [x] History summarisation (worker job, cheap model, `purpose='report'`): chunk elapsed
      `session_event` history by phase → summarise → reduce; **resolutions, entity changes,
      and disclosure events injected verbatim from their records into the summary frame**,
      never paraphrased from prose (the G4.10 principle, applied early).
      → `core/sessions/history.py` (`summarise_history`), `worker/history_summary.py`.
- [x] History token budget: a first-class slice of the phase budget (C1.2 enforces before
      retrieval, not truncation after); summary depth adapts to the budget.
- [x] Summary is per-viewer: generated through visibility filtering of the event stream for
      the *resuming context's* principal — a participant's recap never contains events they
      couldn't see live.
- [x] Manifest records the summary's source event range and hash (INV-10: the resumed
      turn's context replays).

## Acceptance criteria
- A session resumed after a checkpoint produces its next turn with the summary in context,
  within the declared history budget, and the turn replays from its manifest.
  → `test_resumed_turn_stays_in_history_budget_and_replays`
- A dice result in elapsed history appears in the summary with the recorded value even when
  a planted prose message lies about it.
  → `test_summary_takes_mechanical_facts_from_records_not_prose`
- Two viewers with different scopes get different summaries of the same elapsed history,
  each consistent with what they could see live.
  → `test_history_summary_is_visibility_filtered_per_viewer`
