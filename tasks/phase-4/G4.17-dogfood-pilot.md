## Goal
The end state D15 names, run for real once: a Pyrrhula session on a workspace whose
knowledge is **this repository**, where an Engineering Manager facilitator proposes the next
task from the ingested `tasks/` backlog, an engineer agent's work is delegated to a real
coding agent over MCP (real branch, real PR), a second engineer agent reviews in-session
against the rubric, and a human approves the merge. Not a demo script — a session whose
artifacts (events, manifests, resolutions, action records, the PR itself) are kept as the
pilot record.

      deliberately not attempted here.
- [x] `plan`: the assigned engineer agent drafts an approach in-session, grounded in
      retrieved standards (`CLAUDE.md`, agent-guide → `rules`-class citations visible in
      the context inspector).
- [x] `implement`: G4.16 delegation produces a real branch + PR on a fork/sandbox remote
      configured for the pilot; the session suspends on the `await` and resumes on the
      outcome. **Include one forced restart mid-delegation** proving
      reconcile-not-reexecute.
- [x] `review`: the second engineer agent reviews in-session; `checklist_eval` runs the
      pack rubric and writes a `ResolutionRecord`; the verdict renders from the record in
      the session view (INV-7).
- [x] `merge`: human `await` — the Engineering Director approves or rejects; the decision
      is a recorded event; the `work_item` walks its full lifecycle driven by records.
- [x] Pilot write-up: what the agents did well/poorly, where retrieval briefed badly
      (feeds the §15.9 code-aware-chunking trigger), where the process templates chafed —
      an honest artefact, deviations included.

## Acceptance criteria
- One task from this repository's backlog is proposed by the EM **from ingested
  knowledge** (the proposal message cites `tasks/` entries via validated citations, C1.8),
  implemented via a real delegated branch + PR, reviewed in-session, and human-approved —
  the `work_item` traverses backlog→…→in_review→approved driven by EffectfulAction
  outcomes and F3.5 transitions, never by prose.
  → recorded pilot session + `test_pilot_work_item_lifecycle_is_record_driven` (replaying
  the pilot's event log asserts every transition has a record-level cause)
- The forced restart mid-delegation produced no double-dispatched external call (exactly
  one branch, one PR, one completed action record for the attempt chain).
  → `test_pilot_restart_left_single_branch_pr_and_action_record`
- The review verdict shown in the session renders from the `checklist_eval`
  `ResolutionRecord` by id (INV-7 in the third domain).
  → `test_pilot_review_verdict_renders_from_record`
- Zero core diffs attributable to the swdev pack across the whole pilot (INV-9's claim,
  held under real use — the F3.14 lints stay green on the pilot's commit).
  → CI state on the pilot branch + `test_all_shipped_packs_boot_and_run_smoke_sessions`

## Design decisions
- **Human-confirmed dependency checks are honest scoping.** A markdown-parsing dependency
  tool would be a new deterministic tool with its own correctness bar; the pilot's job is to
  prove the loop, not to automate every judgment. The gap is named in the write-up, not
  hidden.
- **A sandbox remote, not the live repo.** The pilot exercises real git/PR machinery
  without making CI on `master` depend on an experiment. Graduating to the live repo is a
  decision the pilot write-up informs.
- **Synchronous cadence.** G4.3's async machinery exists, but the pilot runs sitting-down
  synchronous — one variable at a time.
