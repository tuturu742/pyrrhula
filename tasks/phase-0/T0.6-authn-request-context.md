# T0.6 — AuthN + RequestContext

**Phase:** 0 · **Track:** Infra · **Est:** 4d · **Status:** done
**Depends on:** T0.2 · **Blocks:** T0.8, T0.9
**Plan refs:** §4.1 (edge layer), §12.1

## Goal
Login, session/JWT issuance, and the middleware that turns every request into a
`RequestContext{principal, tenant_id, workspace_id}` before any handler runs.

## Subtasks
- [x] Local auth: register/login/logout endpoints via `IdentityProvider` (T0.3's argon2
      adapter). Issues a JWT (`api.auth.tokens`), returned in the body **and** set as an
      httponly session cookie; either is accepted by `get_request_context`.
- [x] `Principal` resolution (`api.middleware.auth.get_request_context`): token → verified
      claims → principal exists & not disabled → tenant membership check (re-checked on
      *every* request, not cached from token-issue time) → `RequestContext`. 401 for
      missing/invalid/expired token, 403 for disabled principal, no membership, or a
      token/header tenant mismatch.
- [x] Tenant resolution (`api.middleware.tenant.resolve_tenant_for_auth`): `X-Pyrrhula-Tenant`
      header (slug) for the pre-auth surface (register/login), falling back to
      `PYRRHULA_DEFAULT_TENANT_SLUG` when `PYRRHULA_SINGLE_TENANT_UI=true`. **Deviation:**
      header-based only, not subdomain — subdomain routing needs real DNS/hosting wiring
      that has no home in Phase 0; header is sufficient for API clients and revisit if a
      concrete subdomain deployment need shows up.
      Authenticated routes do **not** re-resolve tenant from a header at all — the tenant
      comes from the signed JWT claims; a `X-Pyrrhula-Tenant` header on an authenticated
      request is only checked for *consistency* against the token (mismatch = 403).
- [x] `api.dependencies.get_db_session` — the one FastAPI-injectable way a handler gets a
      session, always `tenant_scope(ctx.tenant_id)` under the hood.
- [x] Rate limiting (`api.middleware.rate_limit`): Redis **fixed-window counter**
      (`INCR`+`EXPIRE`), not a true token bucket — noted honestly since "token bucket"
      implies smoothing this doesn't do. Three keying dimensions: `rate_limit_by_ip` (auth
      endpoints, pre-principal), `rate_limit_by_principal` and `rate_limit_by_tenant`
      (protected endpoints, independent budgets — one exhausting doesn't affect the other).
- [x] Logout clears the session cookie. **Deviation:** no token rotation/refresh flow or
      server-side revocation list — v1 is a stateless JWT with a fixed 24h expiry; a
      logged-out token remains technically valid until it expires. Acceptable for
      dev-stage MVP; revocation is a Phase-5-adjacent hardening item.
      Disabled-principal handling (`disabled_at`) takes effect immediately (re-checked
      every request), not just after token expiry.

## Acceptance criteria
- [x] No route (except `/health`, `/auth/*`) is reachable without a resolved principal —
  `packages/api/tests/test_route_inventory.py`, walking FastAPI's full dependant tree
  (not just direct per-route dependencies). Demonstrated live: added a scratch unprotected
  route, confirmed the test failed, removed it, confirmed green again.
- [x] A principal from tenant A presenting a valid token cannot address tenant B's context —
  `test_valid_token_cannot_be_pointed_at_a_different_tenant` (403), plus RLS backstop.
  Verified over real HTTP against the running container, not just in-test.
- [x] Rate limit returns 429 with Retry-After — unit tests in
  `packages/api/middleware/tests/test_rate_limit.py`, plus verified over real HTTP by
  hammering `/auth/login` against the running container (429 hit at request 58/60, with a
  correct `Retry-After` header).

## Bugs found and fixed along the way
- **Orphaned principal on registration race.** Creating `Principal`+`Membership` then
  separately creating the `Identity` (two transactions) leaves an orphaned, unauthenticatable
  principal if identity creation fails (duplicate email race). Fixed: a best-effort
  pre-check plus cleanup-on-failure that deletes the orphan.
- **Cross-event-loop singletons.** `TestClient` runs the ASGI app on its own internal event
  loop, separate from the pytest-asyncio loop the test function and its fixtures run on. The
  module-level engine (`core.tenancy.scope`) and Redis client (`rate_limit`) singletons now
  rebind when the running loop changes, and their close/dispose functions are best-effort
  (skip closing a client bound to a different loop rather than crash attempting it). See
  `docs/agent-guide.md` §7 for the general pattern — this will recur for any new lazily-
  cached async client.
- **Route enumeration silently vacuous.** This FastAPI/Starlette version wraps
  `include_router()`'d routes in an opaque `_IncludedRouter` object rather than flattening
  them into `app.routes`; a naive walk of `app.routes` found zero `/auth`/`/me` routes and
  every "route must require auth" test passed *because there was nothing to check*, not
  because the mechanism worked. Fixed with a recursive walk through `.original_router.routes`
  plus an assertion that at least 5 routes are found, so this class of bug can't silently
  recur.
