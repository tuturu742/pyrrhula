## Goal
The one and only secret-plaintext read path outside the assembler:
`OverseerService.inspect(principal, workspace_id, query) → SecretView`, where the permission
check, the read, and the audit append are **one transaction** (INV-5). In-fiction rules
(`scope_key`) never block the overseer; permission rules (`secret:inspect`) always do.

## Acceptance criteria
- No code path reads secret plaintext without an audit row in the same transaction — a
  forced failure between read and append leaves neither visible.
  → `test_inspect_read_and_audit_row_are_atomic`
- A principal without `secret:inspect` gets a permission error and **no audit-free partial
  data**; scope rules alone never grant or deny overseer access.
  → `test_inspect_is_gated_by_permission_not_by_scope`
- The audit rows chain correctly: the verifier job detects a tampered `inspect` row.
  → `test_verifier_detects_tampered_inspection_audit_row`
- A multi-human workspace cannot be activated without a designated overseer; a solo
  workspace can.
  → `test_multi_human_workspace_requires_designated_overseer`

## Design decisions
- **One service for both surfaces.** The Director's View UI (E2.11) and the `overseer.query`
  MCP tool (E2.12) call this same service — two audit paths would drift and one would lie.
- **The overseer is a principal type with a permission, not a scope.** Scopes model
  in-fiction knowledge; `secret:inspect` models out-of-fiction authority. Collapsing them
  reintroduces the confusion §7.1 exists to prevent.
