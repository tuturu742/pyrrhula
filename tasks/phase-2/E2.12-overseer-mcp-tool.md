# E2.12 — `overseer.query` MCP tool

**Phase:** 2 · **Track:** E · **Est:** 2d · **Status:** done (partial — see scope note)
**Depends on:** E2.10 · **Blocks:** —
**Plan refs:** §7.4, §9.1, §13.7

> Scope note: §13.7 states plainly "Phase 4 ships MCP" (tasks/phase-4/G4.12,
> G4.13 -- MCP client and server transport/protocol wiring). `packages/api/mcp_server/`
> is otherwise an empty scaffold (just `__init__.py` from T0.1) with no JSON-RPC framing,
> no tool registry, and no `mcp` SDK dependency anywhere in this repo yet -- building a
> real protocol server here would be redoing G4.13's own job early and out of order. What
> this task actually builds, matching the "build the tested piece, defer full-pipeline
> wiring" pattern used throughout this track: the tool's own logic
> (`packages/api/mcp_server/tools/overseer_query.py`, a thin wrapper over
> `OverseerService.inspect()`) and its token model
> (`packages/api/mcp_server/tokens.py`, `(tenant, workspace, principal)` claims, JWT-based
> like the existing HTTP session token but tagged `"aud": "mcp"` so the two can't be
> cross-used). Both are fully real and independently callable now; G4.13 is what will
> eventually dispatch an actual MCP JSON-RPC tool call into `overseer_query()`. "Domain
> nouns" get a `label_key` via a `subject_kind.*`/`disclosure_state.*` namespace -- the
> same pattern `class.rules`/`class.lore`/`class.misc` already use for enum-shaped
> values (D1.6) -- rather than overloading the existing `entity.*` keys, which name
> nouns, not a secret's own classification of what it's attached to.

## Goal
Expose overseer inspection over MCP — same service, same permission check, same
audit-in-transaction path as the UI. A scoped token carrying (tenant, workspace, principal)
authenticates the call, so the MCP surface inherits the permission and visibility model
instead of re-implementing it.

## Subtasks
- [x] `overseer.query` tool in `packages/api/mcp_server/`: thin handler over
      `OverseerService.inspect()` — no logic of its own, no direct repo access (INV-1).
- [x] Token: (tenant, workspace, principal) claims; the resolved principal must hold
      `secret:inspect` (enforced by `OverseerService.inspect()` itself -- the tool adds no
      permission logic of its own). Not yet routed through the standard `RequestContext`
      HTTP middleware -- there is no HTTP request for an MCP tool call to arrive on until
      G4.13 exists; `verify_mcp_token` is this task's own equivalent resolution step.
- [x] Responses carry `label_key`s for domain nouns so MCP clients can overlay-resolve.
- [ ] Rate limit aligned with the API's overseer routes. Not built -- rate limiting
      (`api.middleware.rate_limit`) is FastAPI-dependency-based, keyed on an inbound HTTP
      request; there is no request for an MCP tool call to attach that dependency to until
      G4.13's transport exists. Flagging this explicitly as a gap for G4.13 to close, not
      silently dropping it.

## Acceptance criteria
- An MCP call and a UI call with the same principal and query produce the same audit-row
  shape — diffable except for the surface field.
  → `test_mcp_and_ui_inspections_write_identical_audit_shape`
- A token whose principal lacks `secret:inspect` is rejected before any secret read occurs.
  → `test_mcp_token_without_inspect_permission_reads_nothing`
- The handler contains no import of `core/secrets/repo` (the service is the boundary).
  → `test_mcp_handler_does_not_import_secrets_repo`
