## Goal
The structured behavioural-parameter framework: axis definitions as pack content, immutable
versioned profiles per agent, and the binding-kind taxonomy that decides *how* each axis is
enforced. The load-bearing rule: an axis declared `stakes: high` **must** carry a gate
binding — enforced at validation time, so a prompt-only malice slider cannot be authored at
all.

## Subtasks
- [x] `axis_definition` (pack content): `pack_id`, `key` (e.g.
      `secret_disclosure_propensity`), `label_key` (overlay-resolved — never a literal
      domain word), `range_min`/`range_max` (0..100), **`stakes` ∈ low|high**,
      `semantics_md`, `bindings` JSONB.
- [x] `behavior_profile` ‡ (immutable versions): `agent_id`, `version`, `pack_id`,
      `axis_values` JSONB, `created_by`; `UNIQUE(agent_id, version)`; a change is always a
      new version. Every `ContextManifest` records the version in effect (C1.3 wiring) —
      `write_context_manifest` gained a `behavior_profile_version` kwarg, resolved and
      passed by `core.process.live_session` via `get_current_behavior_profile`.
- [x] Binding kinds: `prompt_directive` | `gate` | `retrieval_bias` | `sampling` |
      `tool_policy`. An axis may carry several. `sampling` is documented as weak (nudges
      temperature/top_p — never a control claim).
- [x] **Validation rule: `stakes: high` ⇒ a `gate` binding is present.** Loading an axis
      pack that violates it fails at validation with a named error, not at runtime.
- [x] RLS + isolation tests for `behavior_profile` (tenant-scoped); `axis_definition` ships
      in packs and loads through the pack loader, not user CRUD — `create_axis_definition`
      is the idempotent upsert-by-`(tenant_id, pack_id, key)` load path, matching
      `create_rule_system`'s (C1.5) identical shape.
- [x] Axis-pack seeds for validation fixtures: the RPG axis examples from §8.2
      (talkativeness, cooperativeness, secret_disclosure_propensity…). The enterprise axis
      pack lands in F3.8 and the swdev axis pack (`review_strictness`,
      `escalation_propensity`, `risk_tolerance` with `stakes: high`) in F3.13 — this task
      builds the machinery they load into, not their content.

## Acceptance criteria
- An axis pack declaring `stakes: high` without a gate binding fails validation with a
  specific error naming the axis.
  → `test_high_stakes_axis_without_gate_binding_fails_validation`
- `behavior_profile` versions are immutable: updating axis values produces a new version;
  the app role cannot UPDATE an existing row.
  → `test_behavior_profile_versions_are_append_only`
- The profile version in effect at generation time is recorded on the `ContextManifest` and
  survives INV-10 replay.
  → `test_manifest_records_behavior_profile_version_and_replays_identically`
- `axis_definition.label_key` resolution: the UI renders overlay labels; no literal axis
  nouns appear in core API responses.
  → `test_axis_labels_resolve_through_vocabulary_overlay`

## Design decisions
- **Why the stakes split (§8.3).** 97% per-turn prompt adherence over 60 relevant turns is
  an ~84% cumulative leak probability — for a high-stakes axis, prompt injection is not a
  control, it is a delay. Low-stakes axes (talkativeness, formality) get prompt directives
  because occasional drift there is a style bug, not a product-ending event.
- **Immutable versions are the audit story.** "What disposition was this agent running when
  it concealed that?" must be answerable six months later; a mutable row destroys it.
