## Goal
The editor for the four faces of a secret — `content`, `gist`, `hint_text`,
`behavioral_directive` — with AI-assisted drafting of the directive and hint. §8.4 is blunt
about this: authoring the behavioural directive is the real cost of the exclusion design,
and the AI-assist pass is what makes that burden survivable. Without it, D4 dies of author
fatigue, not of architecture.

## Subtasks
- [x] `web/src/features/secrets/` editor: the four text fields, subject picker (entity /
      agent / workspace / knowledge entry), scope picker, holder management (add/remove
      holders with `holder_kind`), disclosure-state display (read-only — state changes come
      from events, not edits).
- [x] **AI-assisted drafting**: "given this secret content, draft (a) a behavioural
      directive the holder can act on without revealing the fact, and (b) a bounded hint
      variant." Proposals render as a diff-and-approve flow; nothing writes without explicit
      acceptance; accepted text saves as a new secret `version`. Model call uses
      `purpose='rewrite'` (D14 taxonomy).
- [x] Gist editor with a persistent caption: "the gate sees only this line — write it so a
      small model can judge topical relevance without learning the fact."
- [x] Empty-directive lint: saving a concealable secret with no `behavioral_directive`
      surfaces a warning ("concealment will produce a flat agent, not a motivated one").
- [x] Authoring-time moderation scan hook point (wired fully in G4.14): secret content is
      user-authored text and is scannable at write time — the secrets model does not blind
      moderation (§16.7). `core.secrets.authoring.create_secret`/`update_secret_fields`
      call the injected `ModerationProvider` (`api/moderation_provider_factory.py`, v1
      allow-all) before every content write; a rejection surfaces as 422.
- [x] Worked examples in the empty state, one per overlay: RPG hidden motive ("the innkeeper
      is the missing heir"), enterprise MNPI, swdev embargoed incident ("the outage was
      caused by our own migration script — undisclosed until the postmortem publishes").

## Acceptance criteria
- Plaintext `content` is fetched only for principals passing
  `PermissionService.check(principal, "secret:author", …)`; a participant's request for the
  same secret returns gist-level fields only.
  → `test_secret_content_requires_author_permission_and_participants_get_no_plaintext`
- The AI-assist endpoint never echoes `content` into the saved directive verbatim — a
  draft containing a fuzzy match of the plaintext is rejected with a visible warning.
  → `test_ai_drafted_directive_containing_plaintext_is_rejected`
- Accepting an AI draft creates a new secret version; declining leaves the record untouched
  (no silent writes).
  → `test_ai_assist_writes_only_on_explicit_acceptance_as_a_new_version`
- The AI-assist call is metered with `purpose='rewrite'` in the same transaction.
  → `test_ai_assist_usage_record_written_in_transaction_with_purpose_rewrite`

All four verified live over real HTTP through the FastAPI app
(`packages/api/tests/test_secrets_flow.py`), plus the leak-detection logic itself unit
tested directly (`packages/core/secrets/tests/test_drafting.py`) against a scripted
`ModelProvider`. Frontend: `pnpm typecheck`/`pnpm lint`/`pnpm build` all pass; no headless
browser is available in this sandbox to visually verify the rendered page (same
documented limitation as D1.2/D1.5).

## Design decisions
- **Draft-and-approve, not autopilot.** The AI pass proposes; the author owns the directive.
  A bad directive is the leading cause of `directive_leak_rate` (E2.8) — the UI's job is to
  make the author look at it, not to hide it behind automation.
- **No live "test my secret" chat here.** Tempting, but probing a secret properly is E2.8's
  scenario harness; a one-off chat box would give authors false confidence from n=1.
