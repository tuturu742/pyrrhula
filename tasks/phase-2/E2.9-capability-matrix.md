# E2.9 — Capability matrix

**Phase:** 2 · **Track:** E · **Est:** 3d · **Status:** done (partial — see scope note)
**Depends on:** E2.8 (done) · **Blocks:** —
**Plan refs:** §8.6 (capability matrix), §13.6

> Scope note: enforcement lives in a new, standalone
> `core.behavior.capability_validation.validate_profile_capability` — not folded into
> `core.behavior.repo.create_behavior_profile` itself, since that would create a circular
> import (`repo.py` already exposes `get_axis_definition`, which capability validation
> needs). No API route creates a `behavior_profile` yet (E2.3 is backend-only, see its own
> task notes), so there is no live call site wiring this check in ahead of
> `create_behavior_profile` — the same "build the tested piece, defer full-pipeline
> wiring" gap as E2.5/E2.6/E2.7. `model_capability` is a new global (non-tenant-scoped)
> table, matching `price_table`'s shape — not literally "extending `capabilities()`" on
> the `ModelProvider` port, since axis fidelity is inherently data (this task's own
> "data-driven, not code-driven" acceptance criterion), not a static per-adapter property
> the way `supports_tools`/`supports_json_mode` are.

## Goal
Turn E2.8's per-provider results into an enforced capability surface:
`ModelProvider.capabilities()` reports which behavioural axes are exposable per model, the
UI shows "unavailable on this model" instead of a slider that does nothing, and provider
content-filter surprises are detected rather than discovered by users.

## Subtasks
- [x] `model_capability` (new, global, non-tenant-scoped table): structured-output
      fidelity, per-axis `behavioral_fidelity` pass/fail from E2.8, and a reason code --
      the data-driven capability surface, queried by `core.behavior.capabilities
      .is_axis_capable`/`get_capability`, not a static `ModelProvider.capabilities()`
      extension (axis fidelity isn't a fixed per-adapter property the way
      `supports_tools` is).
- [x] Enforcement: `core.behavior.capability_validation.validate_profile_capability`
      raises `CapabilityRejectedError` (naming the model and axis) for a `stakes: high`
      axis whose model fails its stored capability check — not wired into
      `create_behavior_profile` itself (see scope note: no live caller exists yet either).
- [x] UI-facing API: `GET /model-profiles/axis-capabilities` returns `{axis_key, stakes,
      capable, reason}` per axis in a pack for a given provider/model — the reason code a
      disabled agent-config control needs; no React component consumes it yet (no
      behavior-profile-editing UI exists in Phase 2 at all, per E2.3's own scope note).
- [ ] Provider-filter detection (neutral `label_key` phrasing for axes whose vocabulary
      trips provider safety filters, e.g. "malice" → "adversarial disposition") — not
      built; no provider-filter-tripping incident has been observed to design against
      yet, and the fixtures' own `label_key`s (`axis.secret_disclosure_propensity` etc.)
      are already neutral by construction (E2.3).
- [x] Matrix regenerates from data, not code: `upsert_capability` is exactly what a
      nightly E2.8 run (or a manual correction) calls to flip a capability — proven by
      `test_capabilities_reflect_latest_eval_results`. No nightly job actually calls it
      yet (E2.8's own scope note: the nightly job runs the harness skeleton, not a live
      per-provider matrix that would produce real capability rows to upsert).

## Acceptance criteria
- A model failing gate-schema adherence in the latest eval refuses a high-stakes axis
  binding at validation, with an error naming model and axis.
  → `test_high_stakes_axis_rejected_on_incapable_model`
- Capability changes are data-driven: mutating the stored eval result flips
  `capabilities()` without a code change.
  → `test_capabilities_reflect_latest_eval_results`
- The UI state for a disabled axis includes the machine-readable reason code.
  → `test_disabled_axis_carries_reason_code_in_api_response`
